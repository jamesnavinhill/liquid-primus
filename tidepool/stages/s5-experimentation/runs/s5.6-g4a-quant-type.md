## Q4_K_L is dropped before it is scored, on the check registered before the numbers

The queue message for `d2ce6665` said: if a variant comes back within 5 MB of its plain Q4_K_M
counterpart, the tensor-type flags did not take effect and the arm is a re-run of Q4_K_M
whatever it scores. Both `Q4_K_L` builds came back at 0.731 GB, the same as plain Q4_K_M to the
megabyte. So `q6_K` on the embedding and output tensors changed nothing, and the two Q4_K_L
arms are not scored. Two eval arms of compute saved by a check that cost nothing.

The arithmetic says why, and confirms the reading rather than leaving it a guess. The tied
embedding/output tensor is 65,536 x 2,048 = 134.2M parameters. At `q6_K`'s 6.5625 bits per
weight that tensor is 110.1 MB; at `q8_0`'s 8.5 bits it is 142.6 MB, a difference of 32.5 MB.
The observed Q4_K_L-to-Q4_K_XL gap is 32 MB. So `llama.cpp`'s stock Q4_K_M recipe was already
placing that tensor at `q6_K` for this architecture, the `Q4_K_L` request asked for what it
already had, and `q8_0` is the only step left in that direction.

That is a fact about the G1 builds worth stating plainly: the shipped Q4_K_M arms were never
uniformly 4-bit. Their embedding and output tensor already carried 6.5 bits, and they still
missed the retention bar.

## What is being scored

`R3-Q4_K_XL` (job `d3ee0d7a`) and `C7-Q4_K_XL` (job `bd52b7bc`), one arm per card, both cards
at once. Same harness, same item counts, same clean-control arm, same serving shape as the six
G1 arms; the retention reference stays each checkpoint's own already-scored F16 export, so the
comparison is the one registered in s3 and not a new one.

Running the two concurrently is the operator's standing preference applied where it is safe: a
2-GPU cap is not a cap on parallel work, and parallelism across cards is exactly the kind that
does not reproduce the compute contention that corrupted the packed attempts.

## G4b was made buildable while these ran

`llama-imatrix` was not among the four targets the pinned b10622 build compiled, which is the
only reason calibrated quantization sits second in the ladder. `s5-llama-build` now takes an
`extra_targets` parameter, empty by default, so the G4b rung is `-p extra_targets=llama-imatrix`
rather than a code change made under time pressure after G4a's numbers land.

The tarball name is derived from the extra targets inside the job, never passed in. Every 4-bit
number this project recorded was served from `tidepool/llama-b10622-sm89.tar.gz`, downloaded by
that exact name; a build asking for `llama-imatrix` writes
`llama-b10622-sm89-imatrix.tar.gz` and has no parameter value that would let it write the pinned
object. Re-listing a base target is a no-op rather than a second identical tarball under a new
name. Verified on a local fixture across four argument shapes, the empty default among them,
which reproduces the pinned target list and object name exactly.

This is preparation and not a commitment. The stop rule in `s5.6-recovery-plan.md` is unchanged
and is read against G4a's numbers when they land.
