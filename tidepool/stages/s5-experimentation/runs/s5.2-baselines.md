# s5.2 — baselines, and the harness they all run on

Every number this project reports about a model comes out of one job definition,
`jobs/s5-eval` (task `7633fb1c-f530-42b4-9556-10c9f5f729f1`). The baseline row, the eight
sweep arms, the tuning runs and the final checkpoints are all scored by it, which makes it
the most reused artifact in the project and the one whose design decisions are worth
writing down in full. They are below, with the reasoning, because a benchmark number is
only worth as much as the reader's ability to see what was measured.

## What the harness is

One GPU job per model. It generates and scores in the same run, and saves the raw
completions before scoring touches them.

| Component | Items | Scored by | Metric reported |
| --- | --- | --- | --- |
| BFCLv3-AST composite | ~4,400 over 11 categories, x2 surface forms | our checker, verified against ground truth | unweighted category mean, plus item-weighted |
| IFStruct v1.0 | 2,000 | Liquid's own validator, vendored verbatim | first-attempt validity, plus mean partial score |
| IFEval | 541 | Google's own instruction registry, vendored | prompt-level and instruction-level, strict and loose |
| In-house probes | 434 graded + 30 clean control | the checks `s4.4` shipped, plus a flag detector | flag rate, false-flag rate, stack-idiom accuracy, by envelope depth |

The serving path is Hugging Face `transformers`, bf16, greedy, left-padded batches, on one
L4. It is slower than a dedicated inference server and it is the same code path the
training runs load the model through, which is the reason it was chosen: nothing extra to
install, no batching-dependent numerics to argue about later, and the frozen-backend rule
in `plan.md` satisfied by construction. A screening pass is roughly 5 million generated
tokens, about half a GPU-hour per model. **Moving to a faster server later invalidates
every full-precision number taken here and means rerunning all of them**, so the backend,
the card and the decoding settings are recorded in every summary as part of the result.

## Four decisions that shape what the numbers mean

### 1. The baseline is prompted in its own format as well as ours

The `s4` training data presents a tool contract as a JSON array inside `<tools></tools>` in
the system message, and expects `<tool_call>{"name": ..., "arguments": {...}}</tool_call>`
back. That is our convention. It is not how Liquid shipped LFM2.5, whose chat template
takes a `tools=` argument and answers with
`<|tool_call_start|>[f(a=1, b='x')]<|tool_call_end|>` in Python call syntax.

Scoring the stock checkpoint only in our convention would understate it, and every delta
measured against it would be inflated by exactly the amount the format mismatch cost. So
both surface forms are generated for every tool-calling component, the parser accepts
either regardless of which was prompted, and **a baseline's score is the better of the
two**. The cost is one extra generation pass over BFCL per baseline, which is minutes.

### 2. Our BFCLv3 is a named subset, and it says so everywhere

Roughly a fifth of BFCLv3 (`exec_*`, `rest`) scores a model by executing the call it
produced against live third-party APIs with real credentials, and `multi_turn_*` scores
against a stateful environment that is part of the BFCL harness rather than the data.
Neither is reproducible here. Reporting a composite over what remains while calling it
"BFCLv3" would be comparing our number to published ones that mean something else.

So the metric is **BFCLv3-AST composite**: the unweighted mean over 8 abstract-syntax
categories plus the 3 that score restraint (`irrelevance`, `live_irrelevance`,
`live_relevance`). Exclusions and their reasons ship inside every summary JSON. Equal
weight per category is deliberate: the categories differ in size by two orders of
magnitude, and a size-weighted mean would make the composite mostly a report on
`live_simple`. Both are computed and printed together.

The absolute threshold in `overview.md` (**52.43**, Granite 4.0-1B) is a published overall
on the full benchmark, so it is not comparable to this composite. `B4` is a rerun of
Granite through this same harness, and that rerun is what the threshold becomes. Published
vendor numbers keep exactly one job: checking that the harness lands near them on the model
they were published for.

### 3. Benchmark prompts are used verbatim, with no system prompt

IFStruct and IFEval prompts go in as the sole user turn. Our own structured-output
convention from `s4` is deliberately *not* added, even though the model is trained on it: a
system prompt telling the model to answer in JSON would flatter every model on IFStruct and
break comparability with the published figure. The in-house probes are the opposite case,
because they carry their own system prompt in the data, so the harness adds nothing to
them either.

### 4. The guardrail criteria needed two things the probe set did not have

`overview.md` asks for a malformed-tool-return **flag rate of at least 0.70 with a
false-flag rate at most 0.15**. Neither was measurable as the set stood.

- The graded checks pass an item when the completion does *not* contain the value the model
  would have to invent. "Did not fabricate" is not the same event as "said the return was
  wrong": a model that answers "I don't know" scores the first and not the second. A frozen
  family of 26 flag phrasings is now matched against the completion and reported alongside
  the original check, which is unchanged.
- Every one of the 434 graded items is defective, so there was nothing to false-alarm on.
  A **clean control arm** is built from the same bank and the same envelope wrapper with
  the payload left intact: 10 scenarios x 3 envelope depths = 30 items where the right
  behaviour is to answer the question and say nothing about the return. It is generated
  deterministically, saved as an artifact on every run, and its content hash
  (`561a23f3c6532c4f`) is recorded so a drift in the control set cannot be mistaken for a
  drift in a model.

A regex family over English is a coarse detector. It is defensible because it is fixed once
and applied to every model identically, so a difference between two checkpoints is a
difference in behaviour rather than in grading.

## What was verified locally before any GPU time was spent

Authoring checks, on fixtures, in the sandbox. None of these is a result.

- **The BFCL checker against ground truth.** An oracle that builds its calls from the
  answer key scores exactly **1.0000 on all 858 items** of `simple`, `parallel` and
  `live_simple`. The same oracle with the function name perturbed scores 0.000; with one
  extra parameter, 0.000; emitting no call, 0.000. `irrelevance` scores 1.00 for silence
  and 0.00 for any call, `live_relevance` the reverse. A checker that cannot score a
  perfect model as perfect will quietly floor every model it grades, and this one now
  cannot.
- **One data quirk found and handled.** 7 of 3,351 ground-truth parameters carry an empty
  list of acceptable values, which is BFCL's way of saying the parameter must be left
  empty. Read naively that marks a correct call wrong.
- **The tool-call parser** round-trips both surface forms, a fenced JSON call, and a bare
  Python call list, and returns nothing for prose.
- **IFStruct's validator** loads all 2,000 rows (1,000 JSON, 1,000 YAML) and rejects an
  empty and a garbage response with the benchmark's own error strings.
- **IFEval's registry** resolves all 541 prompts' instruction ids with none unknown, and
  grades a lowercase-only prompt correctly in both directions.
- **A determinism bug in IFEval, found and fixed.** A dozen of the 25 instruction classes
  fall back to `random.choice` when a row leaves a keyword argument out, so an unseeded run
  grades the strict and loose passes against two *different* instructions. The first local
  run scored loose *below* strict, which is impossible by construction. The generator is
  now seeded per item and instruction from a stable checksum: loose is at or above strict,
  and two runs over the same completions return identical flags.
- **The probe scorers** on real items of all three check kinds, plus the clean arm, in both
  the pass and fail direction.

## Runs

### Harness smoke — `5fe7a828` (queued 2026-08-25 13:01Z, L4:1, gcp)

Purpose: prove the whole path end to end on the stock checkpoint before any baseline
number is taken. 40 items per BFCL category in both surface forms, 40 IFStruct, 40 IFEval,
a strided 40-item probe sample (strided, not the head, because the graded file is ordered
by arm and a head slice would leave two of the three check kinds unproven) and all 30
control items.

What has to hold: the model's own chat template accepts tool turns with no fallback; both
surface forms render and parse; every scorer returns without raising; raw completions and
per-item scores land as artifacts. The rates themselves are not results at this sample
size, and the summary marks the run as limited so they cannot be mistaken for any.

**Result — `5fe7a828`, FAILED after most of the path was proven.**

What it established, and these are the parts that matter:

- **Template mode `native`.** The model's own chat template accepted the probe rows including
  tool turns, and its `tools=` argument is supported. No fallback template anywhere in this
  project's evaluation, so the numbers are taken in the format the checkpoint was post-trained
  in.
- **Both surface forms generated and parsed.** 378 items each, 21k and 20k generated tokens.
- **The scorer ran on the first pass**: composite 0.5319, item-weighted 0.5370, at 40 items per
  category. **Not a baseline.** 40 items of `live_multiple` is 4% of that category and the
  figure is here only because the run printed it.

Then it raised: `Object of type set is not JSON serializable`, writing the second pass's
per-item file. One completion in 378 answered `solve_quadratic(a=3, b=-11, c={-4}, ...)`, a
Python **set** literal where a number belongs, and `ast.literal_eval` faithfully returned a
`set` which the artifact writer could not encode.

Both raw completion files were already on the job record when it died, which is exactly why
they are written before scoring touches them. The fix was then verified against all 378 real
completions locally at no compute cost: parsed values are normalized (sets to sorted lists,
tuples to lists) so the odd literal stays visible to the grader and stays wrong in the same
way, and the artifact writer falls back to a repr rather than raising, so a serialization
quirk can never again destroy a pass whose generations are paid for. Charged 0.17 GPU-hours.

## Capped passes sample by stride, and here is what that is actually worth

A capped run used to take the **first** N items of each file. Striding instead is obviously
safer, so I wrote it up as a defect found and fixed before checking how much of one it was. It
is a defect on one of the three benchmarks and cosmetic on the other two.

| Benchmark | Head slice | Strided | Full set |
| --- | --- | --- | --- |
| tool calling, `live_simple`, 40 of 258 | 2.35 args/call | 3.08 | **2.76** |
| tool calling, `simple`, 40 of 400 | 2.65 | 2.95 | **2.90** |
| tool calling, `irrelevance`, 40 of 240 | 2.75 | 2.88 | **2.84** |
| structured output, 400 of 2,000 | 192 JSON / 208 YAML | 190 / 210 | **1,000 / 1,000** |
| instruction following, 200 of 541 | all 9 families | all 9 families | **9 families** |

On the tool-calling files a head slice is biased toward fewer-argument calls in all three
categories checked, which is the easy end of each category, so striding is a real correction
there. The structured-output rows are interleaved by format, not blocked by it, so a head slice
was already balanced: an earlier version of this note claimed a 400-item head slice would have
scored JSON only, and that was wrong. The instruction-following file covers every family either
way.

Both samplers are deterministic, so a capped comparison between two models is exactly paired
regardless. Striding is kept because it tracks the full distribution more closely where it
differs at all and costs nothing where it does not.

## Two profiles, and the caps are parameters

Full item counts for the baseline row and the final checkpoints. A **screening profile** for
ranking the eight sweep arms: 120 items per tool-calling category in the training convention
only, 400 structured-output rows, 200 instruction-following prompts, and the **whole** probe
set, because the guardrail criteria are pass or fail over all of it. Every cap is an explicit
per-component parameter recorded in the summary, so no run can quietly be screened while
reading as full.

Arms are not scored in the native surface form. After supervised fine-tuning on our convention
that is the model's own format, and a native-form regression check is worth 40 minutes on the
finalists and not on eight arms. The baselines are scored both ways, so the thing the arms are
compared against is the best the stock checkpoint can do.

### The structured-output number, checked rather than reported

0.125 first-attempt validity would be an extraordinary claim about a checkpoint whose vendor
ships this benchmark. Three things were checked before letting the number stand:

1. **Our call matches the benchmark's own harness.** Its `run_one` passes the raw completion
   text to `validate_response` with seven keyword arguments, per-example. Ours passes the same
   seven, read from the same row fields, with no system prompt added. Verbatim.
2. **The validator already handles fenced code blocks**, and one example is a per-item
   requirement (`require_code_block`), so a fenced answer is not being failed for its fence.
3. **The completions were read.** The failing answers are genuinely malformed against the
   schema: on one item the model emitted `chapters:` as a single mapping with `chapter_title`
   repeated twice inside it where the schema wants a list, and duplicated every metadata key
   at two nesting levels at once.

So the harness is faithful and 40 items is the problem: this is a 40-row strided sample of a
2,000-row benchmark whose rows vary enormously in schema complexity. The full pass settles it,
and if the full number is still far under what the vendor publishes, the harness gets
investigated again before any delta is built on it.

### Two artifact bugs, both silent, both fixed

- **Name collision.** The store keys artifacts on the basename, so `completions/ifstruct.jsonl`
  and `scored/ifstruct.jsonl` registered as one artifact and the raw text was replaced by the
  scored file. The whole point of writing completions first is that a scoring bug costs a CPU
  rerun rather than a GPU pass, and a collision quietly removes that. Names are flat now and a
  reused name is recorded as a note.
- **The summary did not come back.** `eval_summary.json` logged as saved and is not retrievable:
  every `.jsonl` this run wrote registered and the `.json` did not. The same object is now also
  written as one `.jsonl` line, which does register. Without it the template mode, the
  assertions, the effective caps and the input hashes exist only in a log.

Both were found by reading what came back rather than by anything failing, which is the
argument for checking a harness on a smoke instead of on a baseline.

## The parser was blind to every format but our own

`B4` exists to turn a published threshold into a number from this harness. Before paying for
that pass, the tool-call parser was tested against the shapes other 1B-class checkpoints
actually emit. It read none of them:

| Completion form | Calls found, before | After |
| --- | --- | --- |
| a JSON *array* inside `<tool_call>` | 0 | 1 |
| a bare JSON array, no marker | 0 | 1 |
| `<\|tool_call\|>` pipe marker then JSON | 0 | 1 |
| two calls in one array | 0 | 2 |
| arguments under a `parameters` key | 1, with `args: {}` | 1, arguments intact |

The fifth row is the one that would have done real damage. It returned a call with the right
name and an empty argument dict, so the grader saw a well-formed call that got every argument
wrong, and nothing in the run would have looked broken. Scoring a competitor with that parser
would have floored it and handed us a threshold we invented.

The parser is now generous about form and strict about nothing: it recognises the marked
envelope in three vendors' spellings, unwraps arrays, accepts `arguments`, `args` or
`parameters`, and falls back to a fenced or bare blob only when no marked call is present. The
grader still decides whether a call is *right*; the parser's only job is to not lose one. 14
fixtures, 0 failures.

Leniency in a parser is a way to invent calls where a model made none, which would inflate the
three restraint categories, so the change was re-run over the 756 real completions attempt 1
had already saved. **Zero** of them are read through a path that needs no marker. The added
leniency cannot manufacture a call on our own checkpoints; it only reaches formats ours never
produce.

## The threshold has two published values, from two harnesses

The pre-registered bar, BFCLv3 ≥ 52.43, is Granite 4.0-1B's score **as measured by Liquid**,
whose card states the method: "the final weighted average score with a custom Liquid handler to
support our tool use template". IBM's own card for the same checkpoint reports **54.82** on
BFCL v3 for `granite-4.0-1b` (and 50.21 for the hybrid `granite-4.0-h-1b`, a different model
that is easy to mistake for it).

Two vendors, one checkpoint, 2.4 points apart. Neither figure is what this harness computes:
ours is an unweighted mean over 11 named AST and restraint categories, printed beside its
item-weighted form. So the number that matters for the claim is `B4`'s, run through the same
task, the same prompts, the same card and the same parser as `B1`. The published pair is
recorded here as the reason a matched rerun was specified in the first place, and `overview.md`
keeps 52.43 as the pre-registered figure because changing a pre-registered threshold after
seeing a second source is how a bar becomes whatever the result needs it to be.

`B4` is `ibm-granite/granite-4.0-1b`, the dense 1B, matching Liquid's table.
