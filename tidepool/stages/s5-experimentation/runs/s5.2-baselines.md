# s5.2 — baselines, and the harness they all run on

Every number this project reports about a model comes out of one job definition,
`jobs/s5-eval` (task `7633fb1c-f530-42b4-9556-10c9f5f729f1`). The baseline row, the eight
sweep arms, the tuning runs and the final checkpoints are all scored by it, which makes it
the most reused artifact in the project and the one whose design decisions are worth
writing down in full. They are below, with the reasoning, because a benchmark number is
only worth as much as the reader's ability to see what was measured.

## What the harness is

One GPU job per model. It generates and scores in the same run, and saves the raw
completions before scoring touches them.

| Component | Items | Scored by | Metric reported |
| --- | --- | --- | --- |
| BFCLv3-AST composite | ~4,400 over 11 categories, x2 surface forms | our checker, verified against ground truth | unweighted category mean, plus item-weighted |
| IFStruct v1.0 | 2,000 | Liquid's own validator, vendored verbatim | first-attempt validity, plus mean partial score |
| IFEval | 541 | Google's own instruction registry, vendored | prompt-level and instruction-level, strict and loose |
| In-house probes | 434 graded + 30 clean control | the checks `s4.4` shipped, plus a flag detector | flag rate, false-flag rate, stack-idiom accuracy, by envelope depth |

The serving path is Hugging Face `transformers`, bf16, greedy, left-padded batches, on one
L4. It is slower than a dedicated inference server and it is the same code path the
training runs load the model through, which is the reason it was chosen: nothing extra to
install, no batching-dependent numerics to argue about later, and the frozen-backend rule
in `plan.md` satisfied by construction. A screening pass is roughly 5 million generated
tokens, about half a GPU-hour per model. **Moving to a faster server later invalidates
every full-precision number taken here and means rerunning all of them**, so the backend,
the card and the decoding settings are recorded in every summary as part of the result.

## Four decisions that shape what the numbers mean

### 1. The baseline is prompted in its own format as well as ours

The `s4` training data presents a tool contract as a JSON array inside `<tools></tools>` in
the system message, and expects `<tool_call>{"name": ..., "arguments": {...}}</tool_call>`
back. That is our convention. It is not how Liquid shipped LFM2.5, whose chat template
takes a `tools=` argument and answers with
`<|tool_call_start|>[f(a=1, b='x')]<|tool_call_end|>` in Python call syntax.

Scoring the stock checkpoint only in our convention would understate it, and every delta
measured against it would be inflated by exactly the amount the format mismatch cost. So
both surface forms are generated for every tool-calling component, the parser accepts
either regardless of which was prompted, and **a baseline's score is the better of the
two**. The cost is one extra generation pass over BFCL per baseline, which is minutes.

### 2. Our BFCLv3 is a named subset, and it says so everywhere

Roughly a fifth of BFCLv3 (`exec_*`, `rest`) scores a model by executing the call it
produced against live third-party APIs with real credentials, and `multi_turn_*` scores
against a stateful environment that is part of the BFCL harness rather than the data.
Neither is reproducible here. Reporting a composite over what remains while calling it
"BFCLv3" would be comparing our number to published ones that mean something else.

So the metric is **BFCLv3-AST composite**: the unweighted mean over 8 abstract-syntax
categories plus the 3 that score restraint (`irrelevance`, `live_irrelevance`,
`live_relevance`). Exclusions and their reasons ship inside every summary JSON. Equal
weight per category is deliberate: the categories differ in size by two orders of
magnitude, and a size-weighted mean would make the composite mostly a report on
`live_simple`. Both are computed and printed together.

The absolute threshold in `overview.md` (**52.43**, Granite 4.0-1B) is a published overall
on the full benchmark, so it is not comparable to this composite. `B4` is a rerun of
Granite through this same harness, and that rerun is what the threshold becomes. Published
vendor numbers keep exactly one job: checking that the harness lands near them on the model
they were published for.

### 3. Benchmark prompts are used verbatim, with no system prompt

IFStruct and IFEval prompts go in as the sole user turn. Our own structured-output
convention from `s4` is deliberately *not* added, even though the model is trained on it: a
system prompt telling the model to answer in JSON would flatter every model on IFStruct and
break comparability with the published figure. The in-house probes are the opposite case,
because they carry their own system prompt in the data, so the harness adds nothing to
them either.

### 4. The guardrail criteria needed two things the probe set did not have

`overview.md` asks for a malformed-tool-return **flag rate of at least 0.70 with a
false-flag rate at most 0.15**. Neither was measurable as the set stood.

- The graded checks pass an item when the completion does *not* contain the value the model
  would have to invent. "Did not fabricate" is not the same event as "said the return was
  wrong": a model that answers "I don't know" scores the first and not the second. A frozen
  family of 26 flag phrasings is now matched against the completion and reported alongside
  the original check, which is unchanged.
- Every one of the 434 graded items is defective, so there was nothing to false-alarm on.
  A **clean control arm** is built from the same bank and the same envelope wrapper with
  the payload left intact: 10 scenarios x 3 envelope depths = 30 items where the right
  behaviour is to answer the question and say nothing about the return. It is generated
  deterministically, saved as an artifact on every run, and its content hash
  (`561a23f3c6532c4f`) is recorded so a drift in the control set cannot be mistaken for a
  drift in a model.

A regex family over English is a coarse detector. It is defensible because it is fixed once
and applied to every model identically, so a difference between two checkpoints is a
difference in behaviour rather than in grading.

## What was verified locally before any GPU time was spent

Authoring checks, on fixtures, in the sandbox. None of these is a result.

- **The BFCL checker against ground truth.** An oracle that builds its calls from the
  answer key scores exactly **1.0000 on all 858 items** of `simple`, `parallel` and
  `live_simple`. The same oracle with the function name perturbed scores 0.000; with one
  extra parameter, 0.000; emitting no call, 0.000. `irrelevance` scores 1.00 for silence
  and 0.00 for any call, `live_relevance` the reverse. A checker that cannot score a
  perfect model as perfect will quietly floor every model it grades, and this one now
  cannot.
- **One data quirk found and handled.** 7 of 3,351 ground-truth parameters carry an empty
  list of acceptable values, which is BFCL's way of saying the parameter must be left
  empty. Read naively that marks a correct call wrong.
- **The tool-call parser** round-trips both surface forms, a fenced JSON call, and a bare
  Python call list, and returns nothing for prose.
- **IFStruct's validator** loads all 2,000 rows (1,000 JSON, 1,000 YAML) and rejects an
  empty and a garbage response with the benchmark's own error strings.
- **IFEval's registry** resolves all 541 prompts' instruction ids with none unknown, and
  grades a lowercase-only prompt correctly in both directions.
- **A determinism bug in IFEval, found and fixed.** A dozen of the 25 instruction classes
  fall back to `random.choice` when a row leaves a keyword argument out, so an unseeded run
  grades the strict and loose passes against two *different* instructions. The first local
  run scored loose *below* strict, which is impossible by construction. The generator is
  now seeded per item and instruction from a stable checksum: loose is at or above strict,
  and two runs over the same completions return identical flags.
- **The probe scorers** on real items of all three check kinds, plus the clean arm, in both
  the pass and fail direction.

way, and the artifact writer falls back to a repr rather than raising, so a serialization
quirk can never again destroy a pass whose generations are paid for. Charged 0.17 GPU-hours.

## Capped passes sample by stride, and here is what that is actually worth

A capped run used to take the **first** N items of each file. Striding instead is obviously
safer, so I wrote it up as a defect found and fixed before checking how much of one it was. It
is a defect on one of the three benchmarks and cosmetic on the other two.

| Benchmark | Head slice | Strided | Full set |
| --- | --- | --- | --- |
| tool calling, `live_simple`, 40 of 258 | 2.35 args/call | 3.08 | **2.76** |
| tool calling, `simple`, 40 of 400 | 2.65 | 2.95 | **2.90** |
| tool calling, `irrelevance`, 40 of 240 | 2.75 | 2.88 | **2.84** |
| structured output, 400 of 2,000 | 192 JSON / 208 YAML | 190 / 210 | **1,000 / 1,000** |
| instruction following, 200 of 541 | all 9 families | all 9 families | **9 families** |

On the tool-calling files a head slice is biased toward fewer-argument calls in all three
categories checked, which is the easy end of each category, so striding is a real correction
there. The structured-output rows are interleaved by format, not blocked by it, so a head slice
was already balanced: an earlier version of this note claimed a 400-item head slice would have
scored JSON only, and that was wrong. The instruction-following file covers every family either
way.

Both samplers are deterministic, so a capped comparison between two models is exactly paired
regardless. Striding is kept because it tracks the full distribution more closely where it
differs at all and costs nothing where it does not.

## Two profiles, and the caps are parameters

Full item counts for the baseline row and the final checkpoints. A **screening profile** for
ranking the eight sweep arms: 120 items per tool-calling category in the training convention
only, 400 structured-output rows, 200 instruction-following prompts, and the **whole** probe
set, because the guardrail criteria are pass or fail over all of it. Every cap is an explicit
per-component parameter recorded in the summary, so no run can quietly be screened while
reading as full.

Arms are not scored in the native surface form. After supervised fine-tuning on our convention
that is the model's own format, and a native-form regression check is worth 40 minutes on the
finalists and not on eight arms. The baselines are scored both ways, so the thing the arms are
compared against is the best the stock checkpoint can do.

### The structured-output number, checked rather than reported

0.125 first-attempt validity would be an extraordinary claim about a checkpoint whose vendor
ships this benchmark. Three things were checked before letting the number stand:

1. **Our call matches the benchmark's own harness.** Its `run_one` passes the raw completion
   text to `validate_response` with seven keyword arguments, per-example. Ours passes the same
   seven, read from the same row fields, with no system prompt added. Verbatim.
2. **The validator already handles fenced code blocks**, and one example is a per-item
   requirement (`require_code_block`), so a fenced answer is not being failed for its fence.
3. **The completions were read.** The failing answers are genuinely malformed against the
   schema: on one item the model emitted `chapters:` as a single mapping with `chapter_title`
   repeated twice inside it where the schema wants a list, and duplicated every metadata key
   at two nesting levels at once.

So the harness is faithful and 40 items is the problem: this is a 40-row strided sample of a
2,000-row benchmark whose rows vary enormously in schema complexity. The full pass settles it,
and if the full number is still far under what the vendor publishes, the harness gets
investigated again before any delta is built on it.

### Two artifact bugs, both silent, both fixed

- **Name collision.** The store keys artifacts on the basename, so `completions/ifstruct.jsonl`
  and `scored/ifstruct.jsonl` registered as one artifact and the raw text was replaced by the
  scored file. The whole point of writing completions first is that a scoring bug costs a CPU
  rerun rather than a GPU pass, and a collision quietly removes that. Names are flat now and a
  reused name is recorded as a note.
- **The summary did not come back.** `eval_summary.json` logged as saved and is not retrievable.
  Without it the template mode, the assertions, the effective caps and the input hashes exist
  only in a log. The cause recorded here at the time was that the store registered every `.jsonl`
  this run wrote and dropped the `.json`; that was wrong, and the correction is below under
  "The artifact bug, diagnosed properly this time". The `.jsonl` twin added in response is kept
  anyway, because one summary per line concatenates cleanly across runs.

Both were found by reading what came back rather than by anything failing, which is the
argument for checking a harness on a smoke instead of on a baseline.

## The parser was blind to every format but our own

`B4` exists to turn a published threshold into a number from this harness. Before paying for
that pass, the tool-call parser was tested against the shapes other 1B-class checkpoints
actually emit. It read none of them:

| Completion form | Calls found, before | After |
| --- | --- | --- |
| a JSON *array* inside `<tool_call>` | 0 | 1 |
| a bare JSON array, no marker | 0 | 1 |
| `<\|tool_call\|>` pipe marker then JSON | 0 | 1 |
| two calls in one array | 0 | 2 |
| arguments under a `parameters` key | 1, with `args: {}` | 1, arguments intact |

The fifth row is the one that would have done real damage. It returned a call with the right
name and an empty argument dict, so the grader saw a well-formed call that got every argument
wrong, and nothing in the run would have looked broken. Scoring a competitor with that parser
would have floored it and handed us a threshold we invented.

The parser is now generous about form and strict about nothing: it recognises the marked
envelope in three vendors' spellings, unwraps arrays, accepts `arguments`, `args` or
`parameters`, and falls back to a fenced or bare blob only when no marked call is present. The
grader still decides whether a call is *right*; the parser's only job is to not lose one. 14
fixtures, 0 failures.

Leniency in a parser is a way to invent calls where a model made none, which would inflate the
three restraint categories, so the change was re-run over the 756 real completions attempt 1
had already saved. **Zero** of them are read through a path that needs no marker. The added
leniency cannot manufacture a call on our own checkpoints; it only reaches formats ours never
produce.

## The threshold has two published values, from two harnesses

The pre-registered bar, BFCLv3 ≥ 52.43, is Granite 4.0-1B's score **as measured by Liquid**,
whose card states the method: "the final weighted average score with a custom Liquid handler to
support our tool use template". IBM's own card for the same checkpoint reports **54.82** on
BFCL v3 for `granite-4.0-1b` (and 50.21 for the hybrid `granite-4.0-h-1b`, a different model
that is easy to mistake for it).

Two vendors, one checkpoint, 2.4 points apart. Neither figure is what this harness computes:
ours is an unweighted mean over 11 named AST and restraint categories, printed beside its
item-weighted form. So the number that matters for the claim is `B4`'s, run through the same
task, the same prompts, the same card and the same parser as `B1`. The published pair is
recorded here as the reason a matched rerun was specified in the first place, and `overview.md`
keeps 52.43 as the pre-registered figure because changing a pre-registered threshold after
seeing a second source is how a bar becomes whatever the result needs it to be.

`B4` is `ibm-granite/granite-4.0-1b`, the dense 1B, matching Liquid's table.

## The 4-bit half of the harness

Three of the six baseline rows are published GGUF files, and the project's headline promise is
that a 4-bit build holds the full-precision bar. Until now only one side of that comparison had
a harness. The gap is closed by adding a second serving path to the same task rather than a
second task: `backend=gguf` swaps the generator and nothing else, so item selection, prompt
rendering, parsing and scoring are the same code on both sides of every quantization claim.

**No prebuilt Linux CUDA binary exists.** llama.cpp's own releases ship CUDA builds for Windows
and CPU-only builds for Linux, so the backend is compiled once by its own job
(`s5-llama-build`), pinned to tag `b10622`, targeted at `sm_89` (both project cards, L4 and
L40S, are that architecture), and kept as a stored artifact every later 4-bit run downloads. A
backend rebuilt per run is a backend that can change under a comparison with nothing in the
record showing it moved.

The build job does four things beyond compiling:

- **Probes for a CUDA compiler and says what it found.** The eval image carries the CUDA runtime
  because torch needs it; whether it carries `nvcc` is unknown until asked. If it does not, the
  compiler is installed from a wheel and the fact is recorded. A silent fall back to a CPU build
  would still finish, and would make one 4-bit pass cost a day.
- **Serves the real file.** It pulls `LFM2.5-1.2B-Instruct-QAD-Q4_0.gguf`, which is baseline row
  `B2`, offloads it to the card, and generates from it. A successful compile is not evidence
  that llama.cpp can run this architecture.
- **Checks that the server reproduces itself.** Two identical requests at temperature 0 must
  return identical text, or every 4-bit delta this project reports carries sampling noise.
- **Prices a full 4-bit pass** from its own measured tokens per second, single-stream and across
  eight concurrent slots, instead of from an assumption.

It also keeps `llama-quantize` and `convert_hf_to_gguf.py` from the same tag. Our own finetuned
checkpoint has to become a GGUF at some point, and the converter that makes it must be the same
version as the runtime that serves it.

### Prompt bytes are identical across the two backends

The Q4 path renders prompts with the Hugging Face tokenizer of the full-precision repo the GGUF
was quantized from, then has the server tokenize with `add_special` off. Both halves matter. The
chat template writes the beginning-of-sequence token as text, so letting the server prepend its
own would put two in front of every prompt, and a comparison of two checkpoints on different
prompts is not a comparison of the checkpoints.

### Two backends is a confound, and here is the honest version of it

GGUF only runs in llama.cpp, so a Q4 row and an FP row cannot share a backend. What that buys is
a delta between two *deployed artifacts*, weights and runtime together, which is what the
success criteria are actually about: the operator ships a 4-bit build on an 8 GB card, not a
dequantized tensor. What it costs is that quantization and runtime are not separable from that
number alone.

Both are recoverable, and cheaply, because the vendor publishes an F16 GGUF beside the Q4 ones:

| Comparison | What it isolates |
| --- | --- |
| Q4 in llama.cpp vs **F16 in llama.cpp** | quantization alone, same runtime |
| F16 in llama.cpp vs FP in `transformers` | the runtime alone, same weights |
| Q4 in llama.cpp vs FP in `transformers` | what actually ships |

The third row is the success criterion; the first two are what make it interpretable. All three
are one parameter change on the same task, and which comparison a number belongs to is written
into its summary.

### The three published files, named

Each of these repos publishes a dozen quantizations, and the task refuses to guess: `gguf_file`
has no default and a run without one fails rather than picking by pattern.

| Row | Repo | File |

| `B2` | `LiquidAI/LFM2.5-1.2B-Instruct-GGUF` | `LFM2.5-1.2B-Instruct-QAD-Q4_0.gguf` |

a matched 4-bit form; the mismatch is recorded rather than smoothed over.

### What the Granite smoke found, and why it changes the threshold

| Surface form | Composite | Item-weighted |
| --- | --- | --- |
| `tools_text`, our training convention | 0.1841 | 0.2143 |
| `native_tools`, Granite's own template | **0.7795** | 0.7831 |

A factor of four between two renderings of the same 378 items on the same checkpoint. The
`tools_text` failure is uniform and specific: **299 of 378 completions are the single string
`<tool_call>`**, the opening marker and nothing after it.

Everything that could be a harness fault was checked before the reading was believed:

- The prompt Granite received is well formed for Granite. Its own role markers, its own
  end-of-text token between turns, the tool schemas inside `<tools></tools>` exactly as its card
  documents, and the generation prompt at the end.
- The failure does not track batching. Prompts are bucketed by length before generation, the
  spread inside a batch is 33 to 215 characters, and the stubs are spread across all 24 batches
  (7 to 16 per batch) rather than clustering where padding would be worst.
- The parser is not losing them. `<tool_call>` is added token 100270 in Granite's vocabulary and
  is *not* marked special, so it survives decoding, which is why it is visible at all. There is
  no JSON after it to lose.
- The model is not broken in this run. The restraint categories produced fluent, correct refusals
  ("the available tools do not include a function to calculate the area of a triangle"), and four
  items produced complete, well-formed calls.

So the reading is real: asked in prose to emit a format it was not post-trained on, Granite opens
the block and stops. That is a fact about the checkpoint, not about the harness.

**This is the decision from "Four decisions that shape what the numbers mean" earning its keep.**
Every baseline is prompted in its own format as well as ours and scored on the better of the two.
Without the native pass we would have published the tier's incumbent at 0.18, and any finetune of
ours would have "beaten" it by a margin that was entirely an artifact of prompting. The same rule
protects our own checkpoints in the other direction, since they will be strongest in the
convention they are trained on.

**And it changes what the pre-registered threshold means.** `overview.md` fixes the bar at BFCLv3
≥ 52.43. Granite scores 0.7795 here. Neither number is wrong: ours is an unweighted mean over 11
named AST and restraint categories at 40 strided items each, and the published figure is a
weighted average over a wider benchmark including categories this harness does not run. They are
not on the same scale and never were, which is why the plan specified a matched rerun instead of
a quoted number. The operative threshold is `B4`'s composite from this harness at full item
counts, and the pre-registered 52.43 stays in `overview.md` as the published figure that motivated
it.

**Cost note.** Granite generates at 42 to 67 tokens per second against the LFM checkpoint's 280,
at the same batch size on the same card. Part of that is 1.63B parameters against 1.2B and part is
prefill dominating when a completion is one token long. Its full pass is therefore priced from
this smoke rather than from `B1`'s throughput, and both surface forms are still run: the
`tools_text` pass is nearly free precisely because the model stops after one token.

## The artifact bug, diagnosed properly this time

The Granite smoke logged eleven `saved artifact` lines and `lab job artifacts` listed six. The
six present were `probes_control.jsonl`, `completions_probes.jsonl`, `completions_ifstruct.jsonl`,
`completions_ifeval.jsonl`, `completions_bfcl_tools_text.jsonl` and
`completions_bfcl_native_tools.jsonl`. The five absent were every `scored_*.jsonl` and both forms
of `eval_summary`. `job download --file scored_bfcl_tools_text.jsonl` answered "No artifacts
matched" for a file the log gave a byte count for.

Lining the two lists up against the code settled it in one pass. The six that came back are
exactly the six `save()` calls with no `kind` argument. The five that did not are exactly the five
that passed `kind="evals"` through to `lab.save_artifact(path, type="evals")`.

So the extension had nothing to do with it. The `type` argument files a copy under eval-results
metadata rather than in the generic artifact store, and the CLI exposes no route to that
metadata: not `job artifacts`, not `job download`, not any subcommand of `job`. The one line of
documentation for the argument says as much, read the right way round: "so they appear in eval
results metadata, **not as generic artifacts**". It behaves as designed and the design is wrong
for us, because the per-item scored detail is the thing s6's error analysis reads.

Every `save()` in the eval task now saves untyped. `kind` survives as a label on the log line,
and the numbers a metrics pane wants arrive through `finish(score=...)`, which does show up. The
GGUF server log, saved the same way, was typed too and is now untyped.

**What it costs.** `4350ce4e` launched before the fix, so the reference row's scored per-item
files and its summary will not be retrievable when it lands. Its raw completions will be, and
scoring is deterministic CPU work over exactly those files, so the detail is recoverable by
re-scoring rather than by regenerating. That path is worth building for its own sake: it lets any
finished run be re-scored when the parser improves, without paying for generation twice.

Three silent artifact faults now, all three found by reading what came back rather than by
anything failing. The rule that earned its place: **a job's outputs are unproduced until they have
been listed by `job artifacts`, and a log line saying "saved" is not a listing.**

## `B1` at full item counts — the reference row's tool calling

### The re-score is a mode of the eval task, not a task of its own

The obvious build was a second task with the graders copied into it. That is the wrong shape, and
for a reason this project has already been bitten by twice: two copies of a scorer is how one set
of completions ends up with two different scores, and the whole discipline of `s5.2` is that the
harness must not move underneath the numbers. So the replay is a **parameter of `s5-eval`**.

`rescore_object` names a storage directory holding a finished run's `completions_*.jsonl`. Set it
and the run loads no weights, touches no GPU, generates no tokens, and every component reads its
text from that directory by **item id** instead of from a model. Everything downstream of
generation is the identical code path that produced the original numbers.

Four things make it safe rather than merely convenient.

- **It joins on id, never on position.** A positional join would silently mis-pair if the item
  order ever changed; the four component functions now pass their item ids alongside their prompts
  and the runner raises if it is given none.
- **It re-renders every prompt and checks the recorded hash.** Each completions row carries a
  `prompt_sha`. The replay rebuilds the prompt from the live chat template and compares. If the
  published template has moved since the run, the saved completions no longer answer the prompts
  this harness builds, and that shows up as a counted mismatch rather than as a quietly
  incomparable number. Checking the hash is why the tokenizer is still loaded.
- **It rebuilds the clean probe arm and diffs it against the source.** The arm is generated
  deterministically rather than read back, so a drift in the generator would put the false-flag
  rate of the source run and of this one on different items. The rebuilt arm is now compared
  item-by-item against the source run's saved `probes_control.jsonl` and the comparison is an
  assertion.
- **It refuses to invent throughput.** A replay generated nothing, so it reports how many saved
  completions it scored, not a tokens-per-second figure. `rescored: true` and the source object go
  into the summary, so no re-scored number can later be mistaken for a fresh pass.

The two real runners gained an `ids=` argument they ignore, so one `generate()` call serves all
three modes. One incidental defect fixed on the way: `gen.Runner.generate` bound its local
`ids` from `model.generate(...)`, which after the signature change would have shadowed the new
parameter. Renamed, with the reason written next to it.

Verified in the sandbox against a five-row slice of B1's own structured-output completions, none of
it a result: the id join returns the recorded text, an unknown id counts as missing and yields an
empty completion rather than a substituted one, a component whose file is absent raises instead of
scoring nothing, a call with no ids raises, and the control-arm diff reports identical, changed and
added items correctly. Every prompt hash mismatched in the fixture, as it must when the prompts are
the string `"x"`, which is the check working.

`B1`'s six completions files were pulled from the job and placed in shared storage at
`tidepool/s5.2/B1-fp-instruct/`, full counts intact: 3,490 and 3,490 tool-calling rows in the two
surface forms, 2,000 structured-output, 541 instruction-following, 464 probes and the 30-item
control arm. 29 MB in total.

**Why it is not queued yet.** `s5-eval` requests `L4:1` at the `resources` level and resources are
not overridable per queue, so the replay would take one of the two concurrent GPU slots, both of
which are now full. The alternatives were both worse than waiting. A second CPU-only task means
duplicated graders, the thing this design exists to avoid. Editing the task's resources to run
CPU-only and editing them back is a mutable-configuration dance whose failure mode is the eval task
left CPU-only and the next GPU row landing on a CPU box, which is exactly the class of silent
misconfiguration this stage keeps finding. So the replay runs on the L4 when a slot frees, at a
cost of roughly 0.2 GPU-h for twenty minutes of an idle accelerator. One harness, no duplicated
scorers, no mutable resources; the price is an idle GPU, and against 145 approved GPU-hours it is
not worth a second copy of the graders.

published". It is: `LiquidAI/LFM2.5-1.2B-Base`, `Lfm2ForCausalLM`, 16 layers, one safetensors
shard. So the starting-checkpoint ablation is available and will run at the screening profile once
a slot frees.

One thing to record before it does, because it is a limit on what B6 can mean. **The base and
instruct checkpoints do not ship the same chat template.** Base carries a 1,296-byte template,
Instruct a 5,487-byte one; both use the same `<|im_start|>` role framing and the same
`<|tool_list_start|>` tool rendering, so the harness renders and parses either without changes, and
`native_tools` is available on both. But a B1-versus-B6 delta is then a delta across two
checkpoints *and* two templates, and the two cannot be separated by running B6 alone. Forcing the
instruct template onto the base weights would isolate the checkpoint at the cost of prompting a
model in a format it never saw, which is the same mistake the two-surface-form rule exists to
prevent. B6 is scored under its own template, and the delta is reported as what it is: what
post-training bought, template included. Nothing in the project depends on B6, so the ambiguity is
recorded rather than paid to remove.

## The 4-bit build compiled, and then threw away the compile

Attempt 4 (`b7de2af2`, aws, L4:1, sm_89 at tag `b10622`) got further than any attempt before
it and failed at 45%. What it did, from its own task log:

Then, from the machine log:

```

  raise RuntimeError("the server started without initializing a CUDA device, so it is serving "
RuntimeError: the server started without initializing a CUDA device, so it is serving on the CPU.
Every 4-bit number taken through it would be correct and priced wrong.
```

That gate was mine, and it fired on evidence it should not have trusted. Two things say so.
A CPU-only llama.cpp build takes a few minutes and produces much smaller binaries; 1,038 s and
four binaries at 70-82 MB are what a CUDA build looks like. And the startup text the gate
searched was missing far more than its CUDA lines: it had no `llama_model_loader:`, no
`print_info:` and no `load_tensors:` lines at all, on a server that had just loaded a model and
answered `/health`. A log missing the loader's own output is a log read before the writer
flushed it. Grepping the machine logs for driver or backend messages returned nothing but the
traceback, so there is no positive evidence either way about the device: the gate proved
nothing, and cost the compile.

The second failure is the one worth more. The tarball was packed, saved as an artifact and
pushed to shared storage at step 7, after verification, so a verification failure discarded
seventeen minutes of successful compiling. Every earlier attempt died before the compile, which
is why the ordering had never been tested.

### Attempt 5

`905755d3`, same aws L4 source, same pinned tag and card. Three changes.

**The compile is preserved before it is judged.** Packing, the artifact save and the shared
storage upload move to a new step immediately after the binaries are collected. `FACTS` carries
`verified: false` from that point and only becomes true once every check has passed, so a
tarball in storage is not a licence to serve from it: nothing may use the backend until a run
reports `verified: true`.

**The device is proved by asking, not by reading.** `llama-cli --list-devices` returns on its
own and cannot be read early. Beside it the run records `nvidia-smi`, the CUDA libraries
`llama-server` actually links, and the CUDA entries in the CMake cache. Three signals, because
any one can be silent for a reason unrelated to the device: a runtime older than the flag
prints usage text, a static build links no CUDA library, and a cache can be absent on a
rebuild. The run fails hard only when the enumeration genuinely answered and no CUDA device was
in it (detected by the `available devices` header, so usage text does not read as a card-less
machine), or when none of the three signals is positive.

**The startup log becomes evidence rather than a gate.** It is given five seconds to flush,
saved as an artifact *before* anything is asserted on it, and reported either way; a log with no
CUDA line now writes a note instead of raising.

**A throughput floor is what actually protects the pricing.** After the batched measurement, the
run asserts `min_tok_s` (default 150) generated tokens per second across eight slots. A 1.2B
Q4_0 model on an L4 sits in the high hundreds; on a couple of CPU threads it sits in the tens.
The floor catches a CPU fallback whatever the logs say, and it also catches the case the log
gate never could: a build that reaches the device but is slow enough to make the quoted hours
for a full 4-bit pass meaningless.

The floor is deliberately far below the expected figure. It is a fallback detector, and a
performance number that has to be met would invite tuning the threshold instead of reading it.

### Why this is not a no-progress relaunch

The substage's relaunch allowance counts attempts that change nothing. Attempts 2 and 3 were
byte-identical to each other and attempt 4 changed only the compute source, so the allowance was
already thin. Attempt 5 changes what the job keeps and what it trusts, and it is aimed at the
specific signature attempt 4 produced. Recorded at 0.75 h against attempt 4's reconstructed
0.40 h; project spend is now 3.417 of 145 GPU-hours, of which 0.68 h has bought nothing.

Attempt 4 has no published end timestamp, so its 0.40 h is reconstructed from the 1,038 s
compile plus the setup, configure, download and server start around it. It is an estimate and
the ledger says so.

## The three 4-bit rows are resolved down to filenames, and one of them is not what it looks like

While the build compiles there is CPU-only work worth doing: pinning exactly which file each
4-bit row loads, and which repository renders its prompts. All three repositories publish a
dozen quantizations, and picking one by pattern at run time is a choice the harness deliberately
refuses to make for itself.

| Row | GGUF repo | File | Renders prompts with |
| --- | --------- | ---- | -------------------- |
| B2 | `LiquidAI/LFM2.5-1.2B-Instruct-GGUF` | `LFM2.5-1.2B-Instruct-QAD-Q4_0.gguf` | `LiquidAI/LFM2.5-1.2B-Instruct` |
| B3 | `unsloth/LFM2.5-1.2B-Instruct-GGUF` | `LFM2.5-1.2B-Instruct-UD-Q4_K_XL.gguf` | `LiquidAI/LFM2.5-1.2B-Instruct` |
| B5 | `NovachronoAI/LFM2.5-1.2B-Nova-Function-Calling-GGUF` | `LFM2.5-1.2B-Nova-Function-Calling.Q4_K_M.gguf` | `NovachronoAI/LFM2.5-1.2B-Nova-Function-Calling` |
| runtime ref | `LiquidAI/LFM2.5-1.2B-Instruct-GGUF` | `LFM2.5-1.2B-Instruct-BF16.gguf` | `LiquidAI/LFM2.5-1.2B-Instruct` |

Two of those cells were decisions rather than lookups.

**B5 has no Q4_0.** The Nova repository publishes `Q2_K` through `Q8_0` in the K-quant family
only, so the 4-bit row is `Q4_K_M`. B3 is a K-quant too, which makes the B2-against-B3 comparison
the one the plan wanted (a vendor's quantization-aware Q4_0 against the best cheap community
quant) and leaves B5 as a third point rather than a matched pair.

**The runtime reference is BF16 rather than F16.** Its only job is to separate what quantization
costs from what changing the serving runtime costs, and B1 was served bf16. Taking the reference
at bf16 holds the dtype fixed so the runtime is the only thing that moved. If llama.cpp refuses
the type on this card the fallback is `F16.gguf`, which costs a few minutes at model load and
adds a dtype change to the comparison; the fallback would be recorded in the row's summary.

### B5 is a different model, prompted a third way

The Nova checkpoint publishes a full-precision twin and its own chat template, and the template
is 1,783 bytes against Liquid's 5,487. Reading it: tools are rendered as a plain
`List of tools: [{...}, {...}]` line folded into the system prompt, with none of the
`<|tool_list_start|>` framing LFM2.5 ships with and no declared convention for the call itself.
So B5's tool-calling number mixes three differences from B1 at once: a different fine-tune,
a third tool surface form, and 4-bit quantization. It cannot be read as "does a competitor's
4-bit beat ours at calling tools".

The harness's existing policy already handles the prompting half of that: every baseline is
scored under its own native rendering and under our `s4` text convention, and the better of the
two is the row's number. What the policy cannot do is separate the fine-tune from the
quantization. The clean way to do that is a full-precision Nova row, which the plan does not
call for and nothing downstream needs; at about 1.4 GPU-hours against a project spend of 3.4 of
145 it is affordable, so it is recorded here as an option for `s6`'s error analysis rather than
queued now. B5 stays what the plan made it: a published competitor's 4-bit build, scored on the
same items through the same runtime, and reported with the caveat attached.

### Ready to run, once the serving path is verified

Each row is one queue against the eval task, with the tarball named by the object the build
stores. None may run until a build reports `verified: true`.

```
# B2 — the vendor's quantization-aware 4-bit build
lab task queue 7633fb1c-f530-42b4-9556-10c9f5f729f1 -e tidepool --no-interactive \
  -p backend=gguf -p run_tag=B2-q4-vendor-qad \
  -p llama_object=tidepool/llama-b10622-sm89.tar.gz \
  -p gguf_repo=LiquidAI/LFM2.5-1.2B-Instruct-GGUF \
  -p gguf_file=LFM2.5-1.2B-Instruct-QAD-Q4_0.gguf \
  -p tokenizer_repo=LiquidAI/LFM2.5-1.2B-Instruct -p profile=full

# B3 — the best cheap community quant
  -p run_tag=B3-q4-unsloth-udq4kxl -p gguf_repo=unsloth/LFM2.5-1.2B-Instruct-GGUF \
  -p gguf_file=LFM2.5-1.2B-Instruct-UD-Q4_K_XL.gguf

# B5 — a competitor's function-calling fine-tune, its own template
  -p run_tag=B5-q4-nova-fc -p gguf_repo=NovachronoAI/LFM2.5-1.2B-Nova-Function-Calling-GGUF \
  -p gguf_file=LFM2.5-1.2B-Nova-Function-Calling.Q4_K_M.gguf \
  -p tokenizer_repo=NovachronoAI/LFM2.5-1.2B-Nova-Function-Calling

# runtime reference — same weights, same runtime, no quantization
  -p run_tag=B1r-bf16-llamacpp -p gguf_repo=LiquidAI/LFM2.5-1.2B-Instruct-GGUF \
  -p gguf_file=LFM2.5-1.2B-Instruct-BF16.gguf
```

GPU concurrency is 2, so these go two at a time behind whichever of the build and B4 finishes
first.
