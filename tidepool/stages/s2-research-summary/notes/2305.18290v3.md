# 2305.18290v3 — Direct Preference Optimization: Your Language Model is Secretly a Reward Model

**Relevance:** high
DPO is the named candidate at the third rung of the project's candidate ladder ("DPO on preference pairs including generated malformed-tool-return pairs"), and this is the source paper defining the loss, the reference-model setup, and the hyperparameters to start from.

## TL;DR

DPO replaces the standard RLHF pipeline (fit a reward model, then run PPO against it) with a single closed-form reparameterization: the optimal KL-constrained policy implies a reward function expressible directly in terms of the policy's own log-probabilities, so preference pairs can be fit with one binary cross-entropy loss and no sampling, reward model, or RL loop. Tested only up to 6B parameters (GPT-2-large, GPT-J-6B, Pythia-2.8B) on sentiment control, summarization, and single-turn dialogue — not on structured output or tool use.

## Techniques to try

- The DPO loss itself, directly applicable to a preference-pairs stage: "$\mathcal{L}_{\text{DPO}}(\pi_{\theta};\pi_{\text{ref}})=-\mathbb{E}_{(x,y_{w},y_{l})\sim\mathcal{D}}\left[\log\sigma\left(\beta\log\frac{\pi_{\theta}(y_{w}\mid x)}{\pi_{\text{ref}}(y_{w}\mid x)}-\beta\log\frac{\pi_{\theta}(y_{l}\mid x)}{\pi_{\text{ref}}(y_{l}\mid x)}\right)\right]$" — Section 4, Eq. 7.
- Starting hyperparameters given as a default recipe: "we use a $\beta=0.1$, batch size of 64 and the RMSprop optimizer with a learning rate of 1e-6 by default. We linearly warmup the learning rate from 0 to 1e-6 over 150 steps." — Appendix B. Note the optimizer is RMSprop, not AdamW, and β was raised to 0.5 for the summarization task, so β needs task-specific tuning rather than reuse as-is.
- Reference-model initialization rule directly reusable for a tool-call preference stage: "we initialize $\pi_{\text{ref}}=\pi^{\text{SFT}}$ whenever available. ... when $\pi^{\text{SFT}}$ is not available, we initialize $\pi_{\text{ref}}$ by maximizing likelihood of preferred completions" — Section 4 ("DPO outline"). This maps onto the project's SFT-then-DPO ladder: use the LoRA/full-SFT checkpoint as $\pi_{\text{ref}}$.
- DPO was "much more robust to the sampling temperature than PPO, the performance of which can degrade to that of the base GPT-J model at high temperatures" (Section 6.2) — relevant if the shipped model is sampled at nonzero temperature in the agent gateway.

## Baselines & datasets used

- Controlled sentiment: GPT-2-large SFT'd on IMDB, preference pairs labeled by a sentiment classifier (siebert/sentiment-roberta-large-english) rather than humans — a synthetic/verifiable-reward setup structurally similar to what a schema-validity-labeled preference set would look like.
- Reddit TL;DR summarization: GPT-J-6B SFT model, human preference labels from Stiennon et al.
- Anthropic Helpful-Harmless single-turn dialogue: Pythia-2.8B, 170k human-labeled dialogue pairs.
- All experiments are at ≤6B parameters, so scale is directly comparable to the project's 1.2B target; none involve JSON/tool-call structured output.

## Pitfalls / negative results

- A naive unweighted preference objective (no importance weighting term) "can cause the language model to degenerate" — the paper's Unlikelihood baseline (maximize $\log p(y_w|x)$, minimize $\log p(y_l|x)$ with no weighting) was dropped from summarization/dialogue experiments entirely because "it produces generally meaningless responses": sampled outputs degenerate into token repetition loops like "when when when when when ... whenUB" (Appendix Table 3, C.3). This is a direct warning that a naive DPO-like loss without the sigmoid weighting term is unsafe to use for a malformed-tool-return preference stage.
- Reward over-optimization may already show up inside DPO itself: the paper flags "the slight decrease in performance in Figure 3-right" over the course of training as a possible instance of over-optimization, left as an open question rather than resolved — worth watching for in a GRPO-with-verifiable-rewards stage where reward hacking is an explicit project concern.
- GPT-4-as-judge is not perfectly faithful even when validated: in one dialogue example GPT-4 judged DPO's answer better despite it containing a fabricated "coalition of the willing"/"all-inclusive association" account of WWII causes, and in an arithmetic example GPT-4 judged correctly only because the ground truth was correct, not because it caught DPO's wrong arithmetic (Appendix D.2, Tables 9-10) — a caution against relying on an LLM judge to certify correctness/schema validity rather than fluency.

## Metric / eval choices

- Reward-vs-KL frontier is used as the primary controlled-setting metric ("we must take into account both reward achieved as well as the KL discrepancy; achieving slightly higher reward but with much higher KL is not necessarily desirable" — Section 6.1); DPO's own implicit reward is $\hat{r}_\theta(x,y)=\beta\log\frac{\pi_\theta(y|x)}{\pi_{\text{ref}}(y|x)}$, i.e. a per-example scalar directly computable from log-probs without a separate reward head — a template for a self-contained "how far did we push the policy" diagnostic during the project's DPO stage.
- GPT-4 win-rate judgments were validated against a 25-rater human study and found to "agree with humans about as often as humans agree with each other" (Section 6.4, Table 2), but only for open-ended summarization/dialogue quality — no analogous validation exists here for judging structured/schema-correctness, which the project cannot borrow directly.

## Open questions for our project

- All results are at ≤6B parameters on free-text tasks (sentiment, summarization, dialogue); nothing here demonstrates DPO behavior on schema validity, tool-call correctness, or "flag vs assert" behavior, so the preference-pair construction method for malformed tool returns (the project's specific need) has to be designed from scratch rather than adapted from this paper.
- The paper's preference labels come either from a ground-truth classifier (IMDB) or human raters (TL;DR, HH-RLHF); it gives no guidance on constructing preference pairs from a verifiable but non-model check like JSON Schema validity, which is exactly the project's proposed use case and remains untested here.
- No instruction embedded in the paper text was directed at the reader/agent; it is a standard academic paper and nothing needed to be flagged as an injected instruction.
