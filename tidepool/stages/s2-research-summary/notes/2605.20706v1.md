# 2605.20706v1 — Llamas on the Web: Memory-Efficient, Performance-Portable, and Multi-Precision LLM Inference with WebGPU

**Relevance:** low
The paper is a systems/infra contribution for browser-based WebGPU inference in llama.cpp — it touches GGUF quantization formats and llama.cpp internals that overlap this project's shipping format, but every measurement is browser/WebGPU-specific and none addresses output quality, structured-output behavior, or native single-GPU throughput, so nothing here settles a decision for this project.

## TL;DR

LlamaWeb is a new WebGPU backend for llama.cpp that cuts browser memory usage 29–33% and boosts decode throughput 45–69% versus other browser LLM frameworks (WebLLM, Transformers.js), largely through static memory allocation, a tunable kernel library, and templated dequantization kernels supporting llama.cpp's many GGUF quantization formats. It is purely a systems/performance paper — it never touches training, fine-tuning, or task-accuracy evaluation.

## Techniques to try

- None directly applicable to training or structured-output reliability. The only potentially transferable idea is their static/pre-allocated memory arena for KV-cache and kernel parameters ("we statically allocate all memory necessary to run the model at startup ... a fixed-size KV-cache which can be allocated before running inference" — Sec. 3.1), which is a serving/deployment engineering pattern, not a training technique, and would apply only if the eventual deployment path used a browser/WebGPU stack rather than the RTX 2080 Super native GPU target.

## Baselines & datasets used

- Uses llama.cpp's standard GGUF quantization families as its test formats: q4_k_m is explicitly the standardized variant used across all evaluations ("we specifically use q4_k_m model variants for all llama.cpp q4_k evaluation" — Sec. 4), which is the same quantization family this project would likely target for its 4-bit GGUF shipment — useful naming/format context but no accuracy numbers.
- Evaluation models are small/edge models (LFM2.5-350M, Bonsai-1.7B, Gemma3-270M, Qwen3-0.6B, Granite4-1B, Qwen3.5-2B, SmolLM3-3B, Ministral3-3B, Gemma4-E2B, Llama3.2-1B) across 16 devices/8 GPU vendors, but all measurements are throughput/memory, not task quality (BFCL, IFEval, etc. are not evaluated at all).

## Pitfalls / negative results

- Quantization in this system does not scale throughput the way one might expect: "moving from q4_k_m to q2_k weights causes a 17% decrease in throughput" on their mid-tier device cluster (decode, KV-cache depth 0), and prefill with f16 weights actually outperformed q4_k_m on the same cluster (152 vs 79 tok/s) — a caution that lower-bit weight formats do not automatically mean faster inference, since dequantization cost can dominate on memory-bound kernels. This is on WebGPU-in-browser hardware, not the project's native RTX 2080 Super target, so the magnitude likely does not transfer, but the qualitative warning (quantization can be memory-savings-only, not a throughput win) is a relevant framing check against the project's "4-bit decode throughput within 5% of base" requirement.
- Explicit statement that generic weight-only GGUF quantization is not a speed technique in their setting: "llama.cpp quantization in WebGPU is mainly a technique for reducing the memory requirements for running a given model, rather than a performance optimization" (Sec. 7).
- Floating-point precision instability under quantization/casting was observed as a correctness pitfall (not a quality-benchmark result, but a numerics one): "differences in floating-point rounding behavior while casting from f32 to f16 values caused higher NMSE on some devices" and "using f16 accumulation for the register-tiling kernel caused some models, e.g., Qwen2.5, to generate incoherent output on Apple M-series GPUs" (Sec. 3.2) — a reminder that low-precision accumulation choices can silently break generation quality, relevant context if the project's quantization-aware training/distillation step touches accumulation precision.

## Metric / eval choices

- All evaluation is throughput (tok/s, prefill vs. decode, at KV-cache depths 0 and 2048) and peak memory usage, geometric-mean-normalized across devices; there is no task-accuracy, instruction-following, or structured-output metric anywhere in the paper.
