# 2603.15954v2 — MobileLLM-Flash: Latency-Guided On-Device LLM Design for Industry Scale Deployment

**Relevance:** low
This is a pretraining-time neural architecture search paper for building new on-device model families from scratch (or via pruning+CPT); it has no post-training, tool-calling, structured-output, or quantization-for-deployment content applicable to fine-tuning a fixed LFM2.5-1.2B-Instruct checkpoint.

## TL;DR

Meta presents a hardware-in-the-loop Bayesian-optimization NAS that jointly searches model shape (depth/width) and attention pattern (skip / global / sliding-window) against measured mobile-CPU latency, producing the MobileLLM-Flash family (350M/650M/1.4B) via pruning a larger pretrained model and continued pretraining. It's a pretraining/architecture-design paper, not a post-training or quantization-for-deployment paper, so it doesn't bear on the LoRA→DPO→GRPO→quantization ladder this project follows.

## Techniques to try

- (None directly transferable — the "technique" here is architecture search over layer count, FFN/model dims, and attention-type-per-layer via Bayesian optimization on a pretrained backbone, which does not apply to post-training a fixed, already-shipped LFM2.5-1.2B architecture.)

## Baselines & datasets used

- Reports LFM2 350M/700M/1.2B as direct baselines on HellaSwag, BoolQ, PIQA, SocialIQA, TriviaQA, NQ, ARC-c/e, WinoGrande, plus MMLU/MBPP/HumanEval/OpenRewrite/TLDR9+ for instruction-tuned models — e.g. "LFM2 1.2B | 45.26 | 66.09 | 74.27 | 37.72 | 33.50 | 8.60 | 52.20 | 77.90 | 58.80 | 50.48" (Table 6) — but these are generic knowledge/reasoning benchmarks, not BFCL/IFEval/tool-calling, so the numbers don't ground any of this project's specific targets.
- Uses lm-eval-harness for standard benchmark scoring: "Using lm-eval-harness lm-eval-harness, we report exact-match rate for TriviaQA/NQ and character-level accuracy for other tasks" (Sec 4.2.1).

## Pitfalls / negative results

- "skipping too many attention layers consecutively (empirically, more than 3) degrades model quality under a fixed latency constraint and can even impair performance on harder generative tasks" (Sec 3.5) — a hybrid-architecture caveat, not applicable since our project isn't redesigning the attention pattern.
- Notes LFM2's own building block has a runtime weakness: "the underlying conv1d operator can perform poorly at small batch sizes or sequence lengths" (Sec 2) — mildly relevant background on the LFM2 architecture family this project builds on, but not something addressable via post-training.

## Metric / eval choices

- TTFT (time-to-first-token) is treated as the primary latency metric, with "∼2k tokens is a practical sweet spot where OD-LLMs can both perform useful tasks and achieve TTFT ≤4s" (Sec 1) — a deployment-latency framing distinct from this project's throughput-floor requirement (4-bit decode within 5% of base), and measured on mobile CPU (Samsung Galaxy S25 / iPhone 17) rather than the project's RTX 2080 Super GPU target, so not directly transferable.

## Open questions for our project

- None of this paper's core contributions (architecture NAS, pruning-based candidate evaluation, latency-quality Pareto search) speak to the project's actual questions (quantization damage to structured output, reward signals for "flag rather than assert," LoRA vs full fine-tuning, vocabulary-size effects on tool-call tokenization). One partial data point: MobileLLM-Flash uses a 202k vocabulary vs LFM2.5's 65,536, for the stated reason that "this increases the embedding parameters, it enhances information density per token" (Sec 4.2.2) — tangential support for the concern that a 65K vocabulary could be a tokenization handicap, but not a direct measurement of it.
