# 2605.26128v1 — The Constraint Tax: Measuring Validity-Correctness Tradeoffs in Structured Outputs for Small Language Models

**Relevance:** high
Directly targets sub-3B model tool-calling/structured-output reliability and shows that hard grammar-constrained decoding can silently wreck executable accuracy even at 100% schema validity — a core risk for a project whose consumer parses LFM2.5-1.2B tool calls programmatically.

## TL;DR

The paper measures a "constraint tax": for small models (0.5B–3B), forcing outputs through a hard JSON schema raises parse validity to ~100% but can tank answer/executable accuracy, because the model spends its limited capacity on syntax rather than solving the task and produces confidently wrong-but-valid objects. In a calendar tool-call analogue, prompt-only JSON (91.5% executable accuracy) beats hard-schema decoding (48.0%) even though both are 100% schema-valid — the failure is semantic (wrong `duration_minutes`), not structural.

## Techniques to try

- Adopt "reason free, constrain late": let the model solve the task in free or lightly-structured form, then package the answer into the schema only at the end, rather than constraining generation from the first token. ("delayed_constraint reaches 40.7% answer and executable accuracy at 100.0% schema validity" — Section 6.6, Table 10)
- Prefer rationale-bearing schemas or short scratchpads over answer-only hard schemas when the model needs to reason. ("Short rationales and post-solution packaging do better." — Section 6.6)
- Measure a prompt-only/soft-constraint baseline before adopting hard constrained decoding for the same object, and treat schema validity as a serving SLO, not a quality metric. ("Measure prompt-only JSON before hard-constraining the same object." — Section 7.5, item 1)
- If constrained decoding must be used, replicate results across the intended serving backend (vLLM vs SGLang) before trusting them, since backend/kernel differences can materially change accuracy for some models. ("Qwen results replicate across vLLM and SGLang... SmolLM2 is backend-sensitive" — Section 6.4, Table 8)

## Baselines & datasets used

- Deterministic synthetic "StructReason-Small" task suite (arithmetic_two_step, symbolic_string, object_tracking, boolean_logic, tool_call_argument), 1,000 instances × 5 modes per checkpoint, 15,000 generations total, evaluated with vLLM on a commodity GPU (Section 5, Table 1).
- Models tested: Qwen2.5-0.5B, Qwen2.5-1.5B-Instruct, SmolLM2-1.7B, and a Qwen2.5-3B-Instruct "boundary check" — all within or near this project's parameter regime.
- Calendar tool-call analogue: 200 examples, deterministic executable checker on tool name + arguments (title, date, start time, duration, attendee, topic), directly relevant to agent tool-call evaluation.

## Pitfalls / negative results

- Hard answer-only schema decoding on the main suite: schema validity 61.5%→100.0%, but answer accuracy fell 19.7%→11.0% (-8.7 pts) and wrong-valid-schema rate rose 49.5%→88.9% ("wrong-valid-schema outputs rise from 49.5% to 88.9%" — Section 6.1, Table 3).
- Calendar tool-call task: both prompt-only JSON and hard schema modes were 100.0% schema-valid, but hard-schema executable accuracy was 43.5 points lower (91.5%→48.0%), driven almost entirely by wrong `duration_minutes` (102 of 104 hard-schema failures were single-field duration errors) — a concrete example of "valid tool call, wrong decision" that a schema-validity-only gate would never catch (Section 6.3, Tables 6–7).
- This tax does not disappear at 3B: Qwen2.5-3B under answer_only_schema still lost 15.3 answer-accuracy points and gained 31.6 points of wrong-valid-schema outputs relative to prompt_json ("The evidence does not support the claim that this issue is limited to the smallest models." — Section 6.5, Table 9).
- Constraint effects are not universal — SmolLM2-1.7B's accuracy improved under hard schema decoding because its unconstrained JSON baseline was weak, and its results were backend-sensitive (18.7% on vLLM vs 25.7% on SGLang) — showing the effect is model- and serving-stack-dependent, not a fixed law (Section 6.2/6.4, Tables 5, 8).
- Reproducing SGLang results required a compatibility patch (routing RMSNorm through SGLang's native implementation), underscoring that constrained-decoding benchmarks are entangled with serving-engine maturity, not just model weights (Section 6.4).

## Metric / eval choices

- Explicitly separates four metrics that are usually collapsed: schema validity, answer accuracy, executable accuracy, and wrong-valid-schema rate — directly analogous to this project's need to track first-attempt schema validity separately from BFCL/tool-call correctness and from the malformed-tool-return flag rate.
- Defines "constraint tax" as a clipped, paired accuracy delta between a baseline and a constrained interface on identical problem instances: `Tax(m,t,c;b) = max(0, Acc(m,t,b) - Acc(m,t,c))`, with a normalized version dividing by baseline accuracy (Section 4.2).
- Uses an explicit error taxonomy (correct_valid, invalid_json, parse_failure_freeform, schema_validation_error, trace_answer_contradiction, wrong_answer_valid_schema) rather than a pass/fail bit — a useful template for this project's "flag rather than assert" malformed-tool-return work, since it distinguishes retryable parse failures from non-retryable wrong-valid-schema failures.
- Reports 95% nonparametric bootstrap confidence intervals over problem instances for paired comparisons where available.

## Open questions for our project

- Does the same tax pattern apply to LFM2.5-1.2B's hybrid conv/GQA architecture, or is it specific to the standard-attention Qwen/SmolLM2 families tested here? The paper explicitly limits its scope to "low-compute, locally accessible, or commodity-GPU-feasible checkpoints" and does not test hybrid architectures or 65K-vocab models.
- If grammar-constrained decoding (e.g., via vLLM/SGLang structured-outputs) is used at serving time for the shipped model, this paper suggests measuring wrong-valid-schema rate and executable accuracy under constraint, not just schema validity — worth incorporating into the eval harness alongside BFCLv3 and the malformed-tool-return probe.
- The paper's "reason free, constrain late" pattern is in tension with a deployment that wants deterministic, immediately-parseable tool calls (e.g., via grammar-constrained decoding for guaranteed valid JSON); worth deciding whether the project's serving stack should avoid hard grammar constraints on tool-call arguments entirely and instead rely on SFT/DPO to produce naturally valid + correct JSON, checked post hoc.
- No instruction-like text directed at the reader was found in this paper; it reads as a standard measurement/benchmark report.
