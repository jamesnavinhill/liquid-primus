# 2608.04714v1 — What We Observe as LLM Behavior Can Be a Side-effect of Inference Backend

**Relevance:** high
This project compares a base vs. post-trained ~1.2B model on BFCLv3/IFEval with 2-point guardrail margins, then ships a 4-bit GGUF (llama.cpp/Ollama-style stack) that must retain ≥97% of full-precision average — exactly the cross-backend, cross-format comparison this paper shows is not free of measurement noise, at the same ~1B-1.5B parameter scale.

## TL;DR

In a fully-crossed study of 3 instruction models (~1-1.5B params) × 5 inference backends (hf_raw, hf_pipeline, langchain_hf, vllm, ollama) × 6 benchmarks × 4 generation modes, the authors find that just changing the serving backend — even under greedy, noise-free decoding — can significantly shift benchmark scores and change which individual items are answered correctly. The effect is strongly model-dependent (Llama-3.2-1B was very sensitive, Gemma-3-1B was nearly immune) and larger on factual than social-bias tasks.

## Techniques to try

- Use deterministic/greedy decoding whenever comparing scores across backends or precisions, since it is the only regime free of sampling noise: "we recommend a minimum reporting standard where the backend name and its version, the complete generation configuration, and, for any cross-backend comparison, the use of deterministic (greedy) decoding as the only regime free of sampling noise."
- Explicitly disclose and match the full generation configuration (temperature, top_p, top_k, repetition penalty, max_new_tokens) across whatever harness is used for base-model vs. fine-tuned-model vs. quantized-build evaluation, since backend defaults differ a lot (Table 6: e.g. vLLM ignores the model's own `generation_config` and samples at temperature=1.0 by default; Ollama falls back to temp=0.8/top_p=0.9/top_k=40 when the Modelfile doesn't set them).
- If the shipped artifact is GGUF (this project's 4-bit build), treat the weight-format conversion as inseparable from the serving-stack effect rather than a confound to net out: "GGUF conversion is an unavoidable consequence of choosing Ollama, so its effect is part of the backend cost a practitioner incurs, not a confound to be removed."
- For any generation-based metric using surface overlap (e.g. ROUGE-L-style scoring), match `max_new_tokens` across all frameworks being compared before drawing conclusions, since response length is a confound: "Researchers using ROUGE-L as a proxy for generation quality should therefore ensure that max_new_tokens is matched across all comparison frameworks before drawing cross-backend conclusions."

## Baselines & datasets used

- Models: Llama-3.2-1B-Inst, Gemma-3-1B-IT, Qwen2.5-1.5B-Inst — all fp16, single RTX 3090, no quantization (except Ollama's GGUF export).
- Backends: hf_raw (AutoModelForCausalLM.generate), hf_pipeline, langchain_hf, vllm 0.8.5 (V0 engine), ollama (llama.cpp/GGUF).
- Benchmarks: MMLU, TriviaQA, TruthfulQA-MC1, TruthfulQA-Gen (factual family); BBQ, StereoSet (social-bias family) — none of these are tool-calling/structured-output benchmarks, so the paper gives no direct evidence for BFCLv3/schema-validity-style metrics.

## Pitfalls / negative results

- Even with zero sampling noise (greedy, temp=0, fixed seed), backend alone produced significant divergence: for Llama-3.2-1B-Inst, ollama diverged by mean |Δ|=0.055 and langchain_hf by 0.049 from the hf_raw baseline, each significant on the majority of the 11 per-item metrics tested (Table 1).
- The effect is not a small aggregate shift — it changes *which* items are answered correctly. Cohen's κ between ollama and hf_raw on Llama-3.2-1B-Inst fell to 0.45, and error-set Jaccard similarity to hf_raw dropped to a mean of 0.792 (vs. ≥0.93 for Gemma), meaning backends "redirect success and failure to different questions, a qualitatively different failure mode."
- Backend sensitivity is strongly model-dependent and not predictable from one test model: Gemma-3-1B-IT was severely affected in at most 4/16 backend×mode configurations on any task, while Llama-3.2-1B-Inst was severely affected in 14/16 on MMLU, TriviaQA, TruthfulQA, and BBQ — so validating a harness on one ~1B model does not establish it is safe for another model at the same scale.
- Variance attributable to backend/config choice compounds as more of the pipeline is left uncontrolled: 0.00074 (backend only, greedy) → 0.00112 (+ sampling noise) → 0.00190 (+ each framework's own default hyperparameters) — the structural backend effect alone is "roughly 39%" of the variance seen under realistic default settings.
- Only tested at ~1-1.5B scale, single GPU (RTX 3090), no quantization other than Ollama's GGUF path, no tool-calling/agentic/code benchmarks, and the authors themselves flag the ladder of generation modes as "an approximation rather than an exact decomposition," not a clean causal split.

## Metric / eval choices

- Calibrates all 14 raw benchmark metrics onto a common [0,1] scale (1 = best) before aggregating, so higher-is-better and ideal-at-0/0.5 metrics can be compared on the same axis.
- Defines "severe" divergence as a backend/mode flipping >5% of a task's items (dis_b > 0.05), citing this as the threshold "prior work treats benchmark differences as consequential."
- Uses McNemar's test for binary-outcome benchmarks and Wilcoxon signed-rank for continuous metrics, with Benjamini-Hochberg FDR correction across comparisons, plus Cohen's κ / Jaccard error-set overlap / PCA clustering as complementary per-item agreement diagnostics — a reasonable template for how this project could validate that its own eval harness is stable across the fp16-baseline vs. 4-bit-GGUF comparison it plans to run.

## Open questions for our project

- This paper only tests factual-knowledge and social-bias benchmarks, not tool-calling, JSON/schema validity, or agentic tasks — does the same backend-induced item-level flipping (up to 55% divergence, κ as low as 0.45) also apply to BFCLv3 and structured-output scoring, or could format-constrained outputs be more or less sensitive to backend/tokenization differences than free-form QA?
- If this project runs its fp16 base/fine-tuned model evals on one stack (e.g. HF/vLLM for training-time evaluation) and its shipped 4-bit build's evals through llama.cpp/Ollama, this paper implies part of any measured gap or regression could be a backend/GGUF-conversion artifact rather than a real quantization or fine-tuning effect — worth deciding upfront whether to force greedy decoding and a single consistent backend (or explicitly quantify and subtract the backend-only component) before trusting the ≥97%-retention and ≤2-point-guardrail-drift claims.
- No instructions directed at the reader were found embedded in the paper's text; Appendix I only discloses that the authors used an LLM coding tool for visualization/writing assistance, which is a disclosure, not a directive.
