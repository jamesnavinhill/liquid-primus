# 2608.18578v1 — Compress and Forget: bitsandbytes Quantization Amplifies Proactive Interference in LLMs

**Relevance:** medium
Directly bears on the "does quantization damage more than aggregate benchmarks show" question and on the 4-bit quality-retention target, but the quantization method tested (bitsandbytes NF4/INT8) is not the GGUF/llama.cpp path this project will actually ship, and the task (multi-turn key-rebinding retrieval) is not tool-calling/schema specific.

## TL;DR

The paper loads three 4–7B instruction models at FP16/INT8/INT4 (bitsandbytes) and shows that INT4 quantization sharply degrades accuracy on a "proactive interference" retrieval task — tracking a value that has been overwritten multiple times in-context — even though aggregate benchmark accuracy barely moves (1–2 points). The effect is specific to semantically confusable distractors, is mechanistically traced to more frequent retrieval of stale ("same-key intrusion") values, and INT8 is shown to be measurably risky in 2 of 3 models once paired statistical tests are used, not "safe by default" as commonly assumed.

## Techniques to try

- Use a targeted, non-aggregate behavioral probe (not just perplexity/MMLU-style eval) to check whether 4-bit quantization degrades state-tracking specifically, since "aggregate accuracy differences between FP16 and INT4 are small in absolute terms (1.1–2.4 percentage points) ... This is precisely why the effect we report below would not be visible from aggregate accuracy alone" (Section 4.1) — analogous logic could motivate a dedicated eval for whether the shipped 4-bit GGUF still tracks tool-call state/updated slot values correctly across a multi-turn agent conversation, beyond BFCLv3/IFEval aggregate deltas.
- Use paired (McNemar's) rather than unpaired significance testing when comparing base vs. quantized model outputs on identical prompts, since "McNemar's paired test tells a different story ... Mistral and Phi both show a real, if smaller-magnitude, INT8 accuracy penalty ... that the unpaired test lacked the power to detect" (Section 4.2) — relevant to how this project should statistically validate the ≥97%/no-axis-below-93% quantization retention claims rather than relying on raw score deltas.
- Do a component ablation (here: quantizing lm_head vs. backbone) to localize which part of the model a quantization-induced regression comes from, per Section 4.7: "the proactive-interference penalty under INT4 quantization is backbone-driven, not an artifact of quantizing the output projection."

## Baselines & datasets used

- PI-LLM key-rebinding retrieval task (Wang & Sun 2025, arXiv:2506.08184): a subject's attribute is overwritten k times, model must retrieve only the final value; tested at k ∈ {1,2,4,8,16,32,64,96}.
- Models: Qwen2.5-7B-Instruct, Mistral-7B-Instruct-v0.3, Phi-3.5-mini-instruct — all above this project's 1.2B target scale, so absolute numbers don't transfer, only the qualitative pattern.
- Quantization via bitsandbytes only (LLM.int8() INT8, NF4+double-quant INT4) — not GPTQ/AWQ/EXL2/HQQ, and explicitly not the GGUF/llama.cpp quantization path this project will use for the final artifact.

## Pitfalls / negative results

- "INT8, often assumed safe, also carries a smaller but real penalty in two of three models" — paired testing revealed a real INT8 accuracy penalty (p=0.018 Mistral, p=0.004 Phi) that an unpaired Fisher's test had missed entirely (p=0.410, 0.197) — a caution against assuming any "safe" quantization level based on standard significance testing without paired trial design.
- The effect is a "cliff," not graceful degradation: "INT8 is statistically indistinguishable from FP16 in two of three models, while INT4 shows a significant, consistent drop" — e.g., Qwen accuracy drops 81.0% → 68.3% at its highest interference level under INT4 while overall pooled accuracy only drops 97.6% → 96.5%. A 1-point aggregate quantization delta can mask a 10+ point regression concentrated in a specific behavioral regime.
- Non-monotonic exception noted honestly: "the one condition in our data where INT8 accuracy falls below INT4" (Phi at k=16, Appendix E) — the authors report this rather than omit it, flagging that quantization effects aren't always cleanly ordered by bit-width.
- Bitsandbytes' default INT4 loading path silently left lm_head at full precision despite no explicit skip-list, discovered only by inspecting the loaded module directly — a reminder to explicitly verify which layers a quantization library actually converts, not just what config flags claim.
- Explicit scope limitation acknowledged by the authors: "Our quantization coverage is bitsandbytes-specific ... Extending this evaluation to calibration-based quantizers (GPTQ, AWQ) and newer formats (EXL2, HQQ) ... would clarify whether the effect is specific to bitsandbytes' NF4 scheme or reflects a more general cost of aggressive weight compression" (Section 6) — i.e., the authors themselves do not claim this generalizes to other quantization schemes (including, implicitly, GGUF k-quants).

## Metric / eval choices

- Interference Endurance Score (IES): area under the accuracy-vs-log2(interference-level) curve, normalized to [0,1] — a single-number summary metric for a capability that degrades gradually, useful as a template for summarizing a degradation curve rather than a single point estimate, but the paper also cautions IES can "understate" a real cliff effect when most of the tested range is near ceiling.
- Same-key intrusion rate (fraction of all trials, not just errors, where the wrong answer exactly matches an earlier overwritten value) as a mechanism-level metric distinguishing "confusion between plausible values" from generic noise — a useful pattern for diagnosing *why* structured-output failures occur post-quantization (e.g., distinguishing "grabbed a stale tool-arg value" from "produced garbage").
- McNemar's exact paired test as the primary significance test when the same prompts are run across quantization levels — directly applicable template for this project's base-vs-quantized comparisons.

## Open questions for our project

- Does an analogous "cliff" exist for LFM2.5-1.2B under GGUF 4-bit quantization specifically for tool-call argument tracking across multi-turn conversations (e.g., a tool result value referenced several turns later), even if BFCLv3/IFEval aggregate deltas stay within the pre-registered 2-point guardrail band?
- The paper's mechanism (representational coarsening of semantically similar candidates in the backbone) suggests structured-output tasks with many similar-looking valid values (e.g., near-duplicate enum options, similar field names in a JSON schema) could be disproportionately at risk under 4-bit quantization — worth a targeted probe analogous to this paper's same-key intrusion analysis, adapted to schema-slot-value confusion.
- No instruction-like text directed at the reader was found in the paper; it is a standard empirical study throughout.
