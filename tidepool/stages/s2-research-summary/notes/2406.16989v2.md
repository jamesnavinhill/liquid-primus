# 2406.16989v2 — Retrieval-Augmented Mixture of LoRA Experts for Uploadable Machine Learning

**Relevance:** low
The paper's core problem — retrieving and composing many independently-trained, domain-specific LoRAs at inference time for a multi-tenant serving platform — is a different setting from this project (one model, one specialized skill, no ensembling), and the project's standing constraints explicitly place ensembling out of scope.

## TL;DR

RAMoLE proposes a "retrieve-then-compose" system (LoraRetriever + an attention-based RouterLoRA + a batched-inference kernel) so a server holding a large, growing pool of task-specific LoRAs can pick and blend the right ones per incoming request, on Llama-2-7B/13B. It is a multi-tenant LoRA-serving architecture paper, not a single-model post-training recipe, so it mostly doesn't bear on how to train LFM2.5-1.2B for reliable tool calling.

## Techniques to try

- None directly transferable: the project trains and ships a single specialized LoRA/model, not a dynamically expanding pool of independently-trained LoRAs requiring runtime retrieval and routing.
- Minor, reusable data point if LoRA SFT is used: their per-task LoRAs were trained with "rank $r$ and the scaling hyperparameter $\alpha$ are set to 6 and 12, respectively" (Sec. V-2) on Llama-2-7b/13b for Flan-v2 task clusters — a concrete low-rank config that worked for narrow-task specialization, though at a different model scale/architecture than LFM2.5-1.2B.

## Baselines & datasets used

- Base models: Llama-2-7B and Llama-2-13B, not ≤8B in the sense of small on-device models — closest to relevant but still 6x+ larger than the 1.2B target, so numbers are not directly transferable.
- Training/eval data: a subset of Flan-v2 (Wei et al.) used to train 48 task-specific LoRAs across 10 task clusters (NLU/NLG); mixed-task eval built from 50 held-out samples per task (2400 total).
- Baselines compared: MoE (dense/top-1/top-3 gating), SMEAR (parameter-level soft merging), AdapterSoup, LoRAHub — all multi-LoRA composition methods, none of which resemble the single-adapter SFT/DPO/GRPO ladder this project is following.

## Pitfalls / negative results

- Naive parameter-level fusion of multiple task LoRAs fails badly under heterogeneous tasks: "This results in catastrophic collapses in performance on respective tasks after fusion due to parameter interference, a phenomenon that becomes more pronounced with the increasing number of composed LoRAs" (Sec. IV-B1) — relevant only if this project ever considers merging multiple trained LoRAs (e.g., a tool-calling LoRA + a separate guardrail LoRA); the paper's evidence says don't average parameters across heterogeneous skills.
- "LoRAHub proves to be entirely ineffective in the mix-task scenario... the presence of heterogeneous tasks introduces conflicting parameter optimization directions, resulting in the total breakdown of parameter fusion" (Sec. V-A) — another data point against naive weight-space merging of adapters trained on different objectives, which could matter if a future iteration tries to combine a tool-calling LoRA with a separately-trained flag/refusal LoRA rather than joint training.

## Metric / eval choices

- Not applicable — the paper's task suite (Struct-to-Text ROUGE, Translation BLEU, NLU exact-match on GLUE-style tasks) has no overlap with this project's BFCLv3 / IFEval / schema-validity / malformed-tool-return metrics.

## Open questions for our project

- If a future iteration explores training separate LoRAs for tool-calling vs. the "flag malformed tool return" behavior rather than one joint objective, this paper's negative result on parameter-fusion of heterogeneous LoRAs ("catastrophic collapses... due to parameter interference") is a concrete reason to prefer joint SFT/DPO over post-hoc adapter merging — worth flagging even though the paper itself is otherwise out of scope.
- No instruction-like text directed at the reader was found in the paper; it reads as a standard research paper throughout.
