# 2410.07295v2 — ITERGEN: Iterative Semantic-Aware Structured LLM Generation with Backtracking

**Relevance:** low
This is an inference-time constrained-decoding/backtracking framework, not a training method, and it sits opposite the project's core metric, which is explicitly scored with "no retry, no repair, and no constrained decoding or grammar enforcement"; it is useful only as background on what grammar-guided baselines can and cannot fix.

## TL;DR

ITERGEN adds forward/backward navigation over grammar symbols (not raw tokens) to LLM decoding, so a program can detect a semantic violation (bad SQL column name, private email, invalid Vega-Lite field) and selectively backtrack and resample just that fragment instead of restarting generation. It is evaluated on small-to-mid open models (0.5B–8B) for SQL generation, Enron-email privacy leakage, and Vega-Lite spec generation, consistently beating plain unconstrained decoding and the authors' own prior grammar-only tool (SYNCODE).

## Techniques to try

- None directly transferable to this project's training pipeline — this is a decode-time framework requiring a hand-written BNF/Lark grammar and a custom generation loop, not a fine-tuning or RL method. Could only matter if the shipped gateway were allowed to use grammar-constrained decoding as a deployment-side backstop, which the project's own metric design deliberately excludes for the headline number.
- The recurrence-penalty idea for avoiding repeated resampling loops is a generic technique worth knowing about: "we introduce a small recurrence penalty, denoted by γ, which is applied to the probabilities of previously selected tokens... multiplying them by (1 − γ)^α, where α is the number of times the token has been backtracked" (Section 3.2, Decoding Trace) — relevant only if the project ever builds a rejection-sampling/backtracking harness for generating training data (e.g. malformed-tool-return pairs), not for the shipped model itself.

## Baselines & datasets used

- Text-to-SQL: Spider dataset (1034 problems, easy/medium/hard/extra-hard splits), evaluated with Qwen2.5-0.5B/1.5B (base, instruct, coder) and Llama-3.2-1B/3B, Llama-2-7b-chat, Meta-Llama-3-8B — a useful reminder that structured-output failure rates at ~0.5–1.5B scale are large even for pure syntax tasks: STANDARD (unconstrained) decoding on Llama-2-7b-chat scored "0.0" accuracy and 0% execute rate on Spider in Table 1.
- Privacy leakage: DecodingTrust Enron email extraction benchmark; ITERGEN reduces leaks to 0 across 9 models (0.5B–8B) at the cost of "a small increase in average time per completion and average tokens per generation" and "a small increase in response perplexity."
- Vega-Lite: NLV Corpus (814 text-utterance/spec pairs), evaluated on Qwen2.5-1.5B, Llama-3.2-3B, Llama-3-8B.

## Pitfalls / negative results

- Grammar constraints alone (their own prior tool SYNCODE) guarantee syntax but not semantics: "these techniques fall short of enforcing semantic properties that extend beyond syntax... grammatical constraints alone cannot adequately ensure that a variable name in LLM-generated code is defined before its use" (Section 1) — directly evidences that syntactic validity and semantic/execution correctness are separate axes, which matters for how this project should structure its schema-validity vs. execution-correctness reward.
- Explicit scope limitation: "ITERGEN is currently limited to single LLM generation and does not support multiple sequence generation in batch" (Section 6, Limitations) — a batching/throughput cost that would matter if anyone considered this for the deployed gateway.
- The backtracking overhead is nontrivial even though the paper frames it as small: on SQL generation, ITERGEN's average generation time is higher than STANDARD or SYNCODE for several small models (e.g. Qwen2.5-0.5B: 0.981s vs 0.607s STANDARD, Table 1), i.e., resampling for correctness costs real latency — a relevant caution if any future design considers decode-time correction as a cheaper substitute for training-time fixes, but not something this project needs since constrained decoding is out of scope for the target metric.

## Metric / eval choices

- Uses paired metrics (Accuracy = exact/correct query, Execute = runs without runtime error) rather than a single pass/fail number for SQL — conceptually similar to this project's own paired flag-rate/false-flag-rate design, though applied to a different problem (syntax+semantics of generated code, not malformed-tool-return detection).
- Privacy eval reports leak count alongside perplexity as a utility/quality check, showing the paper's authors also worried about a guardrail intervention silently degrading output quality — analogous concern to this project's requirement that guardrail metrics stay within 2 points of base.
