# 2608.19098v1 — Open-MOPD: Diagnosing and Fixing Capability Imbalance in Multi-Teacher On-Policy Distillation

**Relevance:** low
Studies multi-teacher on-policy distillation for merging separate RL specialists into one 3B student — a method explicitly out of scope here ("Ensembling is out of scope") and run at a different scale/architecture (SmolLM3-3B) with no quantization or tool-calling focus, but its diagnosis of short-response tasks losing training signal to long-response tasks is a useful cautionary analogy for balancing tool-call/JSON data against longer instruction data.

## TL;DR

The paper diagnoses why combining three domain-specialist RL teachers (math, code, instruction-following) into one student via on-policy distillation recovers only 35.6% of the achievable improvement, tracing it to token-level optimization-budget imbalance rather than teacher disagreement, then fixes it with token-share balancing, gap-following budget allocation, and reward refresh, raising recovery to 83.4%. It is a multi-teacher consolidation recipe, not a single-model SFT/DPO/GRPO/quantization pipeline like this project's.

## Techniques to try

- Not directly applicable: this project's candidate ladder (LoRA SFT → full SFT → DPO → GRPO → quantization-aware distillation) has no multi-teacher distillation stage, and the brief states "Ensembling is out of scope," which is effectively what Open-MOPD is designed for.
- If a data-mix imbalance shows up between short structured-output examples (tool calls, flags) and longer natural-language answers during SFT/GRPO, the paper's diagnostic — measuring token share vs. prompt share per category — is a cheap, reusable check: "concise IF tasks... accounting for $20.3\%$ of the input prompts but only $0.99\%$ of the gradient tokens" (Section 1/3.3).

## Baselines & datasets used

- Base model SmolLM3-3B-Base (65K+ context, 3B params) — not LFM2.5-1.2B; results are at a larger scale than this project's 1.2B target, so absolute numbers don't transfer.
- Domain datasets: OpenR1-Math-93k, OCR-50k (code), Instruction-Nemotron (SFT); DAPO-Math-17k, DeepScaler-24k, Nemotron-IF-RL-46k (per-domain RL teachers). None overlap with this project's structured-output/tool-calling focus.
- Evaluation: AIME24/25, LiveCodeBench v5/v6, IFEval + IFBenchtest — IFEval and IFBench are also in this project's guardrail metric list, but only as generic instruction-following benchmarks, not BFCL/tool-calling.

## Pitfalls / negative results

- Concise/short-response domains (instruction following) get starved of gradient signal purely because loss is token-mean aggregated: "the average response length of math and code is about 10,500 tokens while that of IF is only 409 tokens, a difference of more than 25 times" (Section 3.3), causing IF's token share to stay near 1% despite ~20% prompt share.
- Naively fixing this by oversampling short-response prompts doesn't work: "For IF to obtain $1/3$ of the token budget, its number of prompts would have to be scaled up about 33.6 times... the math and code prompts in a batch would be squeezed to the point where long-chain supervision can no longer be maintained" (Section 3.3).
- Naive inverse-reward-magnitude weighting (giving more budget to domains that already converged, mistaking a shrinking reward for "still needs help") creates a runaway feedback loop and crashes training: "the IF gap shrinks by $32.5\times$, its weight rises from 24.4 to 80.9, and training stops at step 74" (Section 5.2).
- Directly masking or averaging over "high-conflict" tokens between teachers (i.e., trying to resolve disagreement rather than budget) *hurts* performance: "the three conflict masks reduce the total score by $0.52$, $0.73$, and $0.75$ points... The consensus target reduces it by $0.83$ points" (Section 3.2) — a plausible-looking intervention that this project might be tempted to try (e.g., masking ambiguous tokens in preference data) that backfires here.
- Multi-step/multi-minibatch reuse of one rollout batch causes reward staleness that grows with inner-update count K, and "the fraction of tokens clipped by PPO rises with $K$, from 0 to 0.86" (Section 3.3) — relevant if this project's GRPO stage reuses rollouts across multiple gradient steps.

## Metric / eval choices

- Defines an "integration gap" and "recovery rate" relative to a per-domain oracle-routed reference (RouteRL/RouteOPD) — a useful evaluation pattern (single model vs. a per-task "best possible" ensemble) if this project ever wants to quantify how much of the "ideal" tool-calling + general-capability trade-off a single fine-tuned model actually recovers, though it requires training separate reference models this project won't have.
- Uses mean@k with domain-appropriate n (n=64 for AIME, n=1 for IFEval, n=10 for LiveCodeBench) and macro-averages per-domain before combining — a reasonable template for reporting but not new information for this project's already-specified metric suite.

## Open questions for our project

- None of the paper's text reads as an instruction addressed to a reader; it is a standard research paper.
- Does the token-count imbalance finding (short structured outputs receive disproportionately little gradient signal under token-mean loss) apply to this project's SFT/DPO/GRPO stages, where tool-call JSON outputs may be much shorter than the natural-language answers or reasoning traces they're trained alongside? Worth a quick token-share audit of the training mix before assuming uniform learning across output types.
