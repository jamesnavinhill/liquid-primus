# 2511.03825v1 — How Different Tokenization Algorithms Impact LLMs and Transformer Models for Binary Code Analysis

**Relevance:** low
Real topic overlap on tokenizer/vocabulary-size effects on downstream accuracy, but the paper trains custom tokenizers from scratch for assembly/binary-code tasks (BERT, BART, Llama 3.2 1B), not tool-calling/JSON structured output, and does not touch quantization, LoRA/DPO/GRPO, or agent-turn evaluation — nothing here settles a decision for this project.

## TL;DR

The paper trains BPE, Unigram, and WordPiece tokenizers at four vocabulary sizes (3K/25K/35K/128K) on disassembled x86 code and measures both intrinsic properties (fertility, vocab overlap, OOV) and extrinsic downstream accuracy (masked-token prediction with BERT/Llama 3.2-1B, function-signature/return-type prediction with Llama 3.2-1B/BART) with and without an address-normalization preprocessing step. Bigger vocabularies and preprocessing (normalizing addresses, hex-to-decimal) generally help, but which tokenizer algorithm wins is inconsistent across models and tasks, and the paper's own pretrained-tokenizer baselines often beat the custom-trained alternatives.

## Techniques to try

- Address/hex normalization preprocessing before tokenization — replacing memory addresses with sequential placeholder tokens and converting hex to decimal — consistently improved downstream accuracy across models: "The proposed preprocessing method replaces every distinct memory address in the code with a sequential identifier" and "the preprocessing step consistently enabled higher performance across different tokenizers and vocabulary sizes" (Sections III-B2, V-B). This is a preprocessing-normalization idea (normalize high-entropy, low-information numeric/identifier spans) that could translate to normalizing volatile literals (UUIDs, timestamps, ports) in tool-call training data before tokenization, though the domain is different.

## Baselines & datasets used

- Dataset: 100,000 deduplicated (TLSH fuzzy-hashed) disassembled C functions scraped from GitHub, compiled with GCC -O2, disassembled with Ghidra, filtered to 30–100 instructions per function; 80K train / 20K test (Section III-C).
- Models: Llama 3.2 1B-Instruct (decoder-only, CLM), BERT-family (MiniLM-L12-H384, encoder-only, MLM), BART-base (encoder-decoder) — all ≤1B parameters, matching this project's scale range.
- The models' own pretrained tokenizers (128K vocab for Llama 3.2, default BERT/BART vocabs) were used as baselines against the custom-trained BPE/Unigram/WordPiece tokenizers.

## Pitfalls / negative results

- A larger vocabulary did not uniformly help: "the impact of vocabulary size is less pronounced for WordPiece, where improvements are relatively marginal" and BART's best result overall came from the *smallest* vocabulary (Unigram-3K at 88.81% accuracy on preprocessed data), not the largest (Section V-C1, V-D).
- Custom-trained tokenizers rarely beat the models' original pretrained tokenizers: "The Llama 3.2 model's default pre-trained tokenizer, trained with the dataset, showed the highest performance, 80.48%, and 82.30% accuracy for the default and preprocessed dataset, respectively. For the custom tokenizers, the highest accuracy we obtained is 71.69%" on masked-token prediction (Section V-B) — i.e., swapping out a model's native tokenizer for a domain-retrained one lost ~9–11 points here rather than gaining.
- Preprocessing that helps custom tokenizers can hurt a model's own pretrained tokenizer: "BERT's default tokenizer achieved higher average accuracy on masked token prediction tasks using the default dataset compared to the preprocessed version, underscoring the importance of task-specific dataset-tokenizer alignment" (Section VI) — a preprocessing step is not a free win and must be validated against the specific tokenizer it will pair with, not assumed to generalize.
- No hyperparameter optimization was done for any tokenizer configuration (Section VII-1), and the study explicitly did not test correlation between intrinsic tokenizer metrics (fertility, overlap) and extrinsic task performance (Section VII-3): "intrinsic metrics providing partial but incomplete predictability of extrinsic evaluation outcomes" (Abstract) — so fertility/compression numbers alone should not be trusted as a proxy for downstream quality.

## Metric / eval choices

- Fertility metric (average tokens per instruction) used for intrinsic tokenizer comparison (Section III-E1) — not directly reusable since this project isn't retraining a tokenizer, but the general caution that fertility ("intrinsic") does not reliably predict task accuracy ("extrinsic") is a relevant methodological warning against over-indexing on tokenization-efficiency stats alone.
- Extrinsic evals were masked-token-prediction accuracy and function-signature (parameter/return-type) prediction accuracy — both are pretraining/probing-style tasks, not the agent-turn/tool-call/schema-validity metrics this project needs (BFCL, IFEval, schema validity, flag rate). No transferable eval methodology here.

## Open questions for our project

- The paper only evaluates vocabulary size effects by *training new tokenizers from scratch* on a new domain corpus; it says nothing about how a fixed, already-trained 65,536-token vocabulary (as in LFM2.5-1.2B) performs on JSON/tool-schema tokenization versus a 128K-vocab peer model — the open question about vocabulary-size handicap for tool calling is not actually addressed by this paper despite superficially resembling it.
- No content in this paper reads as an instruction directed at the reader; it is a standard academic paper describing an assembly-code tokenization study.
