# 2510.13998v1 — BitNet Distillation

**Relevance:** high
Directly targets the project's late-ladder step ("quantization-aware distillation, then quantization-aware training if needed"), giving a concrete three-stage recipe (SubLN + continue pre-training + attention/logit distillation) at 0.6B–4B scale plus hard evidence that naive QAT fine-tuning degrades and fails to scale.

## TL;DR

BitDistill fine-tunes off-the-shelf full-precision LLMs (Qwen3, Qwen2.5, Gemma3, 0.6B–4B) into 1.58-bit ternary-weight BitNet models for a specific downstream task, using architectural refinement (SubLN), a short continued-pretraining warm-up (10B tokens), and logits + attention-relation distillation from the FP16 model as teacher — recovering FP16-level task accuracy while cutting memory ~10x and boosting CPU inference ~2-2.65x. It is not the same low-bit target as the project's 4-bit GGUF, but the training recipe (why naive QAT fails, how distillation and a warm-up stage recover it) transfers directly to the project's "quantization-aware distillation/training" rung.

## Techniques to try

- SubLN insertion before MHSA and FFN output projections to stabilize activation variance in the quantized model before any task training: "we further insert SubLN right before the output projection of the Multi-Head Self-Attention (MHSA) module as well as before the output projection of the Feed-Forward Network (FFN)" — §3.1
- A short continue-pretraining warm-up on generic corpus *before* task fine-tuning specifically to fix the quantization-scale gap that otherwise grows with model size: "we propose a two-stage training pipeline consisting of a continue training stage, which leverages only a small amount of pretraining corpus... followed by fine-tuning on the downstream task" — §3.2 (they use only 10B FALCON tokens, called "virtually negligible" next to 4T-token from-scratch pretraining)
- Combine logits distillation (KL between FP16 teacher and quantized student output distributions, temperature 5.0) with attention-relation distillation on Q/K/V (MiniLM-style) at a single well-chosen layer rather than all layers: "we recommend performing attention distillation at only a single layer... as conferring greater optimization flexibility to the 1.58-bit student BitNet often yields superior downstream performance" — §3.3
- Layer choice for attention distillation matters and later layers do better: "layers located in the later stages of the model tend to deliver better distillation performance" — §4.4
- A stronger FP16 teacher (larger model) transfers to better quantized-student results even at fixed student size: "our algorithm can effectively extract larger gains from a higher-quality teacher, even surpassing FP16 models of the same size" — §4.4

## Baselines & datasets used

- Task datasets: GLUE MNLI, QNLI, SST-2 (classification, accuracy) and CNN/DailyMail (summarization, BLEU/ROUGE) — all at Qwen3 0.6B/1.7B/4B, plus Qwen2.5-0.5B and Gemma3-1B robustness checks (§4.1, Table 3)
- Compared against FP16-SFT (full-precision fine-tune) and BitNet-SFT (direct 1.58-bit conversion + fine-tune, no distillation) — both are small-model, standard baselines relevant at our scale
- Compatibility check with post-training quantization methods GPTQ, AWQ, Block-Quant, and plain min-max quantization, all combined with BitDistill (§4.3)

## Pitfalls / negative results

- Naive QAT fine-tuning of an existing full-precision LLM into 1.58-bit, without their pipeline, is unstable and does not scale: "as model size increases from 0.6B to 4B, the performance gap relative to the full-precision baseline grows from 13.9 to 15.3" — §1. This is a direct, at-scale (well under 8B) data point that plain quantization-aware fine-tuning gets *worse* relative to FP16 as the model grows, not better — worth weighing against the project's plan to fall back to "quantization-aware training if needed."
- Removing any one of the three stages (modeling refinement, continue pre-training, distillation-based fine-tuning) causes a "non-trivial drop" in downstream performance (Table 5, e.g. MNLI accuracy drops from 88.17 to 76.30 without continue pre-training and distillation, i.e., with only SubLN) — the components are not individually sufficient.
- Without SubLN, 1.58-bit optimization is described as unstable with worse convergence, motivating the architectural change as a precondition for any of the later stages — an easy-to-miss prerequisite if one jumps straight to distillation-based QAT.

## Metric / eval choices

- Classification: accuracy on MNLI/QNLI/SST-2. Summarization: BLEU + ROUGE-1/2/L/SUM on CNNDM, generation length capped at 4096 tokens, greedy decoding (top-p 1.0, temperature 0) — a reasonable pattern to reuse for reporting quantized-vs-full-precision task-quality retention, though none of these map onto BFCL-style schema/tool-call validity.
- Runtime efficiency reported as CPU token throughput (16 threads) and memory (GB), not GPU decode throughput — differs from this project's GPU-throughput-within-5% requirement, so the speed numbers here (2x–2.65x CPU speedup) are not directly transferable evidence for the project's 4-bit GGUF-on-GPU throughput target.

## Open questions for our project

- The paper's low-bit target is 1.58-bit ternary BitNet (a from-scratch architectural change requiring SubLN insertion and retraining), not a post-hoc 4-bit GGUF of an unmodified architecture — does the distillation recipe (logits + single-layer attention KD, continue-pretrain warm-up) still help at 4-bit where the quantization error is much smaller, or is it only necessary at the much more aggressive 1.58-bit regime?
- All experiments are single-task classification/summarization fine-tunes, not agentic tool-calling/structured-output tasks, so it does not answer whether low-bit quantization disproportionately harms structured-output/instruction-following versus knowledge — that question remains open for our project.
- The continue-pretraining warm-up uses 10B generic-corpus tokens on 8×AMD MI300X GPUs; unclear whether an equivalent warm-up at far smaller compute budgets (single-GPU, queued-job scale) still closes the scalability gap, or whether the benefit requires that token budget.
