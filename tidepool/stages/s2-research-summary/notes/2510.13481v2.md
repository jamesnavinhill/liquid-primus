# 2510.13481v2 — Tahakom LLM Guidelines and Recipes: From Pre-Training Data to an Arabic LLM

**Relevance:** low
The paper is about pre-training-stage data curation, tokenizer design, and evaluation-benchmark correction for Arabic LLMs, using LLaMA3.2-1B continued pre-training as the testbed — it never touches tool calling, structured output, post-training methods (LoRA/DPO/GRPO), or quantization, which are this project's actual levers.

## TL;DR

This is a from-scratch/continued-pretraining recipe paper for Arabic LLMs covering pre-training data collection/filtering, tokenizer vocabulary-size and pre-tokenization ablations, and a corrective re-annotation of the Arabic MMLU benchmark. Its only loose connection to this project is the tokenizer vocabulary-size ablation, which is worth a glance for the "does 65K vocab handicap tool-call/JSON tokenization" question, but the experiment is about Arabic-vs-English fertility on a 1B LLaMA model, not JSON/tool-call tokenization specifically.

## Techniques to try

- None directly transferable — no post-training, quantization, or tool-calling technique is described in this paper.

## Baselines & datasets used

- Vocabulary-size ablation used "the pre-trained LLaMA3.2-1B model with a tokenizers trained on Arabic text" at three sizes: "we trained multiple tokenizers with three distinct vocabulary sizes (32K, 64K, and 128K)" (Section 3.1) — a different model family/scale than LFM2.5-1.2B, but the vocab-size range brackets the 65K vs 128K comparison relevant to this project's open question.

## Pitfalls / negative results

- Larger vocabulary reduces tokenization fertility (better compression) but this does not reliably improve downstream task accuracy: "while fertility scores declined with larger vocabularies, indicating more efficient encoding, this did not consistently lead to higher accuracy on Arabic tasks across all evaluation datasets" (Section 3.2). Relevant caution: fertility/compression gains from vocab size are not a proxy for task quality.
- Structured/symbolic domains barely benefit from larger vocabularies: "Structured domains such as Math and Code, however, maintain relatively high fertility scores even with larger vocabularies. Math decreases only to 2.14, while Code remains above 2.70 across all vocabulary sizes" (Section 3.2) — i.e., going from 32K to 128K vocab gave only marginal fertility improvement on Code text. This is a weak data point (Arabic-focused model, not JSON/tool-call specific) suggesting vocab size alone may not be the dominant lever for code/structured-output tokenization efficiency, but it does not directly test JSON or tool-call schemas.
- Widely-used MMLU-style benchmarks (including the Arabic translation) contain systematic ground-truth and translation errors requiring manual correction — a general reminder to sanity-check any benchmark numbers rather than a specific pitfall for this project's BFCL/IFEval/GPQA metrics.

## Metric / eval choices

- Uses "fertility score" (average tokens per text segment) as the tokenization-efficiency metric when comparing vocabulary sizes and pre-tokenization schemes (Section 3.2) — a metric that could in principle be reused to check tool-call/JSON tokenization efficiency for the 65,536-vocab LFM2.5 tokenizer, but the paper does not apply it to code/JSON specifically beyond the coarse "Code" domain bucket.

## Open questions for our project

- Could the "fertility score" methodology be cheaply repurposed to directly measure how LFM2.5's 65K-vocab tokenizer compresses JSON tool-call syntax versus a 128K-vocab peer, rather than relying on this paper's Arabic-only result as a proxy?
- No instruction, prompt-injection, or agent-directed text was found in the paper; it reads as a standard research paper throughout.
