# 2605.16790v1 — TIER: Trajectory-Invariant Execution Rewards for Multi-Step Tool Composition

**Relevance:** high
This is a direct blueprint for the "GRPO with verifiable rewards (schema validity and execution correctness)" rung of the candidate ladder, including a concrete reward decomposition, weighting rationale, and a documented reward-hacking failure mode that answers one of the project's open questions.

## TL;DR

TIER decomposes the RL reward for tool-calling into four schema/execution-grounded, reference-free terms (format validity, schema adherence, execution success, answer correctness) instead of comparing to one annotated "correct" trajectory. On Qwen3-8B, this lifts multi-step tool composition accuracy from near-zero at depth ≥4 (with a naive outcome reward or with trajectory-matching rewards like ToolRL) to ≥90% at every depth 1–6, and improves BFCL v3 overall from 64.31 (base Qwen3-8B) to 68.92.

## Techniques to try

- Decompose the RL reward into four trajectory-invariant, schema/execution-checked components rather than one outcome signal or a reference-trajectory match: "$R_{\text{total}}=R_{\text{format}}+R_{\text{parse}}+R_{\text{exec}}+R_{\text{answer}}$" with $R_{\text{parse}}=R_{name}+R_{param}+R_{dtype}$ — Section 2.2.
- Grade parameter/type correctness by mismatch count rather than binary pass/fail: "$R_{param/dtype}=\text{clip}(1-\lambda_{p}\cdot p,0,1)$" with $\lambda_{p}=0.25$ — Section 2.2. Directly usable for a schema-validity training signal without an LLM judge.
- Weight final-answer correctness much higher than the structural terms to avoid the model gaming format/schema/execution checks without solving the task: "We weight answer correctness substantially higher than the other components because lower weightings induce reward hacking — the model satisfies format, schema, and execution validity without producing correct answers, and training stalls before the answer correctness signal can take effect." — Section 2.2 (they use $R_{\text{answer}}=5\cdot 1[\text{answer correct}]$ against a $[0,4]$-range structural budget).
- Make execution-success reward all-or-nothing per sequence rather than fraction-of-calls-succeeded, because a failed intermediate call invalidates everything downstream: "a graded reward (e.g., fraction of successful calls) would credit work that produced no usable result" — Section 2.2.
- JSON-based AST is the best intermediate representation for tool-call generation among JSON/XML/direct-call-list, tested under the same reward: "JSON achieves the best overall performance and is therefore used as the default IR" — Section 4.5 (Table 5: JSON 68.92 vs XML 66.06 vs Direct 63.80 overall BFCL v3).
- Batch-Normalized GRPO was their chosen default over standard GRPO and DAPO for consistency across composition depths, though "all three algorithms enable multi-step composition when paired with fine-grained, trajectory-invariant, execution rewards" — Appendix F, so algorithm choice is secondary to reward design.

## Baselines & datasets used

- DepthBench: a new benchmark they release, 1,710 queries over 163 executable tools, depth-stratified 0–6 (944 train / 766 val for multi-step split) — Section 3.
- BFCL v3 (Berkeley Function Calling Leaderboard) and NestFUL used as external transfer benchmarks — Sections 4.1, 4.4.
- ToolACE (~10K examples, ~26K tools) and xLAM (~60K examples, ~4K tools) adapted into executable-reward form for a data-scale comparison — Appendix E.
- ToolRL (Qian et al., 2025) is the trajectory-supervised reward baseline they compare against throughout.

## Pitfalls / negative results

- SFT baseline underperformed and regressed versus the untrained base model on BFCL v3: "SFT performs worse overall (61.47%) and degrades relative to the base model, reflecting overfitting to single reference trajectories." — Section 4.4. Directly relevant given this project's ladder starts with SFT.
- Trajectory-supervised reward (ToolRL) collapses to 0% accuracy at depths 5–6 on DepthBench and to 0.38%/0.81% on BFCL Multiturn/Irrelevance, because it "penalizes valid alternative compositions" — Sections 4.2, 4.4.
- Simple outcome-only reward (format + final-answer correctness) drops from 94.38% at 1-step to 1.25% at 2-step and 0% beyond 4-step — Table 1.
- Reward hacking observed when execution reward is added without the schema/parsing term: "the model learns to route most queries to a small set of 'safe' tools that reliably execute, accumulating execution reward while answering incorrectly" — Section 4.3. Directly answers the project's question about avoiding reward hacking on a schema-check reward: schema and execution terms must both be present, and answer correctness must dominate the weighting.
- All ablated (partial) reward variants converge stably but plateau early — "the model saturates the available signal; the signal itself lacks the structure needed for compositional behavior" — Section 4.3. Warning that a training curve that looks converged is not proof the reward design is adequate.
- SFT-based large action models (xLAM, Hammer2.1) "achieve near-zero accuracies despite strong single-call accuracy" on NestFUL's nested/sequential composition, reinforcing that SFT alone does not transfer to multi-step composition — Section 4.4.
- Larger, more diverse tool-use corpora did not beat their compact, composition-focused DepthBench under identical TIER training; xLAM's released trajectories frequently mismatch declared tool schemas, which under execution-grounded reward "penalize schema-conformant calls" — Appendix E.5. Relevant caution if this project reuses an existing SFT/tool-use corpus as an RL data source rather than building schema-consistent tool calls.

## Metric / eval choices

- BFCL v3 reported broken out by category: Overall, Non-Live AST, Live, Multiturn, Relevance, Irrelevance — Table 3. TIER: 68.92 overall vs base Qwen3-8B 64.31, vs SFT 61.47, vs ToolRL 37.27.
- DepthBench accuracy reported per composition depth (0–6) plus a population-weighted overall, explicitly to expose collapse points hidden by aggregate accuracy — Section 3.2, Table 1.
- NestFUL scored via Exact Match Accuracy, "the ratio of test cases where all predicted APIs execute correctly and match the ground truth exactly" — Table 4 caption.

## Open questions for our project

- All results are on Qwen3-8B; the paper does not test smaller (e.g., 1–2B) models, so it is unclear whether the reward-hacking dynamics (routing to "safe" tools) and the answer-correctness/structural-reward weight ratio ($5$ vs a $\le 4$ structural budget) transfer to a model as small as LFM2.5-1.2B, which has far less capacity to satisfy all four reward terms simultaneously.
- No quantization or on-device throughput discussion at all — this paper is entirely full-precision, cloud-scale RL training; it says nothing about whether a GRPO-trained checkpoint survives 4-bit GGUF conversion.
- Their multi-step DepthBench setting assumes "exploratory execution is cheap, repeatable, and safe" (Section 7, Limitations) — this project's target tool surface (SQL, MCP, IPC, containers) may not offer free/idempotent re-execution during RL rollouts, so the execution-reward component may need adaptation or sandboxing before reuse.
- The paper's schema/execution/answer reward is a plausible template for this project's "flag rather than assert" signal on malformed tool returns, but TIER's execution-success term is currently binary "did the call run," not "did the model correctly refuse/flag a bad tool result" — would need a fifth component or a redefinition of $R_{\text{exec}}$ to directly train the flag-rate/false-flag-rate targets.
