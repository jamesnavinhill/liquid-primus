# 2510.23038v2 — Incentivizing Agentic Reasoning in LLM Judges via Tool-Integrated Reinforcement Learning

**Relevance:** medium
Offers transferable RL reward-design patterns for the GRPO-with-verifiable-rewards rung of our ladder (multiplicative correctness×format×tool reward, tool-call budgets, output masking), but the paper trains LLM *judges* (4B/8B Qwen3 backbones) to score/rank other models' responses via code execution — not a policy model doing tool calls/structured output itself, so nothing here speaks to BFCL, quantization, throughput, or vocab-size questions.

## TL;DR

The paper (TIR-Judge) trains Qwen3-4B/8B judge models with DAPO (a GRPO variant) to interleave natural-language reasoning with Python code execution when scoring/ranking candidate responses, using a composite reward of correctness, output-format compliance, and tool-use quality. It shows RL is what unlocks reliable tool use (naive tool access without RL barely helps or hurts), and that an iterative "RL → rejection-sample → SFT → RL again" loop (TIR-Judge-Zero) can match a distillation-based variant without any teacher trajectories.

## Techniques to try

- Composite multiplicative reward gating format/tool correctness on task correctness: "The final reward $R$ is defined as a combination of correctness, format, and tool-specific rewards and assigns full credit only when correctness, format, and tool-use are all satisfied" (Eq. 4, $R=R_c\times(0.1+0.9\,\mathbb{I}[R_t=1\land R_f=1])$) — Section 4.2. Directly applicable pattern for our own GRPO reward combining schema validity and execution correctness.
- Hard cap on tool calls per trajectory with an error-free requirement for reward: "We set the max number of tool calls per trajectory to 3, and set $R_{t}=1$ only when code blocks $c_{i}$ are error-free and within the call budget; otherwise $R_{t}=0$." — Section 4.2.
- Masking tool/interpreter output tokens during the loss to avoid the model memorizing literal execution strings rather than learning to reason from them: "Since execution results $o_{i}=\mathcal{I}(c_{i})$ may cause the model to overfit by memorizing outputs, we mask $o_{i}$ during loss computation... This prevents reliance on exact strings and improves training stability." — Section 4.2 (used in both RL and the SFT cold-start).
- Truncating interpreter error messages to just the final line to control context length while keeping the signal: "We truncate the outputs from Interpreter $\mathcal{I}$ to only the final error line to avoid excessive context length while preserving useful feedback" — Section 4.2.
- Iterative bootstrap loop (RL → rejection-sample retaining only correct/well-formed/error-free trajectories → SFT → RL again) as a no-teacher alternative to distillation: "This iterative process allows TIR-Judge-Zero to progressively bootstrap stronger reasoning and tool-use capabilities entirely from a initial model and facilitates self-improvement without distillation." — Section 4.3.

## Baselines & datasets used

- Training corpus: ~26k preference pairs (12,450 pointwise / 12,450 pairwise / 1,461 listwise) mixed from HelpSteer3, UltraInteract, S1, CodeRM, Tulu-3, Safe-RLHF, MATH, DAPO-Math, WebInstruct, Loong (Table 6, Appendix C) — none of these are tool-schema or agent-gateway datasets, all are general judge-training preference data.
- Backbones: Qwen3-8B and Qwen3-4B-Instruct-2507, both larger than our 1.2B target; trained with DAPO (an improved GRPO variant) via Verl-Tool, on 8×H100-80G.
- Evaluated on judge benchmarks (PPE Correctness, IFBench, CodeJudgeBench, RewardBench, RM-Bench, JudgeBench, RewardBench2) — these measure judging accuracy, not the model's own instruction-following or tool-calling ability, so scores are not comparable to our BFCL/IFEval/IFBench targets even though benchmark names overlap.

## Pitfalls / negative results

- Tool access alone, without RL training, does not help and can hurt: "Simply augmenting Qwen-3 models with code execution yields negligible (<1%) or even negative gains. ... RL is essential for unlocking tool-use capability." — Section 5.2. Relevant caution for us: giving the base LFM2.5 model tool schemas/prompting alone is unlikely to produce reliable structured tool use without a training signal.
- Larger/frontier models can regress when given tools due to run-on tool use: "Sometimes we observe that the performance of Gemini-2.5-flash declines when additional tools are introduced. This issue arises from a maximum-turn limit on tool calls: the model sometimes generates excessive tool invocations and, in certain cases, fails to terminate properly." — Appendix B. A concrete failure mode (excessive/non-terminating tool calls) worth designing guardrails against.
- Rejection-sampling fine-tuning alone (without the online RL step) gives only modest gains: "rejection-sampling fine-tuning yields modest gains, highlighting the necessity of online RL." — Section 5.3. Suggests SFT-only on self-generated correct trajectories is not a substitute for GRPO/RL in this setting.
- Training-task diversity matters: "Training exclusively on chat or reasoning tasks leads to poor transfer across subtasks, largely because the scarcity of tool-use prompts prevents the model from fully developing tool-use capabilities." — Section 5.3.

## Metric / eval choices

- Pointwise scoring gives partial credit (0.5) for ties rather than forcing a binary judgment (Appendix D) — a scoring nuance if we ever need partial-credit grading, though not directly our schema-validity/flag-rate metrics.
- Error-rate breakdown by category (Syntax / Runtime / Format) reported as a simple percentage table (Table 3) — a lightweight template we could reuse for reporting malformed-tool-call failure modes, though their categories are about code-execution errors, not JSON/tool-schema errors.

## Open questions for our project

- The paper masks tool/interpreter output tokens during loss to stop memorization of exact strings — but our target behavior requires the model to actually read and judge tool *return content* to decide whether to flag it as malformed. It's unclear whether masking would help or actively hurt training the "flag rather than assert" behavior; this technique may not transfer as-is.
- All results are at 4B/8B scale; there's no evidence in this paper on whether iterative RL bootstrapping (or RL over tool-use at all) still works at our much smaller 1.2B scale.
- No quantization, throughput, or on-device deployment discussion at all — irrelevant to our 4-bit GGUF and 5% throughput-floor targets.
