# 2505.04016v1 — SLOT: Structuring the Output of Large Language Models

**Relevance:** medium
Gives concrete LoRA-SFT hyperparameters and schema-accuracy lift numbers at 1B–7B scale for JSON structured output, but its architecture (a separate lightweight formatter model post-processing another LLM's free text) doesn't match the project's single on-device model design, and its best results lean on constrained decoding, which the project's schema-validity metric explicitly excludes.

## TL;DR

SLOT is a second, small model (Llama-3.2-1B/3B or Mistral-7B) that is LoRA-SFT'd to take another LLM's unstructured text output plus a JSON schema and rewrite it into schema-valid JSON, decoupled from the original model and task. LoRA SFT alone (no constrained decoding) takes Llama-3.2-1B from 9.6% to 88.9% average schema accuracy across five benchmarks, and stacking SFT with grammar-constrained decoding pushes Mistral-7B to 99.5% schema accuracy / 94.0% content similarity, beating Claude-3.5-Sonnet prompting (74.7%/73.9%).

## Techniques to try

- LoRA SFT hyperparameters for teaching schema-following at small scale: "Rank (r) | 32", "Alpha | 64", "Dropout | 0.05", learning rate 1e-5, 2 training epochs, per-device batch size 2, gradient accumulation 2, context length 16,384 (Table 4, Appx E.1) — a concrete starting point for a 1.2B model's structured-output SFT run.
- "combining SLOT with constrained decoding creates a powerful synergy... SFT teaches the model to inherently produce well-structured and semantically appropriate outputs, while constrained decoding provides a complementary guarantee of structural validity" (§6.2) — relevant if the project ever allows CD at inference, though the pre-registered first-attempt schema-validity metric here explicitly forbids it.
- Two-stage synthetic data validation: stage 1 checks the schema/output pair is parsable and type-consistent; stage 2 uses an LLM validator to check "each structured output field's content is reasonably inferable from the source text" (§4) — a pattern for building malformed/well-formed tool-return probes without hand-labeling everything.

## Baselines & datasets used

- Five text-to-JSON test benchmarks: WebNLG, E2E NLG, WikiBio, ToTTo, and a self-curated "HF GitHub Issues" set (1,000 real GitHub issues with nested/technical structure) explicitly built to be the hardest, most realistic benchmark of the five.
- 126K synthetic SFT training examples generated with Claude-3.5-Sonnet, sampled across industry vertical, JSON complexity, text length, genre, and text type dimensions (§4, Appx D.2).
- Model scales tested: Llama-3.2-1B, Llama-3.2-3B, Mistral-7B-v0.2 (all ≤8B, in-scope for this project), plus proprietary Claude-3.5-Haiku/Sonnet and open Qwen-2.5-14B/32B and Llama-3.3-70B as constrained-decoding baselines (these last three are above the project's scale and not directly transferable).

## Pitfalls / negative results

- Even after SFT, errors concentrate at depth: "errors frequently appeared at deeper nesting levels (beyond 3-4 levels), suggesting that even fine-tuned models struggle to maintain structural coherence across extended hierarchical dependencies" (Appx E.2) — a concrete depth threshold to stress-test in the project's own JSON Schema / tool-call payloads.
- Constrained decoding is not free of semantic cost: "XGrammar sometimes over-constrains the model's generative capabilities when the schema is highly structured, particularly affecting the nuanced language expression in fields with longer texts like descriptions," and Outlines' "regex-based validation, occasionally creates token selection pressures that lead to less fluent text" (Appx E.2).
- Direct prompting on small open models is essentially useless for structured output without training: Llama-3.2-1B/3B and Mistral-7B-v0.2 all score near 0% schema accuracy and content similarity with plain prompting (Table 1) — underscores that the project cannot rely on prompting alone at 1.2B and must actually train.
- Public dataset alone underperforms synthetic-plus-public mixes on content fidelity: for Llama-3.2-1B, "public data alone achieves 63.1% schema accuracy and 68.3% content similarity... [while] the combined dataset demonstrates complementary benefits, achieving 89.0% schema accuracy and 81.7% content similarity" (§6.2) — a data-mix ablation result at the right scale.
- The hardest real-world benchmark (GitHub Issues) still lags well behind the synthetic/simple benchmarks even after SFT (e.g., Llama-3.2-1B SFT: 52.2% schema accuracy on GitHub Issues vs. 97-100% on WebNLG/E2E/WikiBio), which the paper attributes to deep nesting and technical content — a caution against assuming SFT gains generalize uniformly across schema complexity.

## Metric / eval choices

- Schema accuracy: strict match on "key strings and value types" against the target schema, and the output "must be a valid JSON string by itself to be considered correct" (§3) — closely aligned with the project's "first sampled string parses" framing, though this paper measures schema *conformance* rather than just parseability.
- Content similarity: harmonic mean of SBERT-based "soft-precision" and "soft-recall" computed per-value with full key-path matching (including ancestor keys for nested structures), explicitly chosen over edit-distance matching because exact key matching "helps identify cases where values are incorrectly swapped between similar keys" (§3, Appx C.2) — a candidate metric design if the project needs a semantic-fidelity score beyond pass/fail schema validity.
- The paper explicitly avoids LLM-as-judge for structured-output evaluation, noting judges' "non-deterministic nature makes it unsuitable for industrial applications involving LLM agents or function calling" (Appx C.1) — consistent with the project's constraint against reusing a model-scored reward as a training/eval signal.

## Open questions for our project

- SLOT's best numbers come from a two-model pipeline (base LLM + separate fine-tuned formatter), which is architecturally incompatible with this project's single on-device model constraint — none of the paper's top-line results (SFT+XGrammar) transfer directly to a no-CD, single-model, first-attempt setting.
- The paper never touches quantization, throughput, or on-device deployment, so it offers no evidence either way on whether 4-bit quantization would erode the schema-following behavior that SFT instills.
- The paper has no analogue to "flag rather than assert" behavior on malformed tool returns — its task is always well-formed text-to-JSON transformation, not detecting garbage inputs, so it does not help answer that open question.
- No sign of injected instructions directed at the reader was found in the paper text.
