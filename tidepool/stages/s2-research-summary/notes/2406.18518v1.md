# 2406.18518v1 — APIGen: Automated PIpeline for Generating Verifiable and Diverse Function-Calling Datasets

**Relevance:** high
Directly informs the data-generation and data-mix step of this project's SFT candidate: it shows a concrete, verifiable pipeline for building function-calling training data and gives BFCL numbers for 1B–7B models, matching this project's scale and metric family.

## TL;DR

APIGen synthesizes function-calling training data with three LLM-based/executable verification stages (format check, actual execution, semantic check), then fine-tunes DeepSeek-Coder-1.3B and 7B on the resulting 60K-example dataset. The 1.3B model ("xLAM-1B") outperforms GPT-3.5-Turbo and Claude-3 Haiku on the (2024-era) Berkeley Function-Calling Leaderboard, and an ablation shows that skipping the execution/semantic filters and training on the rejected data measurably hurts BFCL accuracy, more so for the smaller model.

## Techniques to try

- Three-stage verifiable data pipeline for tool-call SFT data: "we propose a three-stage verification process: Stage 1: Format Checker... Stage 2: Execution Checker... Stage 3: Semantic Checker" (Section 3.2) — a template for building/curating a technology-stack-specific (SQL/JSON-Schema/MCP) tool-call dataset with pass/fail evidence rather than raw LLM generations.
- Four query-style categories to deliberately cover in the data mix: "simple, multiple, parallel, and parallel multiple" (Section 3.3) — parallel and parallel-multiple calls are explicitly called out as underrepresented in public datasets, which is a concrete gap to check for in whatever tool-call corpus this project builds or reuses.
- Use of a "thought" (chain-of-thought) field before the function call to raise the pass rate of generated/validated data: "We usually also include an additional 'thought' field, which is known as the chain-of-thought (CoT) prompting technique... to increase the pass rate of the generated data" (Section 3.2) — worth testing whether a reasoning-before-call format improves first-attempt schema validity, one of this project's sub-criteria.
- Standardized JSON schema for tools/queries/answers (Fig. 3, Appendix A.2) shared across API sources (REST + Python functions) to keep format-checking and diversity machinery source-agnostic — relevant to specializing on "the underlying technology" rather than one SDK's idiosyncrasies.

## Baselines & datasets used

- Base models fine-tuned: DeepSeek-Coder-1.3B-instruct and DeepSeek-Coder-7B-instruct-v1.5, trained with "the xLAM (large action model) training pipeline" (Section 5.1) — both close to or below this project's 1.2B target scale.
- Benchmark: Berkeley Function-Calling Benchmark/Leaderboard (BFCL), "2,000 testing cases" (Section 5.1), evaluated via AST accuracy and Executable Function Evaluation. Note this is the original BFCL (v1/v2 as of 06/15/2024), not BFCLv3 as targeted by this project's pre-registered claim — numbers are not directly comparable to the ≥52.43 BFCLv3 target without a version check.
- Data source: 3,673 executable APIs across 21 categories, cleaned from ToolBench's 16,464 RapidAPI-Hub REST APIs plus 134 hand-written Python functions (Section 4.1); 60,000 released examples generated from the two strongest generator models (Mixtral-8x22B-Inst and DeepSeek-V2-Chat 236B).
- Reported BFCL numbers at project-relevant scale: xLAM-1B (FC) "74.41" overall accuracy, ranked 24th, "outperforming... Claude-3 Haiku... Command-R-Plus... GPT-3.5-Turbo-0125" (Table 2, Section 5.2); base model DeepSeek-Coder-v1.5 "only ranks 45th... and performs poorly" on parallel/multiple categories before this fine-tuning (Section 5.2).

## Pitfalls / negative results

- Training on data that failed the pipeline's later filters actively hurts accuracy, worse for small models: "adding the datasets that were filtered out by stage 3 (semantic checker) and stage 2 (execution checker) back to the training set... reveals that using these filtered datasets for training harms the final performance, with a more significant impact on the smaller model" (Section 5.2, Fig. 5) — a concrete argument for strict data filtering before SFT on a 1.2B model, and a pitfall to watch for if this project reuses any noisy or self-generated tool-call data.
- Pass rates through the verification pipeline vary hugely by generator model and are low overall: format+execution+semantic pass rate ranges from "34.42%" (DeepSeek-Coder-33B-Inst) to "84.15%" (DeepSeek-V2-Chat 236B) (Table 1) — weaker/smaller generator models produce much more unusable data, a caution if this project considers using its own small model to generate its own training data.
- Scope limitation stated directly by the authors: "the framework and dataset only consider REST APIs and Python functions... APIGen is a general framework, it currently only implements the generation procedure for single-turn function calling" (Section 6) — no multi-turn tool-use data generation, and no coverage of MCP/IPC/container/tracing-style tool schemas this project cares about; would need to be extended.
- Semantic checker is itself an LLM judge scoring "whether the function call aligns with the query's objective," etc. (Section 3.2) — this is a model-scored gate baked into the *data*, not a training-time reward, but it's worth flagging given this project's constraint that "No model-scored stored reward may be reused as a training signal": using an LLM-judge-filtered dataset for SFT is a step removed from that constraint, not a violation of it, but the boundary is worth being explicit about in this project's plan.

## Metric / eval choices

- BFCL's two-part evaluation — Abstract Syntax Tree (AST) accuracy for structural/parameter correctness, plus "Executable Function Evaluation" that actually runs the generated calls (Section 5.1) — is a precedent for pairing a cheap static schema-validity check with an execution-correctness check, aligned with this project's own "schema validity *and* execution correctness" reward components for the GRPO stage.
- The paper reports category-level breakdowns (Simple / Multiple / Parallel / Parallel Multiple, plus Relevance Detection) rather than only an overall score (Table 2) — useful precedent for decomposing BFCL results by query style rather than reporting a single aggregate, especially since parallel/multiple categories are shown to be where small-model gains concentrate.

## Open questions for our project

- Does this project's technology-stack-specific tool schema (SQL dialects, JSON Schema, MCP, IPC, containers, tracing) map cleanly onto APIGen's REST/Python-function JSON format, or does the multi-turn, stateful nature of an agent-gateway conversation (this project's actual prediction unit) require an extension beyond APIGen's stated single-turn-only scope?
- The paper's BFCL numbers predate BFCLv3 and the "flag rather than assert on malformed tool return" sub-criteria central to this project — APIGen's pipeline verifies that *correct* calls execute correctly, but does not appear to generate or verify negative/malformed-tool-return examples at all, so it offers no direct evidence on the 0.80 flag-rate / 0.10 false-flag-rate targets.
- No paper text was found that reads as an instruction addressed to the reader; the document is a standard paper body and appendix.
