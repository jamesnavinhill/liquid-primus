# 2505.18231v2 — NSNQuant: A Double Normalization Approach for Calibration-Free Low-Bit Vector Quantization of KV Cache

**Relevance:** low
This paper quantizes the KV cache (activations) at inference time on 7–13B LLMs using a custom CUDA VQ kernel, which is a different quantization target and mechanism than the project's 4-bit GGUF weight quantization of a 1.2B model, and it is not evaluated on tool-calling/structured-output tasks.

## TL;DR

NSNQuant is a calibration-free vector-quantization scheme for the KV cache that normalizes-shifts-normalizes each token's key/value vector plus a Hadamard transform to match it to a standard normal distribution, then quantizes with a single reusable codebook, giving better out-of-distribution robustness than the prior calibration-based method (CQ) at 1-bit and 2-bit KV cache precision. It targets long-context throughput/memory on 7–13B models (A100 GPU) via a custom CUDA kernel, not weight quantization for GGUF/llama.cpp deployment, so it doesn't transfer directly to this project's shipping format.

## Techniques to try

- None directly applicable: the method quantizes KV cache activations via a bespoke CUDA kernel and codebook lookup, not model weights, so it has no obvious path into a GGUF export pipeline ("NSNQuant costs only additional 0.23 bits on average for the NSN process" — Section 3.5, Double quantization).

## Baselines & datasets used

- Evaluated on LLaMA2-7B/13B, LLaMA3-8B, LLaMA3.1-8B, and Mistral-7B-v0.3 (all ≤13B, none at the project's 1.2B scale) on WikiText-2/C4 perplexity, LongBench, GSM8K, HumanEval, CoQA, MMLU, and AIME-2024 ("we compare NSNQuant against four baselines: KIVI (liu2024kivi), KIVI + Hadamard, KVQuant (hooper2024kvquant), and CQ (zhang2024kv)" — Section 4.1).
- None of the eval tasks are tool-calling, JSON/schema validity, or agentic benchmarks (BFCL, IFEval, etc. are not used).

## Pitfalls / negative results

- At aggressive 1-bit KV cache quantization, task degradation is uneven across capability types on LLaMA3.1-8B-Instruct: GSM8K drops from 76.65 to 53.45 and HumanEval from 57.93 to 44.51 under NSNQuant-1b, while CoQA barely moves (63.78 → 62.70) and MMLU degrades less than GSM8K/HumanEval (Table 4) — weak but suggestive evidence that reasoning/code-structured generation is more fragile under low-bit compression than general knowledge/QA, echoing this project's question about whether quantization disproportionately damages structured output.
- The prior calibration-based method (CQ) "fails to generalize in out-of-distribution (OOD) scenarios where the input distribution is different from that of the calibration set," with perplexity on C4 for LLaMA3-8B degrading to 13.97 vs. NSNQuant's 9.08 at 2-bit — a caution against relying on small calibration sets for any quantization scheme without checking OOD robustness, though this is about KV cache not weights.
- The authors' own limitation: "we find that it does not work well in the early layers due to outlier channels with huge variances" and "NSNQuant does not consider inter-channel correlations or dependencies, while CQ induces errors by relying too much on them" (Appendix I.1).

## Metric / eval choices

- Uses perplexity (WikiText-2, C4) as a fast proxy for quantization quality, cross-checked against downstream task accuracy, and additionally reports "the ROUGE-L score with the FP16 output to measure how well each method preserves the original model output" for noisy-metric tasks like code completion (Section 4.3) — a reasonable pattern (comparing against the FP16 model's own outputs, not just ground truth) that could be adapted for judging 4-bit GGUF fidelity on structured outputs.

## Open questions for our project

- No content in this paper reads as an instruction directed at the reader; it is a standard research paper description.
- The paper offers no guidance on weight-only PTQ/QAT formats (e.g., GGUF Q4_K_M), so it cannot inform the "4-bit GGUF under 1.5GB, ≥97% retention" target directly; if the project's deployment also needs long-context KV cache compression on the RTX 2080 Super, this line of work (and its CUDA kernel requirement) would need separate evaluation for compatibility with llama.cpp/GGUF inference stacks, which is unclear from this paper.
