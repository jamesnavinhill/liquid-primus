# 2602.21265v2 — ToolMATH: A Diagnostic Benchmark for Long-Horizon Tool Use under Systematic Tool-Catalog Constraints

**Relevance:** low
Real topical overlap (tool-use evaluation, tool-selection failure taxonomy) but the benchmark, metrics, and evaluated models (GPT-5, Claude-4.6, Gemini-3.1-Pro, GPT-4o-mini, Llama3-8B, Qwen2.5-7B) target a different problem — distractor-tool robustness in a math-grounded multi-tool catalog — not the single-turn schema-validity, malformed-tool-return-flagging, or quantization questions this project is deciding.

## TL;DR

ToolMATH is a new NeurIPS benchmark (~7.7k questions, ~12k tools derived from MATH solutions) that tests whether models pick the right tool and chain tool calls correctly when the tool catalog is diluted with similar "distractor" tools or when the intended (gold) tools are removed entirely. It introduces diagnostic metrics (Adaptability, Robustness, Tool Connectivity, behavior-conditioned Tool-Acc/NoTool-Acc) and a failure taxonomy, but does not train or fine-tune any model, does not touch quantization, and evaluates only ≥7B models plus frontier proprietary ones — nothing at the ~1.2B scale this project targets.

## Baselines & datasets used

- Benchmark built from the MATH dataset (Hendrycks et al., 2021), via HF distribution `qwedsacf/competition_math`: "ToolMATH is derived from the Mathematics Aptitude Test of Heuristics (MATH) dataset" — Appendix L.
- Models evaluated: "GPT-5, Claude-4.6, Gemini-3.1-Pro, GPT-4o-mini, Llama 3-8B(Grattafiori et al., 2024), and Qwen 2.5-7B(Yang et al., 2024a)" — Section 4.2. The smallest open models are 7-8B; no sub-2B or on-device models are evaluated, so none of these numbers carry over to a 1.2B target.
- Tool-use protocols compared: ReAct-only, Plan+ReAct (main), and DFSDT (decision-tree search) — Appendix H.

## Pitfalls / negative results

- Weaker/older models call tools far more often but far less correctly under catalog noise: "Llama3-8B is the clearest example: it calls tools in over 90% of Distractors-only instances, yet its Tool-Acc remains below 10%." — Section 5.1. This is a cautionary data point (at 8B, not 1.2B) that raw tool-call rate is a poor reliability proxy and that models can fail to calibrate whether to call a tool at all when the catalog is unreliable — a consideration worth keeping in mind when designing this project's malformed-tool-return flag-rate probe, even though the failure mode tested (distractor tool selection) differs from the target failure mode (recognizing a garbage tool *return*).
- "Accuracy decreases with logical-hop count even when gold tools are available, indicating that tool availability alone does not ensure successful long-horizon execution." — Section 5, "Gold-present difficulty trends." I.e., having the right tool present doesn't guarantee correct multi-step chaining; this is a long-horizon-agent finding, of limited relevance to this project's single-agent-turn prediction unit.
- Framework/controller choice matters more as task difficulty (hop count) increases: "controller differences are modest at low hops but become clearer at higher hops, where explicit planning more consistently preserves accuracy" — Section 5.6. Not applicable to this project's single-turn structured-output setting (no multi-turn planner/solver split is in scope).

## Metric / eval choices

- Failure taxonomy used for human trace annotation includes categories that resemble ones this project cares about: "Tool Hallucination ($e_{3}$): At least one call references a tool name that does not exist in the provided tool list," "Wrong Parameter Value ($e_{4}$): ... schema-valid argument types but incorrect/irrelevant values," and "Formatting Error ($e_{5}$): At least one call violates the input schema or fails JSON conversion" — Table 3 (Appendix J). These category definitions could be reused as inspiration for structuring an error taxonomy on this project's own held-out malformed-tool-return probe, even though ToolMATH's numbers were not measured on anything close to a 1.2B model.
- Behavior-conditioned metrics (Tool-call rate, Tool-Acc, NoTool-Acc) separate "whether a model succeeds by using tools or by answering independently" (Section 4.4) — a useful conceptual template for distinguishing "flags correctly" from "just refuses everything," analogous to this project's flag-rate/false-flag-rate pairing, but the paper's own instantiation is tool-selection accuracy, not malformed-input detection.

## Open questions for our project

- None of ToolMATH's reported numbers are measured at ≤8B in a way transferable to a 1.2B model at 4-bit precision; the paper offers no evidence either way on this project's central question of whether quantization degrades structured-output/instruction-following more than knowledge.
- The paper's "Distractors-only" and "Adaptability" framing (recovering when the intended tool is missing) is conceptually adjacent to, but not the same as, this project's "flag rather than assert" requirement (recognizing a malformed *tool result*, not a missing *tool*) — worth noting as a near-miss so it isn't mistaken for supporting evidence.
- No instruction embedded in the paper directed at the reader was found; the paper describes its benchmark and results only.
