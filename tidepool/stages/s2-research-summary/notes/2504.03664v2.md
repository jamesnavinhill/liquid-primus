# 2504.03664v2 — PIPO: Pipelined Offloading for Efficient Inference on Consumer Devices

**Relevance:** skip
PIPO solves GPU-memory-insufficiency via CPU/disk offloading pipelines for 7B–70B+ (and MoE) models that do not fit in consumer GPU memory; this project's target is a ~1.2B model shipped as a 4-bit GGUF under 1.5 GB, which fits entirely and comfortably inside the reference 8 GB GPU with no offloading required at all.

## TL;DR

PIPO is an inference framework for running LLMs too large for a single consumer GPU by pipelining weight/KV-cache transfers across GPU/CPU/disk memory tiers, reporting up to 3.1x throughput over FlexGen on models from 1.3B to 70B (and MoE models up to DeepSeek-R1 671B) on GPUs with 6–24 GB VRAM. None of this is applicable to a project whose whole model plus KV-cache is expected to sit natively in GPU memory.

## Baselines & datasets used

- Baseline is FlexGen ("FlexGen has achieved state-of-the-art performance flexgen in offloading inference. Hence, we choose FlexGen as baseline." — Section 4.1) — a large-model offloading system, not relevant as a baseline for a sub-2B on-device deployment.
- Models evaluated: OPT (6.7B, 13B, 30B, 66B), LLaMA3.1 (8B, 70B), Mixtral 8x7B, DeepSeek-R1 671B — all well above this project's 1.2B scale.

## Pitfalls / negative results

- The paper itself notes PIPO's pipeline "incurs certain memory overhead" from preloading two layers' weights/cache simultaneously, and that "the memory demand is significantly higher during the prefill stage," requiring a separate memory-efficient pipeline mode as a tradeoff ("Section 3.2.3 Performance-Memory Tradeoff"). This is a pitfall specific to offloading multi-GB models, not to a model that already fits on-device.
- Compared to a non-offload implementation, "PIPO can reduce VRAM usage by 66.4% with only 11.2% performance degradation" (Section 4.2) — i.e., even PIPO's best case still costs ~11% throughput versus no offloading at all, reinforcing that offloading should be avoided entirely when avoidable, as it is in this project.

## Metric / eval choices

- Throughput (tokens/s), GPU utilization %, disk-to-GPU transfer speed, time-to-first-token (TTFT), and VRAM/DRAM footprint are the paper's metrics — standard systems-level inference metrics, but measured in an offloading regime this project does not enter.

## Open questions for our project

- None raised directly by this paper's content that bear on structured-output quality, quantization damage to instruction-following, or training signals — the paper is a pure inference-systems paper with no training, fine-tuning, or evaluation of task/tool-calling accuracy.
- One tangential note for the throughput target: the paper's "Computation Optimization" section describes custom handwritten INT4 matrix-vector kernels that "perform matrix-vector multiplication directly on 4-bit quantized weights, avoiding the dequantization operation" (Section 3.4) to cut latency at small batch sizes — a generic technique already standard in llama.cpp/GGUF-style inference stacks, so not a new idea for this project's throughput-floor requirement, just a confirmation that avoiding dequantization matters for INT4 decode speed.
