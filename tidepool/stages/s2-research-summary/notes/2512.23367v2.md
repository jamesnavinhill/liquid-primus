# 2512.23367v2 — Post-Training Quantization of OpenPangu Models for Efficient Deployment on Atlas A2

**Relevance:** medium
Useful as a comparable data point on PTQ degradation magnitude and mitigation (SmoothQuant, Hadamard rotation) at 1B/7B scale, plus a striking repetitive-generation failure mode at 1B, but it targets Huawei Ascend NPU weight-activation quantization (INT8/W4A8 via CATLASS) rather than the weight-only 4-bit GGUF path on a consumer GPU this project needs, and it evaluates only code generation, not tool-calling or structured output.

## TL;DR

The paper quantizes Huawei's openPangu-Embedded 1B/7B models to INT8 (W8A8) and W4A8 for Ascend Atlas A2 NPUs, testing HumanEval/MBPP across three CoT modes. INT8 keeps accuracy essentially at FP16 with a 1.5x prefill speedup, but naive W4A8 causes a real accuracy drop that SmoothQuant and Hadamard rotation partially recover; separately, the 1B model shows a "repetitive generation" degeneracy that quantization actually reduces rather than worsens.

## Techniques to try

- SmoothQuant-style activation/weight rebalancing before quantization: "adopts SmoothQuant (Xiao et al., 2024), which balances the quantization difficulty between activations and weights using a diagonal scaling ${S}=\text{diag}({s})$" — Section 3.2.
- Hadamard rotation to smooth outlier channels before low-bit quantization: "employs Hadamard rotation (Ashkboos et al., 2024; Liu et al., 2024b), which applies an orthogonal transform to the weight matrix before quantization... This rotation preserves the mathematical equivalence in full precision while promoting a more uniform weight distribution, which is better suited for low-bit quantization." — Section 3.2.
- Track "repetitive generation" (terminal output degenerating into repeated identical phrases) as a specific quantization failure signature worth monitoring in our own 4-bit evals, since it strongly predicts task failure: "repetitive generation strongly correlates with functional failure: non-repetitive samples achieve an average accuracy of 87.39%, while repetitive samples achieve only 18.24%." — Section 4.4.

## Baselines & datasets used

- HumanEval (Chen et al., 2021) and MBPP (Austin et al., 2021) code generation benchmarks, evaluated across the model's three built-in CoT modes (slow_think, auto_think, no_think).
- FP16 as the reference precision; INT8 (W8A8) and three W4A8 variants (baseline, +SmoothQuant, +Hadamard) as the quantized comparisons — all PTQ, no retraining: "We apply quantization without retraining, using calibrated scales derived from downstream task data." — Section 4.1.

## Pitfalls / negative results

- Naive 4-bit weight quantization (W4A8) causes a real, non-trivial accuracy drop even at 7B: on the no_think mode, HumanEval fell 85.37 → 81.10 and MBPP fell 77.04 → 70.04 for baseline W4A8 (7B model), i.e. roughly 8-9% relative degradation on MBPP even at 7B — worse than the ≥97%-retention bar this project needs, though SmoothQuant/Hadamard closed some of the gap (MBPP 70.04 → 75.10/75.49). "Due to the use of a lower 4-bit weight for weights, the accuracy of W4A8 has dropped significantly." — Section 4.2.
- The 1B model (closest in scale to our 1.2B target) is quite prone to a degenerate repetition failure mode even at full precision, not caused by quantization: "The 1B model exhibits high susceptibility to repetitive outputs under FP16 (34.15%), which is substantially reduced to 21.95% under INT8 quantization." — Section 4.4. This is a caution that a hybrid small model may already show output-collapse behavior pre-quantization, which for a tool-calling model could show up as malformed/repeated tool-call text — worth checking for in our own 1.2B baseline before blaming quantization for any schema-validity drop.
- Their own related-work section flags that quantization-vs-reasoning studies (including this one) are narrow: "these analyses are primarily focused on general benchmarks and NVIDIA platforms, with limited attention given to structured reasoning modes like slow_think or auto_think on specialized hardware" — Section 5. None of this paper's evaluation touches instruction-following, tool calling, or JSON/schema validity, so it cannot directly answer this project's core question about whether quantization hurts structured output more than knowledge.

## Metric / eval choices

- Accuracy retention framed as "% of FP16 baseline preserved" (e.g., "INT8 quantization consistently preserves over 90% of the FP16 baseline accuracy") rather than absolute point deltas — the same framing this project uses for its 97%-retention / 93%-floor targets, so the retention-percentage convention itself transfers even though the benchmark (code gen) does not.
- Repetitive-generation rate defined mechanically as "terminal output segments containing identical phrases repeated until sequence termination" (Figure 5 caption) — a cheap, automatable degeneration check that could be adapted as a guardrail probe alongside this project's malformed-tool-return flagging.
- Efficiency reported as prefill latency and memory across batch sizes 2-32 on Ascend hardware (Table 3); no decode-throughput numbers are given, so the paper offers nothing directly comparable to this project's "4-bit decode throughput within 5% of base" target.

## Open questions for our project

- Does the SmoothQuant/Hadamard recovery seen here for W4A8 code-gen accuracy generalize to weight-only INT4 GGUF quantization (a different scheme, no activation quantization) and to structured-output/tool-call metrics rather than pass@1 code accuracy?
- If a 1B-scale model shows ~34% repetitive-output rate at full precision on code generation, should the reader-brief's malformed-tool-return probe also check whether *first-attempt* schema failures at 1.2B are driven by this kind of degenerate repetition rather than genuine schema misunderstanding?
- The paper's hardware/toolchain (Ascend Atlas A2, CATLASS operator library) has no bearing on our llama.cpp/GGUF, RTX 2080 Super deployment target — flagging this as a non-transferable dependency rather than assuming any of the reported speedup/memory numbers carry over.
