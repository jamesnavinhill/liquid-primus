# 2510.06126v1 — lm-Meter: Unveiling Runtime Inference Latency for On-Device Language Models

**Relevance:** low
Real topical overlap (on-device LLM latency, quantization's effect on accuracy-latency trade-offs) but the artifact is a mobile-GPU (OpenCL/Vulkan on Android, MLC/TVM stack) profiling tool with benchmarks on ARC/HellaSwag/GSM8K knowledge tasks, not a method or number that transfers to a desktop-GPU llama.cpp/GGUF tool-calling deployment.

## TL;DR

The paper introduces lm-Meter, an online phase- and kernel-level latency profiler for LLMs running on Android phones (via MLC/TVM/OpenCL), and uses it to show that prefill (not decode) is the dominant latency bottleneck on mobile hardware and that 4-bit quantization's accuracy-latency benefit is highly task- and architecture-dependent. None of this is about structured output or tool calling, and the hardware/software stack (mobile SoC, OpenCL kernels) doesn't match this project's target (RTX 2080 Super, llama.cpp-style GGUF inference).

## Techniques to try

- None directly transferable — the profiler instruments native OpenCL/Vulkan/Metal kernel callbacks and MLC/TVM codegen, which is orthogonal to this project's training/quantization pipeline for a CUDA-class desktop GPU deployment.

## Baselines & datasets used

- Accuracy tasks: ARC-Easy, ARC-Challenge, HellaSwag, GSM8K, evaluated with lm-evaluation-harness on KL-divergence-sampled subsets (10% of ARC/GSM8K, 1% of HellaSwag) rather than full benchmarks, to keep on-device eval tractable.
- Model suites profiled: Pythia (70M–1.4B), SmolLM2 (135M–1.7B), Qwen1.5 (up to 1.8B), plus a 4-bit quantized Gemma-2-2B-it for the kernel-level case study — all far below the 1.2B target but on a completely different task distribution (general knowledge/reasoning, not tool calling/JSON).

## Pitfalls / negative results

- 4-bit quantization can produce catastrophic, task-specific collapse rather than uniform degradation: "One anomalous case is SmoLM2-1.7B on GSM8K, whose $\mathcal{HQ}$ collapses due to near-zero accuracy reported by the lm-evaluation-harness. We have evaluated three different 4-bit quantization schemes for this model, all yielding similarly poor accuracy." (§5.1, Quantization impact on accuracy-latency trade-offs) — a concrete example that low-bit quantization can wreck a narrow numerically/structurally sensitive capability while leaving broad accuracy intact, echoing this project's worry about quantization disproportionately hurting structured output vs. knowledge, though here the sensitive capability is multi-step arithmetic, not JSON/tool-call formatting.
- "quantization is not universally beneficial for on-device LLMs. The choice between quantized and full-precision models should jointly consider model size, task type, and hardware constraints." (§5.1, Implication 5) — a caution against assuming a single quantization recipe generalizes across task types, relevant to validating the 4-bit GGUF build across all guardrail axes rather than just BFCL/aggregate score.
- On mobile/edge hardware, prefill — not decode — is the dominant bottleneck ("the average prefill latency per input token across four tasks increases dramatically from 0.012 s/token to 1.9 s/token, a 158× slowdown" scaling Pythia 70M→1.4B, vs. only 10× for decode), the opposite of server-GPU trends; this is a hardware-stack-specific finding (mobile SoC, batch size 1, OpenCL) that likely does not hold for a discrete desktop GPU like the RTX 2080 Super, so it should not be assumed to transfer to this project's throughput-floor requirement.

## Metric / eval choices

- Harmonic Quantization score $\mathcal{HQ}$: harmonic mean of (normalized accuracy ratio, prefill-latency ratio, decode-latency ratio) between quantized and full-precision models, designed so severe degradation in any single component dominates the score — a reusable idea for scoring "does quantization hurt any one axis a lot" rather than only average performance, conceptually similar to this project's "no single axis below 93%" 4-bit retention requirement, though the paper's version blends accuracy and latency into one number rather than tracking axes separately.

## Open questions for our project

- The paper's GSM8K collapse case under 4-bit quantization suggests we should specifically stress-test the 4-bit GGUF build on structured/schema-sensitive outputs (not just aggregate BFCL/IFEval), since this paper shows quantization degradation can be concentrated in one narrow capability while overall/average metrics look fine.
- No instruction in the paper was addressed to the reader as a directive; it is a systems/measurement paper and was treated as descriptive data only.
