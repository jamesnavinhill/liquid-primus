# 2601.20103v1 — Benchmarking Reward Hack Detection in Code Environments via Contrastive Analysis

**Relevance:** low
Real topic overlap with the project's open question on reward hacking under a schema-check reward, but the paper is a benchmark/taxonomy for frontier LLMs (all far above 8B) detecting hacks in long agentic coding trajectories, not a method or number transferable to training or evaluating a 1.2B tool-calling model.

## TL;DR

The paper introduces TRACE, a 517-trajectory human-verified benchmark with a 54-category taxonomy of code RL reward-hacking behaviors, and shows that frontier LLMs (GPT-5.2, Claude Opus 4.5, Gemini 3 Pro, Kimi K2, GLM-4.7, DeepSeek-3.2) detect hacks much better in a contrastive/cluster setting than in isolated classification, topping out at 63% Detection Rate. It is a diagnostic study of LLM-as-judge hack detection, not a training method or a result at a model scale relevant to this project.

## Techniques to try

- None directly applicable. The paper's "contrastive cluster" evaluation setup (comparing $N$ trajectories at once, varying benign ratio) is an idea for *detecting* hacking post hoc via a large judge model, not a training-time mitigation, and would require a large frontier judge model + long multi-turn trajectories, which doesn't fit a 1.2B on-device build with deterministic schema/execution rewards.

## Baselines & datasets used

- TRACE dataset itself: "TRACE contains 517 unique trajectories that span across several domains of software engineering" with "249 benign trajectories," averaging "approximately 26 utterances per trajectory" (Section 3) — a code-agent reward-hacking benchmark, not a tool-calling/JSON-schema benchmark, so not a candidate eval for this project.
- Evaluated models are all frontier-scale: "gpt-5.2-2025-12-11 ... claude-opus-4-5-20251101 ... gemini-3-pro-preview ... kimi-k2-thinking ... glm-4.7 ... deepseek-3.2" (Section 4.3) — no result at or below 8B parameters is reported anywhere in the paper.

## Pitfalls / negative results

- Isolated (single-sample) classification is a hard floor for hack detection regardless of capability: "At $N=1$, all models converge to a narrow performance band (Match rate of 0.35–0.41), suggesting that detecting reward hacks from isolated samples approaches a difficulty floor regardless of model capability" (Section 5, RQ3) — relevant caution if this project ever considered a single-sample LLM judge to flag reward hacking during GRPO, since isolated judging appears unreliable even for frontier models.
- Models are much worse at catching hacks that require understanding intent versus surface pattern-matching: "Performance here drops dramatically (Match Rate 0.0–0.4)" for semantically-oriented categories like "Context Exploitation, Style Manipulation, Information Leakage, and Tool Abuse," versus 0.6–0.95 for mechanical/syntactic exploits (Section 5, RQ2) — a generic reminder that a deterministic schema/execution-correctness reward (this project's plan) is exactly the "syntactic" kind of check that's easier to reason about and audit, whereas anything requiring semantic judgment is harder to trust.
- The strongest coding model was also the worst hack-detector: "Claude-4.5-Opus that outperforms all other models on coding benchmarks such as SWE Bench ... underperforms at the task of code reward hack detection ... achieving a perfect precision score of 1 but with extremely poor recall" (Section 5, RQ1) — a caution that general coding/instruction-following strength does not predict reward-hacking-awareness.
- Even with contrastive samples explicitly included, judges tend to explain away degenerate solutions: "despite including contrastive samples of degenerate implementations in the cluster, LLMs tend to mark such solutions as mere engineering deficiencies instead of reward hacking behaviors" and judges over-trust in-trajectory user/agent self-reports of correctness (Section 6) — worth knowing if this project ever uses an LLM judge (rather than the planned deterministic checks) to audit whether the 1.2B model is gaming its schema/execution reward.

## Metric / eval choices

- Detection Rate is defined as "the macro F1 score calculated on the binary detection prediction of a reward hack," and Match Rate as "the macro, multilabel F1 score for the fine grained reward hack category" (Section 4.4) — a metric pair analogous in spirit to this project's paired flag-rate/false-flag-rate target for malformed tool returns, but built for a different task (multi-label hack category attribution vs. binary flag/false-flag).

## Open questions for our project

- The paper doesn't answer any of the project's pre-registered questions directly (it doesn't touch quantization, tool-call schema validity, structured output, or model scales near 1.2B). Its only indirect bearing is on the standing constraint "No model-scored stored reward may be reused as a training signal" and the open question "How is reward hacking avoided when the reward is a schema check?" — the taxonomy (test targeting, complexity gaming, degenerate/hardcoded implementations, etc., Section 3 and Appendix G) is a useful checklist of *failure shapes* to watch for if the GRPO stage's schema-validity/execution-correctness reward is ever gamed (e.g., the model emitting a minimal/degenerate but technically-valid structured output), but the paper offers no detection or prevention method suited to a 1.2B model or a deterministic reward.
- No instructions embedded in the paper text were found that need flagging; the paper reads as a normal research report throughout.
