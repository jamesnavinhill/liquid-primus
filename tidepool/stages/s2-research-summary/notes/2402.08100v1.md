# 2402.08100v1 — Investigating the Impact of Data Contamination of Large Language Models in Text-to-SQL Translation

**Relevance:** low
Real topical overlap (text-to-SQL, benchmark trustworthiness for a closed/black-box LLM) but the paper studies GPT-3.5 as a black box on the Spider benchmark and offers no training method, quantization insight, or tool-calling/structured-output technique applicable to post-training a 1.2B on-device model.

## TL;DR

The paper shows that GPT-3.5's strong zero-shot Text-to-SQL performance on the Spider benchmark is substantially inflated by data contamination: GPT-3.5 does much better on Spider than on a hand-built, never-published "Termite" dataset of matched difficulty, and it is far more robust to having foreign-key/INSERT information stripped from Spider databases than from Termite ones. For this project it's a reminder to sanity-check that any public SQL/tool benchmark used isn't silently memorized, but it doesn't propose anything to adopt for training or quantizing LFM2.5.

## Baselines & datasets used

- Spider validation split (20 databases, 1,035 NL-SQL pairs, four difficulty tiers EASY/MEDIUM/HARD/EXTRA-HARD) as the "potentially contaminated" benchmark: "This portion of the dataset consists of 20 databases and 1,035 pairs of NL-SQL queries distributed on the four difficulty categories" — Section 3.1.
- Termite, a new hand-crafted, encrypted/never-published Text-to-SQL dataset (10 databases, 202 queries) built to match Spider's size, schema style, and human-judged difficulty, used as the "known-clean" control — Section 3.2.
- Evaluation metric: Test Suite Accuracy (Zhong et al. 2020), which executes model and gold queries against up to 1,000 randomly generated databases per schema rather than a single database, to reduce false positives relative to plain Execution Accuracy — Section 4.2.
- GPT-3.5-turbo tested zero-shot only, via a multi-turn "give dump → get interpretation → ask NL question → get SQL" prompting protocol, to isolate contamination effects from prompt-engineering effects — Section 4.2.

## Pitfalls / negative results

- Benchmark contamination inflates measured capability: "not only does GPT exhibit clear knowledge about Spider, but this also leads to an overestimation of the model's performance in Text-to-SQL tasks in zero-shot scenarios" — Section 1. Relevant caution if this project ever leans on a widely-published, easily-scraped SQL/JSON benchmark to claim capability gains.
- A model that has memorized the benchmark is artificially robust to input degradation: after Adversarial Table Disconnection (removing foreign-key constraints and INSERT rows), GPT-3.5's accuracy on HARD Spider queries barely moved (48.83% → 48.71%) while on HARD Termite queries it dropped meaningfully (28.33% → 22.67%): "the drop observed in the performance of GPT-3.5 after ATD is greater on new data than on contaminated ones" — Section 5.3. This is a useful diagnostic pattern in general (perturb the input structure and see if performance degrades) but the paper only applies it to a 175B-class closed model's schema-interpretation task, not to tool-call/JSON generation or to a small on-device model.
- Findings are explicitly scoped to one closed model family at large scale: "the impact of Data Contamination on the performance of Text-to-SQL tasks has been tested specifically on GPT-3.5... the analysis should be extended to other models," with only "preliminary small-scale pilot experiments" suggesting GPT-4 is similarly affected — Limitations. Nothing here is measured at or near 1.2B parameters, and no quantized setting is considered at all.

## Metric / eval choices

- Test Suite Accuracy (execute-against-many-random-databases) is worth knowing as a more reliable alternative to naive single-database execution-match when scoring generated SQL, if this project ever needs to validate SQL-dialect tool outputs beyond schema-parse checks. Not directly reusable for the project's core BFCLv3/IFEval/tool-schema-validity metrics, which don't involve SQL execution.
- The paper's own contamination-detection metric ("DC-accuracy": ability to reconstruct masked column names from a database dump) is a clever indirect probe for whether a black-box model has seen specific structured artifacts, but it targets schema memorization, not tool-call formatting or instruction-following, so it doesn't transfer to this project's flag-rate/false-flag-rate or schema-validity metrics.
