# 2411.08599v3 — A Preview of XiYan-SQL: A Multi-Generator Ensemble Framework for Text-to-SQL

**Relevance:** medium
Its centerpiece is a multi-model ensemble with a separately fine-tuned selection model — explicitly out of scope for this project — but the M-Schema representation, the curriculum for SQL fine-tuning, and its negative result on small SFT-only models generalizing to new domains are worth carrying into the SQL-dialect specialization work.

## TL;DR

XiYan-SQL is an Alibaba NL2SQL system that ensembles fine-tuned SQL generators, an in-context-learning generator, a refiner, and a separately fine-tuned selection model, plus a new schema-representation format (M-Schema), to hit state-of-the-art execution accuracy on Bird/Spider/SQL-Eval/NL2GQL. For this project the ensemble/selection machinery doesn't transfer (ensembling is out of scope here), but the schema-formatting and curriculum-training ideas are reusable for the SQL-dialect slice of tool-call specialization.

## Techniques to try

- Adopt M-Schema-style formatting when constructing SQL training/eval data: a semi-structured schema block that adds "data type, primary key marking, and column description" plus value examples on top of a MAC-SQL-style layout ("M-Schema adds data types, primary key markings, and changes the rules for displaying sample values." — Sec. 3 / Fig. 2 caption), which beat plain DDL schema by an average of 2.03% EX across four backbone LLMs (Sec. 7.6.1).
- Consider a two-stage curriculum when specializing to SQL dialects: "basic-syntax training" (dialect-agnostic, broad SQL syntax coverage) followed by "generation-enhance training" (semantic understanding + stylistic/dialect diversity, including auxiliary tasks like SQL→question and SQL→evidence) rather than single-stage SFT ("we employ a two-stage and multi-task training approach to fine-tune the model, including basic-syntax training and generation-enhance training." — Sec. 5.1).
- Schema linking (retrieving only relevant tables/columns/values before generation) is worth keeping as a preprocessing step even for a single small model, since it raised column-selection precision from 10.14% to 74.74% and EX by 2.15% with GPT-4o as generator (Sec. 7.6.2, Table 7) — cheap to add regardless of the base model's size.

## Baselines & datasets used

- Spider (SQLite, cross-domain, 1981 questions / 39 DBs) and Bird (SQLite, dev set, 1534 questions / 11 DBs) — standard NL2SQL benchmarks with Execution Accuracy (EX) as the metric.
- SQL-Eval (PostgreSQL, Defog's open-source eval, 304 questions / 11 DBs) — useful as a non-SQLite dialect benchmark if the project needs a Postgres-flavored eval set.
- NL2GQL (nGQL graph query language, 288 questions / 3 DBs) — shows the schema/eval approach extends to non-relational query languages, relevant if the project's "underlying technology" scope ever includes graph queries.
- Compared against SQLCoder-8B (60.20% EX on SQL-Eval) and CodeS-15B (SFT-only, 58.47/60.37% EX dev/test on Bird) as the smaller open fine-tuned baselines; XiYan-SQL itself is built on unspecified (likely much larger) backbones, so its headline EX numbers (75.63% Bird, 89.65% Spider) are not evidence at the project's 1.2B scale.

## Pitfalls / negative results

- Direct warning against small SFT-only models for this exact task: "Approaches based on SFT seek to fine-tune models with much smaller parameter sizes on the NL2SQL task to produce more controllable SQL queries, such as CodeS [9]. Nevertheless, due to their limited parameters, these methods struggle to perform complex NL2SQL reasoning and transfer to databases within a new domain." (Sec. 1). This is a direct caution for a 1.2B target model doing SQL generation on unseen schemas/domains — worth testing explicitly rather than assuming SFT alone will generalize.
- Self-consistency alone is an unreliable selector: "this approach has limitations: it cannot handle situations where none of the queries are consistent, and even the most consistent result is not always the correct case." (Sec. 6) — cautions against relying on majority-vote/self-consistency as a proxy for correctness, relevant if the project ever considers self-consistency as a cheap substitute for a verifier.
- Component ablation on Bird dev shows the fine-tuned generator and the selection model matter most (removing them costs 2.91 and 2.74 EX points respectively), while the refiner adds least (0.55 points) (Table 8) — but this is measured inside a 3-5-candidate ensemble, so the individual-component deltas may not hold for a single non-ensembled model.

## Metric / eval choices

- Execution Accuracy (EX): "EX compares the results of a predicted SQL query and a reference SQL query executed on a specific database instance" (Sec. 7.1) — i.e., a real execution-correctness check rather than string/AST match, consistent with the "execution correctness" reward this project's GRPO stage is considering.
- Schema-linking quality itself is evaluated separately via precision/recall on selected columns against the gold SQL, decoupling retrieval quality from end-to-end EX (Table 7) — a pattern worth reusing if the project builds its own schema/tool-arg retrieval step.

## Open questions for our project

- The paper never states the parameter count of its own fine-tuned SQL generators or selection model (only cites CodeS-15B and SQLCoder-8B as external baselines), so none of its headline numbers are known to hold at 1.2B — the curriculum and M-Schema ideas would need re-validation at this project's scale.
- Given the project's constraint that "Ensembling is out of scope," most of this paper's actual novelty (multi-generator ensemble + a separately fine-tuned selection/verifier model) is not directly usable; only the schema-formatting and curriculum-training sub-ideas are portable to a single-model pipeline.
- No content in this paper reads as an instruction directed at the reader; it is a straightforward technical report.
