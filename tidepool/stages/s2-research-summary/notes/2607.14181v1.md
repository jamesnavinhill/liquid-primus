# 2607.14181v1 — Quantize with Confidence? An Empirical Study of Quantization for Code Generation

**Relevance:** medium
Grounds quantization-technique and 4-bit-GGUF viability with real numbers, and offers a reusable "stratify by prompt complexity" evaluation method, but it measures code-gen pass@1/static-analysis quality on 7B models, not tool-call schema validity or instruction-following on a 1.2B hybrid model.

## TL;DR

The paper compares six 4-bit weight-only PTQ techniques (GPTQ, AWQ, QuIP#, AQLM, BitsAndBytes, GGUF) on Qwen2.5-Coder-7B and CodeLlama-7B for code generation, scoring pass@1 and SonarCloud code-quality metrics, and finds that quantization effects are strongly technique- and model-dependent rather than uniform. For this project it is a useful comparable on "does 4-bit hurt structured/functional output," but it never touches tool-call schemas, JSON validity, or instruction-following — its "structure" is source-code correctness, not the project's target output format.

## Techniques to try

- Stratify quantization evaluation by prompt/input complexity (token length + Shannon entropy) rather than reporting a single averaged pass rate, since aggregate numbers can hide complexity-correlated degradation: "pass@1 averaged over a benchmark conceals systematic, complexity-correlated degradation that emerges only under stratified analysis." (Section VI-B / Implications for Researchers) — directly applicable to stratifying the project's BFCLv3/schema-validity evals by prompt/tool-schema complexity.
- Run a repeated-sampling check (e.g., 10 generations per config) with Friedman's test before attributing score deltas to the quantization technique, to rule out inference-time stochastic noise: "Friedman's test found no significant run-level differences in pass@1 or any SonarCloud metric, indicating that the reported differences reflect technique effects rather than inference noise." (Section IV-E)
- Use McNemar's test for binary pass/fail deltas and Wilcoxon signed-rank + Holm-Bonferroni correction + Cliff's delta for continuous quality-metric deltas, to separate statistical from practical significance when comparing a quantized build against a full-precision baseline. (Section IV-E)
- GGUF (Q4_K_M) is called out as "the practical choice via the llama.cpp ecosystem" for CPU-only / local deployment — relevant since the project's shipped artifact is also a 4-bit GGUF build. (Section VI-A)

## Baselines & datasets used

- Models: Qwen2.5-Coder-7B-Instruct and CodeLlama-7B-Instruct (both 7B, above the project's 1.2B target but within the "≤8B preferred" band).
- Quantization methods compared, all at 4-bit: GPTQ (group size 128), AWQ (default config), QuIP# (Hadamard + E8 lattice codebooks, via QuIP-for-all), AQLM (2 codebooks), BitsAndBytes (NF4 + double quantization), GGUF (Q4_K_M).
- Benchmarks: McEval (Python 42 tasks / Java 53 tasks, short prompts), CoderEval (190 Python / 184 Java tasks, filtered per Crupi et al., mid-length/context-dependent), BigCodeBench (Python only, long/multi-library prompts, used only for RQ3 complexity gradient).
- Quality tool: SonarCloud (bugs/Reliability, code smells/Maintainability, Security, LoC, Cyclomatic Complexity, Cognitive Complexity), justified as sufficient over Pylint/Flake8/PMD based on a cited prior consistency study.

## Pitfalls / negative results

- Quantization technique choice matters far more than "quantization" as a monolithic category: "QuIP# exhibits the largest correctness degradation, particularly on complex prompts" while "AQLM consistently matches or exceeds the full-precision baseline" — the same 4-bit budget produces opposite outcomes depending on algorithm.
- Effects are not just technique-dependent but model-dependent: a technique that helps one model can hurt another on the same benchmark — e.g. "GPTQ improves CodeLlama's McEval pass@1 by 9 percentage points but reduces Qwen's by 13," so results from one model family cannot be assumed to transfer to a different architecture (relevant caution for LFM2.5's non-standard hybrid conv/attention design).
- Quality degradation and correctness degradation don't co-occur predictably: "a technique may preserve quality while losing correctness, or vice versa" (RQ3 discussion) — a build can pass functional tests while quietly accumulating quality/maintainability regressions, or vice versa, so a single pass-rate metric is not sufficient for a "hold the quality bar" claim like this project's.
- Robustness to prompt complexity was itself model-dependent and did not generalize: "For CodeLlama, prompt complexity significantly correlates with degradation for five of six techniques... For Qwen2.5-Coder-7B, almost no significant correlations exist." This is a direct negative result against assuming quantization robustness patterns transfer across model families.
- Scope limits acknowledged by the authors themselves: "Our findings are scoped to 7B models, two languages (Python, Java), three benchmarks, and 4-bit precision. Results may differ at other model scales, bit-widths, languages, or task types" — explicitly flagging that a 1.2B model (this project's target) is out of the tested range.

## Metric / eval choices

- Functional correctness via strict pass@1 (single-attempt, temperature 0), described as "a strict single-attempt measure reflecting realistic deployment" — same spirit as this project's "no retry, no repair" first-attempt schema-validity metric, though applied to unit-test pass/fail rather than parse validity.
- Code quality via five SonarCloud indicators (Reliability, Maintainability, Security, Cyclomatic Complexity, Cognitive Complexity) rather than pass@k alone, explicitly to catch cases where "code that passes test cases may still exhibit excessive complexity or subtle defects."
- Prompt complexity operationalized via two content-agnostic measures, token length and word-level Shannon entropy, with tasks pooled and split at the median into High/Low buckets — a concrete recipe for the project's own question about whether quantization damage scales with input complexity.

## Open questions for our project

- Would a stratify-by-complexity analysis (à la RQ3 here) reveal that this project's schema-validity or flag-rate metrics degrade more on long/complex tool schemas even when the aggregate BFCLv3 number looks fine?
- Given that quantization sensitivity to prompt complexity was highly model-dependent in this paper (CodeLlama sensitive, Qwen not), is there any prior signal on how LFM2.5's hybrid short-convolution + GQA architecture behaves under 4-bit weight-only quantization, or does this need to be measured from scratch?
- None of the paper's text reads as an instruction directed at the reader; it is a standard empirical SE study and was treated purely as reference data.
