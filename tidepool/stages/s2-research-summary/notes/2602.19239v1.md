# 2602.19239v1 — Attention Deficits in Language Models: Causal Explanations for Procedural Hallucinations

**Relevance:** medium
The paper is interpretability research on synthetic long-context binding tasks (2B–9B open-weight models), not on tool-calling, quantization, or fine-tuning, but it gives one concretely testable prompting mitigation (checkpointing) and a stage-decomposition diagnostic that could transfer to diagnosing schema/tool-call failures in long agent turns.

## TL;DR

The paper shows that when models fail to state a value they already computed, the failure is usually not missing knowledge but a "routing" failure at the output stage: the model enters answer mode but binds to the wrong candidate (recency-biased), and a linear probe on the final-layer residual stream can recover the true answer on the majority of these error trials. Restating the critical evidence near the query ("checkpointing") can nearly eliminate this failure mode at long context, but only if the model hasn't also stopped attempting an answer at all (a separate, unrecoverable failure mode).

## Techniques to try

- Restate critical grounding information (e.g., the tool schema, the key constraint, the binding) near the end of a long context rather than relying on the model to retrieve it from far back: "restating the true binding near the query can nearly eliminate Stage 2B failures at long distance (e.g., Qwen2.5-3B 0/400$\to$399/400 at $k=1024$)" — Abstract. Concretely: "Oracle checkpointing inserts a compact serialization of the true binding every 128 tokens in the tail filler" — Table 3 (Section 5.4). This is a zero-training, inference-time/prompt-engineering lever the gateway could use for long multi-turn tool conversations, independent of any fine-tuning decision.
- Decompose structured-output failures into two diagnostic stages rather than treating "wrong output" as one bucket: "Stage 2A failures indicate that the model does not recognize the query as requesting a value from $\mathcal{C}$. This is a format or instruction-following problem" vs. "Stage 2B failures indicate that the model understands the task format but routes to the wrong value. This is an information-routing problem" — Section 3.4. This maps loosely onto "no structured output attempted" vs. "structured output attempted but wrong field/value populated," which could sharpen error analysis on BFCL/schema-validity failures.
- Use logit-margin diagnostics (GateGap, ValueGap) computed purely from next-token logprobs to classify failure type without needing activations: defined in Section 3.2–3.3. This is API-compatible (works even without weight access) and could be adapted as a lightweight eval-time diagnostic for tool-call generation.

## Baselines & datasets used

- Synthetic long-context binding tasks `competing_vars` and `primacy_recency`: single-token key–value assignment recall with $k\in\{256,512,1024,2048\}$ filler tokens and $|\mathcal{C}|\approx 50$ candidates; evaluated on Qwen2.5-3B(-Instruct), Llama-3.2-3B(-Instruct), Gemma-2-2b(-it) — all ≤3B, within this project's relevant scale range.
- A naturalistic option-randomized `notes_binding` task at 8B–9B scale (Meta-Llama-3.1-8B-Instruct, Gemma-2-9b-it) — larger than the project's 1.2B target, flagged as such.
- QuALITY reading-comprehension dataset used for the trace-auditing extension (Llama-3.1-8B-Instruct), with baseline/RAG/checkpoint variants.

## Pitfalls / negative results

- Checkpointing (restating the true value) does not help once the model has stopped trying to answer at all: "The one exception is Llama at $k=2048$ on primacy_recency, where checkpointing fails (0% $\to$ 0.3%). Inspection reveals that Stage 2A gating has collapsed: the model no longer enters answer mode... Stage 2A failures at extreme distance are a distinct breakdown" — Section 5.4. This suggests a re-prompting/restatement fix only rescues "wrong value" failures, not "refused/off-format" failures — relevant if considering restatement tricks as a cheap alternative to fine-tuning for schema reliability.
- The mechanism is not validated on naturalistic long-context tasks: "We do not claim that the same mechanisms fully explain all long-context failures in naturalistic tasks such as document QA; we treat that as an open validation target" — Scope (Section 1.1) and Limitations (Section 7). Nothing here has been tested on tool-call/JSON-schema generation specifically.
- Mechanistic diagnostics (probing, activation patching) "require activation access and thus apply directly only to open-weight models... For hosted APIs, we provide output-level and trace-level diagnostics but cannot estimate $I_{\mathrm{avail}}$" — Section 7. Not a blocker for this project (LFM2.5 weights are available), but flags that the richer diagnostics need local activation access, not just API logprobs.
- Trace-level "flag under-budget claims" auditing (Appendix C) detects claims unsupported by cited evidence but explicitly "does not prove faithfulness to the model's hidden chain-of-thought. A model could produce a valid-looking trace via post-hoc rationalization" — Section 7. Relevant caution if borrowing this style of scrubbing-based flagging for the malformed-tool-return detector: passing the audit is not proof of genuine grounding.

## Metric / eval choices

- Error decomposition metric: "$\mathrm{Frac}\text{-}2A:=\mathbb{P}(G_{k}=0\mid\hat{Y}_{k}\neq V)$ and $\mathrm{Frac}\text{-}2B:=\mathbb{P}(G_{k}=1\mid\hat{Y}_{k}\neq V)$" (Section 3.4) — a template for splitting "did not attempt" vs. "attempted wrong" errors that could be adapted to schema-validity or malformed-tool-return scoring.
- Pseudo-prior / "bits-to-trust" framework: scrub the evidence supporting a claim (replace with `[REDACTED]`) and compare pre/post confidence via KL divergence to certify whether a claim is adequately supported (Section 4.3, Appendix C) — conceptually close to the project's "flag rather than assert" problem (detecting when the model should not trust/assert a tool result), though built for chain-of-thought auditing, not tool-return validity.
- All headline accuracies reported with "95% Wilson binomial confidence intervals" over instance counts (Section E.1) — a reminder to report CIs on the flag-rate/false-flag-rate targets in this project's eval too.

## Open questions for our project

- Does the Stage 2A/2B split (didn't attempt vs. wrong value) actually predict anything about *schema-validity* failures in tool calling, or is it specific to single-token key–value recall? Untested here.
- Would restating the tool schema/system constraints near the end of a long tool-conversation (checkpointing) measurably reduce first-attempt schema-validity failures at 1.2B scale — a candidate cheap mitigation to test before or alongside SFT/DPO/GRPO?
- The paper never touches quantization; it offers no evidence either way on whether 4-bit weights make Stage 2B binding failures worse, which is one of this project's open questions.
- No fine-tuning is done anywhere in this paper (Appendix D: "inference-only on released models (no training or fine-tuning)"), so it cannot inform which training signal (SFT/DPO/GRPO) fixes routing failures — only that a prompting-level fix (checkpointing) exists as a non-training baseline to compare against.
