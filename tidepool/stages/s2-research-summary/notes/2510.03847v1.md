# 2510.03847v1 — Small Language Models for Agentic Systems: A Survey of Architectures, Capabilities, and Deployment Trade-offs

**Relevance:** medium
It is on-topic (SLM tool use, structured output, LoRA/QLoRA, quantization for agents) and offers useful engineering patterns to adopt, but it is a qualitative survey/position paper with no new benchmarked experiments — even its own headline ablation table is explicitly a placeholder — so it cannot ground any of this project's specific numeric targets.

## TL;DR

A survey arguing SLMs (1–12B, occasionally ~20B) should be the default engine for agentic workloads (tool use, structured output, RAG orchestration) with LLMs reserved as an uncertainty-triggered fallback. It proposes a reference architecture (router → structured decoding → validators → execution → LLM fallback → telemetry-driven adapter refresh) and a set of engineering metrics (Schema Validity, ExecRate, Cost-per-Successful-task), but all numbers cited are qualitative/order-of-magnitude claims drawn from other papers' reports, not original measurements.

## Techniques to try

- Train separate LoRA adapters per task/skill rather than one general adapter, to keep specialization modular: "Train LoRA adapters per task cluster (e.g., one adapter for function calling, another for JSON generation). This allows for modular and efficient specialization." — Section VII.A (Practical recipe for SLM specialization)
- Treat schema validity as a first-class KPI measured at valid@1 and valid@k rather than only after retries/repair: "Treat Schema Validity as a KPI; measure valid@1 and valid@k." — Section VI.A (Recommended practice)
- Use streaming JSON output with incremental validators for early failure detection rather than waiting for a full generation: "Use streaming JSON with incremental validators; fail fast." — Section VI.A
- Continuously mine production/eval failures back into adapter refresh, which maps onto this project's "flag malformed tool returns" sub-criterion as an ongoing data-collection loop rather than a one-shot dataset: "Implement a periodic refresh mechanism for the adapters, using logged validator failures and new edge cases to continually improve model performance and robustness." — Section VII.A (Periodic Refresh)
- Fuzz schemas in CI to generate adversarial/malformed inputs for adapter fine-tuning data, relevant to building the ~300 malformed-tool-return probe set: "Fuzz schemas in CI & capture failure for adapter" [fine-tunes] — Section VI.A

## Baselines & datasets used

- The survey references BFCL v3/v4 and StableToolBench as the standard function-calling/tool-execution evals, consistent with this project's own BFCLv3 target, but reports no original scores on any model — all cited numbers point back to those benchmarks' own leaderboards or other papers.
- Representative SLMs discussed (Phi-4-Mini 3.8B, Qwen-2.5 0.5B–72B, Gemma-2/3 2B–27B, Llama-3.2 1B/3B, Ministral 3B/8B, Mistral-NeMo 12B, DeepSeek-R1-Distill 1.5B–70B, Apple on-device ~3B, OpenELM) are all larger than or only occasionally near this project's 1.2B target model; no LFM/Liquid model is mentioned.

## Pitfalls / negative results

- The paper's own central ablation table is a template, not data: "Ablations that matter. The following table illustrates the most action-able levers on CPS; values are representative (fill with your measurements)." (Table II caption) — this means none of the CPS/reliability numbers in the survey are actually measured; treat every quantitative claim in this paper (e.g., "10–30× cost reduction," "order-of-magnitude CPS improvements") as an unverified, unsourced-to-a-specific-model assertion.
- Listed limitations, directly relevant to this project's own risk list: "Benchmark/API drift; results may not transfer." / "Overfitting to narrow traces." / "Heavy validator dependence can hide reasoning errors." / "Router miscalibration causes wrong SLM/LLM escalations." / "Tool-use expands the security risk surface." — Section XVI.A
- Direct tension with this project's protocol: the paper's design recommendation is "Prefer grammar-first prompts (CFG or JSON Schema) + temperature 0" for reliable structured generation, whereas this project's first-attempt schema validity sub-criterion is explicitly measured with "no retry, no repair, and no constrained decoding or grammar enforcement." The survey's whole reliability story leans on constrained decoding as the safety net; it has nothing to say about achieving validity without it.
- General safety caveat worth carrying over: "smaller model size does not inherently guarantee harmlessness; it is imperative to apply robust content filters and rate-limit high-risk tool invocations."

## Metric / eval choices

- Proposes Cost-per-Successful-task (CPS): "This metric is defined as the total operational cost divided by the number of schema-valid, tool-valid completions. It provides a holistic view of efficiency." Could be a useful secondary efficiency metric alongside this project's throughput/quality targets, though it requires a cost model this project may not need.
- Recommends a minimum metric set for SLM-powered agents: "Task success rate: The percentage of tasks successfully completed." and "Schema validity: The percentage of structured outputs that adhere to their defined schemas." plus ExecRate, p50/p95 latency, escalation rate, drift resilience, and energy/request — broader than this project's BFCL+guardrail-suite scope but reinforces that schema validity and task success should be reported as separate numbers, which this project already does.

## Open questions for our project

- The paper gives no evidence either way on whether low-bit quantization damages structured-output/instruction-following more than knowledge — it only asserts quantization is generally beneficial for cost/energy, with no accuracy-retention breakdown by task type or bit-width.
- It gives no method for instilling "flag rather than assert" behavior on malformed tool returns; its only related idea is a generic verifier-adjudication step in a multi-model router pipeline, not a training signal for a single model.
- It does not address vocabulary size effects on tool-call/JSON tokenization, so it is silent on the 65K-vs-128K vocabulary question this project cares about.
- No instruction-like text directed at the reader was found in the paper; it reads as a standard survey/position paper throughout.
