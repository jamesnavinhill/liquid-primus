# 2210.04802v2 — SimSCOOD: Systematic Analysis of Out-of-Distribution Generalization in Fine-Tuned Source Code Models

**Relevance:** medium
Direct evidence on the project's open "LoRA or full fine-tuning at 1.2B?" question and on how fine-tuning erodes pretrained knowledge, but all measured on much smaller code models (220M–770M, plus a 13B LoRA-only run) with CodeXGLUE-style exact-match/BLEU tasks, not tool-calling or structured-output benchmarks.

## TL;DR

The paper simulates out-of-distribution (OOD) scenarios for code models by masking sub-regions of the fine-tuning data along length, syntax, and semantic dimensions, then compares full fine-tuning vs. LoRA fine-tuning on the resulting OOD test sets. Across four pretrained code models and two generation tasks, full fine-tuning and LoRA perform comparably in-distribution, but LoRA generalizes substantially better to OOD data and produces more unseen ("never seen during fine-tuning") language elements at inference time — evidence that freezing pretrained weights and only training low-rank adapters better preserves pretraining knowledge under a narrow fine-tuning distribution.

## Techniques to try

- Simulate OOD generalization gaps for a narrow fine-tuning task by deliberately masking a small slice (~3%) of the fine-tuning distribution along an axis relevant to the task (e.g., a specific tool-schema field, a JSON type, a rarely used API), then evaluating held-out performance on exactly that slice — a cheap, controllable proxy for "does this model handle stack elements it wasn't trained on" without needing a separate OOD dataset ("Simulating various OOD scenarios by masking out sub-regions of training data distribution is an alternative way to systematically study the model behaviors" — Section 1).
- Prefer LoRA over full fine-tuning when the goal is retaining general/pretrained capability while specializing to a narrow domain, since the paper finds LoRA "effectively leverages the previously acquired knowledge, resulting in improved OOD generalization compared to full fine-tuning" ("This observation shows that LoRA fine-tuning, which involves freezing the pretrained weights, effectively leverages the previously acquired knowledge, resulting in improved OOD generalization compared to full fine-tuning." — Section 4.3), directly bearing on the project's "erosion of general ability" concern.
- A "few-data regime" check: adding back just ~1.5% of the fine-tuning data belonging to the masked-out property recovers most of the OOD performance loss — worth trying as a cheap fix if a specific tool/schema pattern is found to be underperforming after SFT ("by adding data in size ≈ 1.5% of the fine-tuning data in each specific scenario, the model can gain significant accuracy performance" — Section 4.3).

## Baselines & datasets used

- CodeXGLUE benchmark tasks: text-to-code generation (CONCODE dataset) and code refinement (Tufano et al. 2019 "medium" bug-fix dataset).
- Models: GraphCodeBERT (encoder-only), CodeT5-base (220M), CodeT5+ (770M), Code Llama (13B, LoRA-only due to full-FT compute cost).
- Metric: exact match as the primary metric ("we focus on the exact match metric to quantify the model behaviors"); BLEU reported in appendix but explicitly flagged as unreliable for correctness.

## Pitfalls / negative results

- Full fine-tuning can collapse almost entirely on OOD extrapolation: "fine-tuning CodeT5 with LoRA fine-tuning resulted in a 24.99% relative exact match, whereas the model's relative performance using full fine-tuning was 0.0%" in the length-extrapolation scenario (Section 4.3, Table 1) — a stark forgetting failure mode, not a modest degradation.
- Syntax-based OOD (an unseen language element that made up only ~3% of the fine-tuning data) is one of the hardest scenarios even though the model "had previously encountered code examples that included the else element" during pretraining — i.e., pretraining exposure alone does not guarantee the fine-tuned model retains/uses that knowledge ("the drop can be as substantial as 90%" — Section 1 contributions).
- BLEU/CodeBLEU are explicitly called out as poor correctness proxies: "a naive copy of the input codes" can match state-of-the-art BLEU on the code-refinement task, and "CodeBLEU and BLEU scores are not necessarily correlated with the correctness of the programs" — relevant caution against relying on n-gram-overlap metrics for judging structured-output correctness.
- Encoder-only GraphCodeBERT (decoder trained from scratch) generates far fewer unseen elements than encoder-decoder or decoder-only models, since it "can only rely on the prior knowledge acquired by the encoder" — architecture matters for how much pretraining knowledge survives into generation.

## Metric / eval choices

- Reports OOD/few-data results as *relative* exact match against a 100%-data baseline (no mask-out) rather than raw scores, isolating the generalization gap from absolute task difficulty — a pattern worth borrowing for structured-output evals for measuring how much a masked-out schema/tool pattern costs relative to a fully-covered baseline.
- Deliberately chose exact match over BLEU/CodeBLEU for OOD analysis because it is "desirable to see if the model can generate specific unseen or rare programs correctly" rather than reward superficial overlap — analogous reasoning applies to first-attempt schema validity as this project's chosen metric.

## Open questions for our project

- All results are on code models far smaller (220M–770M) than the 1.2B target, and the one 13B model (Code Llama) only has LoRA results, not a matched full-FT comparison — unclear whether the LoRA-beats-full-FT-on-OOD gap holds, shrinks, or grows at 1.2B scale with much higher LoRA rank ceilings.
- Tasks are exact-match code generation (CONCODE, bug-fix), not structured tool-call/JSON emission or instruction-following, so it's unclear whether "OOD syntax element" findings transfer to "OOD tool schema field" or "malformed tool return" scenarios central to this project's sub-criteria.
- No exploration of DPO, GRPO, or quantization in this paper — it only informs the SFT stage of the candidate ladder (LoRA vs. full), not the later rungs.
