# 2602.22223v1 — SQaLe: A Large Text-to-SQL Corpus Grounded in Real Schemas

**Relevance:** low
A large-scale text-to-SQL data generation resource/pipeline, useful only as a possible source of SQL-dialect training data for the "specialize to underlying technology" goal, but it says nothing about tool-calling schema validity, structured-output reliability, quantization, or any of the candidate training methods (LoRA/DPO/GRPO) this project is choosing between.

## TL;DR

SQaLe is a semi-synthetic text-to-SQL dataset of 517,676 (schema, question, SQL) triples built over 135,875 database schemas expanded from 22,989 real-world schemas (SchemaPile), generated with Qwen3-30B plus the ReFoRCE candidate-generation-and-voting framework. It targets schema scale and realism (median 91 tables, 435 columns/schema) rather than a new training method, evaluation protocol, or agent/tool-calling behavior.

## Techniques to try

- Schema-extension-then-question-then-SQL pipeline could be adapted as a template for generating SQL-dialect training data if the project needs SQL-specific tool-call/queries for the operator's tech stack: "existing schemas are extended incrementally, for example by including 5 to 25 synthetic tables, until the target query complexity distribution is balanced around a median of 4 joins per query" (Section 2.2).
- SQL candidate generation with self-consistency voting plus execution validation as a data-quality filter: "paired with candidate SQL statements in a query creation phase using the ReFoRCE text-to-SQL framework ... which generates multiple SQL candidates, applies a voting process to select the best one, and validates executability by executing the SQL statement against the schema" (Section 2.2). This execution-based validation pattern is analogous to the project's own GRPO idea of using "execution correctness" as a verifiable reward.

## Baselines & datasets used

- Compares schema/query statistics against BIRD, EHRSQL, Spider 2.0, and SynSQL-2.5M (Table 1, Table 2); SQaLe itself is built on SchemaPile real-world schemas.

## Pitfalls / negative results

- The full pipeline is compute-heavy and not something this project's compute posture will likely match: "executed with up to 100x H100 GPUs in parallel" and "even ReFoRCE requires 12 seconds on an H100 to generate a single SQL query" — highlights that even a curated-dataset baseline (ReFoRCE) is too slow/expensive for real-time or lightweight generation at 1.2B scale.
- Dataset generation and validation relied on a much larger generator model (Qwen3 30B) than the project's 1.2B target, so any adopted pipeline would need a smaller/cheaper generator or distillation step; the paper does not test whether smaller models can perform the same schema-extension/question-synthesis steps.

## Metric / eval choices

- Uses structural/statistical descriptors rather than task accuracy: number of schemas, median columns/tables per schema, number of foreign keys, share of queries using WHERE/JOIN/functions, median tokens per query (Tables 1–2). No execution-accuracy or exact-match benchmark numbers are reported for models trained on SQaLe.

## Open questions for our project

- No results are given for training a small (~1B-scale) model on SQaLe or measuring downstream tool-calling/schema-validity gains, so it's unclear whether this dataset would move any of this project's pre-registered metrics (BFCLv3, schema validity, flag rate) if used as SQL-specialization data.
- The paper's own claim of scaling benefits is speculative, not measured: "we hypothesize that through significantly larger, more complex and diverse text-to-SQL datasets we can achieve proportional gains in model performance as a function of dataset scale" (Section "Toward scaling text-to-SQL with SQaLe") — this is a stated hypothesis, not a validated result, so it should not be treated as evidence for a scaling claim in our plan.
