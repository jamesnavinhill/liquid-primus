# 2512.16083v1 — Scaling Text2SQL via LLM-efficient Schema Filtering with Functional Dependency Graph Rerankers

**Relevance:** low
This is a retrieval/reranking pipeline for selecting relevant schema columns before a downstream Text2SQL LLM call — a different task from post-training a 1.2B model to reliably emit tool calls/structured output, and none of its findings speak to quantization, LoRA vs. full SFT, DPO/GRPO signal design, or malformed-tool-return detection.

## TL;DR

GRAST-SQL is a three-stage schema-filtering system (query-aware LLM column encoder → graph transformer over a functional-dependency graph → Steiner-tree connectivity repair) that shrinks huge database schemas (up to 23K+ columns) down to a compact, join-valid sub-schema before handing it to a Text2SQL LLM, cutting prompt tokens by up to 50% with no accuracy loss. It targets the "which columns to put in the prompt" problem, not how to train a model to produce correct/valid SQL or tool calls.

## Techniques to try

- None directly applicable. The closest adjacent idea is using an LLM's own hidden state at the decision token as a relevance embedding rather than its output label: "Rather than using the predicted label, we extract the hidden state the model uses to score the first answer token ("yes"/"no")" (§3.3) — a general representation-extraction trick, but built for a reranker, not for our agent-turn / tool-call model.

## Baselines & datasets used

- Evaluated on Spider (200 DBs), BIRD (95 real-world DBs), and a constructed Spider 2.0-lite eval set (99 DBs, up to 23,067 columns) — all Text2SQL schema-linking benchmarks, none of which overlap with BFCL, IFEval, or our tool/JSON-schema evaluation targets.
- Baselines compared: SchemaExP, CodeS (350M/3.5B), RESDSQL, BGE embedding/reranker models, Qwen3-Reranker (0.6B/4B/8B) — all schema-filtering or retrieval models, not instruction-following or tool-calling models.

## Pitfalls / negative results

- "The LLM-reranker is not sufficient alone, as evidenced by the consistent gap between w/o Func. Dep. Graph and the full model" (§5.3) — i.e., a plain LLM relevance ranker misses structurally-required columns (join keys) that have no lexical/semantic overlap with the query; only graph-based structural propagation recovers them. This is a schema-structure-specific failure mode, not a generation/instruction-following one, so it doesn't transfer to our flag-vs-assert or schema-validity problem.
- Many real-world databases (BIRD, Spider 2.0) lack declared primary/foreign keys, requiring an auxiliary LLM (GPT-4.1-mini) prompting pass just to reconstruct schema structure before filtering — a reminder that real deployment schemas are often under-annotated, relevant context for the "specialize to SQL dialects" standing constraint but not a training-signal finding.

## Metric / eval choices

- Uses ROC AUC and PR AUC as primary ranking-quality metrics, plus "precision at a high-recall operating point" (recall pushed near 1.0) as the practically meaningful metric, since "omitting a necessary column typically renders the query unsolvable" (§5.2) — a recall-first framing that doesn't map onto our schema-validity / flag-rate targets (which are about output correctness, not input coverage).
- Explicitly recommends against a fixed decision threshold in favor of top-K/top-percentage selection, "as the optimal cutoff can vary depending on the dataset or change after re-training" (§5.6) — a general caution about threshold instability that could loosely inform how we pick a decision threshold for the malformed-tool-return flag rate, though the paper's context is column selection, not classification calibration.
