# 2605.01047v1 — LLM Ghostbusters: Surgical Hallucination Suppression via Adaptive Unlearning

**Relevance:** medium
The paper's target behavior (package-name hallucination in code generation) and scale (7B/16B full-parameter fine-tuning) don't match this project directly, but its per-domain KL-drift evaluation and hybrid reinforce/suppress objective are a plausible technique for the "flag rather than assert" and general-ability-erosion questions this project needs to answer.

## TL;DR

Adaptive Unlearning (AU) is a post-deployment framework that treats "package hallucination" (fabricated Python library names, a slopsquatting attack vector) as an open-ended unlearning problem: it repeatedly samples the model's own outputs, uses a PyPI-registry oracle to label tokens as valid/hallucinated/context, and trains with a token-level hybrid loss (cross-entropy reinforcement of valid tokens + NPO suppression of hallucinated tokens + a regularization anchor on everything else) inside a mutation loop that keeps discovering new hallucination-inducing prompts. On DeepSeek-Coder 7B/16B it cuts hallucination rate ~81-88% while roughly preserving EvalPlus coding scores, and the paper explicitly decomposes KL-divergence drift by domain (code / instruction / package) to show the fix stayed "surgical."

## Techniques to try

- Token-level tri-masking that routes disjoint token populations to different loss terms in the same sequence, so a "reinforce the good behavior" signal and a "suppress the bad behavior" signal never fight over the same gradient: "tri-masking enables surgical edits within a single sequence without affecting adjacent tokens, and is what allows the hybrid CE and NPO objectives to operate on disjoint token populations without competing." (§1.3, Contributions) — could be relevant to instilling "flag rather than assert" on malformed tool returns without degrading normal tool-call generation on the same turn.
- Decomposing distributional-drift measurement by task domain (here: code vs. instruction-following vs. package-recommendation) rather than reporting one aggregate KL number, to check that an intervention aimed at one behavior didn't leak into others — directly useful for this project's "guardrail metric stays within 2.0 points" check and the open question of how general ability is kept from eroding while a narrow skill is trained up.
- Nested outer/inner training loops (regenerate synthetic samples every N_outer steps, train repeatedly on the cached batch for N_inner steps) to stabilize self-generated-data training that would otherwise chase a moving target: "training without inner epochs (equivalent to N_inner=1) failed to reduce hallucination rates, as the model could not consolidate which patterns to suppress before samples changed." (§3.5)

## Baselines & datasets used

- Models: deepseek-coder-7b-instruct-v1.5 (dense 7B) and DeepSeek-Coder-V2-Lite-Instruct (MoE, 16B total / ~2.4B active). Both well above this project's 1.2B target, and results at 1.2B are not shown.
- Baselines: unmodified base model, Gradient Ascent, NPO (Zhang et al. 2024), PMC (Scholten et al. 2025); ablations AU CE-Only and AU NPO-Only.
- Utility benchmark: EvalPlus (HumanEval+, MBPP+), pass@1.
- Hallucination oracle: a static PyPI registry snapshot used to label package names as real or fabricated — a deterministic, non-model-scored oracle, which is the same kind of signal (not "model-scored stored reward") this project's standing constraints require.
- Training data: 20 seed coding prompts (listed in Appendix F) expanded via adaptive mutation to a curated set of 40; entirely model-self-generated, no human annotation.

## Pitfalls / negative results

- "All Adaptive Unlearning runs use full-parameter fine-tuning: we update every trainable parameter rather than adopting parameter-efficient methods such as LoRA" (§4.4, Models) — the method as evaluated has no LoRA data point at all, which cuts against directly reusing it under this project's LoRA-first candidate ladder.
- Neither loss term alone works: "When the suppression term is removed entirely (CE-Only), hallucination rates remain at 12.06%. When the reinforcement term is removed entirely (NPO-Only), the results are similar at 12.42%" on DeepSeek-7B, vs. 2.56% for the full hybrid objective (Table 2, §6.0.1) — a pure preference/suppression loss or pure reinforcement loss on its own was insufficient; only the hybrid closed the gap.
- Scale/architecture-dependent utility cost: on the 16B MoE model, AU's coding-benchmark average dropped 4.2 points versus base (vs. an *improvement* on the 7B dense model), attributed to "each expert sees a small fraction of the training tokens and receives a correspondingly sparser unlearning signal" (§5.1) — a caution that MoE-style sparse routing can make a narrow-behavior fix harder to consolidate without utility loss, worth watching if any candidate architecture uses routing.
- Both key hyperparameters (inner epochs, mutation count) have an inverted-U: too few inner epochs (N=1) never reduces hallucinations (13.8%), but pushing too far (20 epochs) makes it worse again (5.7%, rising KL) versus a sweet spot at 14 (4.0%); same pattern for mutation count (minimum 3.9% at 6 mutations, rebounding to 6.3% at 10) — a generic warning that "more adaptive/iterative refinement" is not monotonically better and needs its own held-out tuning sweep.
- Full-parameter fine-tuning "at those scales requires multi-node GPU clusters that exceed the resources for this study" for scaling beyond 16B (§7, Limitations) — explicitly flagged by the authors as a resource wall, i.e. this approach does not obviously scale down cheaply either, since it depends on updating the whole model.
- The oracle itself is shallow: "Our oracle verifies whether package names resolve against the registry, not whether packages are used semantically correctly in the generated code" (§7) — a reminder that a cheap, deterministic pass/fail oracle can miss semantic correctness, relevant if this project builds a similar cheap oracle for "well-formed vs. malformed tool return."

## Metric / eval choices

- Primary metric: hallucination rate = fraction of emitted package identifiers that fail to resolve against a PyPI snapshot (Eq. 7), measured via two elicitation modes per prompt ("what packages are required to run this?" vs. "what packages would be useful?") so neither framing alone can dominate the headline number — analogous in spirit to this project's own paired flag-rate / false-flag-rate design against gameability.
- Secondary metric: KL-divergence of the fine-tuned model vs. the base model, reported separately for code, instruction-following, and package-recommendation query distributions, used as an "upper bound on collateral damage."
- Utility metric: EvalPlus pass@1 on HumanEval/HumanEval+/MBPP/MBPP+, compared fine-tuned vs. base, with "utility preservation" defined as matching the base model jointly across all four.

## Open questions for our project

- Does anything like tri-masked hybrid reinforce/suppress training transfer down to a 1.2B hybrid-architecture model and to LoRA (rather than full fine-tuning), or does the mechanism specifically depend on updating every parameter?
- Is "flag rather than assert" on a malformed tool return structurally similar enough to "suppress a hallucinated package name while reinforcing a valid one" for the tri-mask idea to carry over, or is tool-return validity too different a target (a binary flag/refuse decision vs. token-level content substitution)?
- Could the paper's per-domain KL-drift decomposition (code / instruction / target-behavior) be adapted as a lightweight regression check for this project's guardrail metrics, in place of or alongside the benchmark-score deltas already planned?
- No embedded instructions to the reader were found in this paper; it is a straightforward research write-up.
