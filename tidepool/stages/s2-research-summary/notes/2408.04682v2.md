# 2408.04682v2 — ToolSandbox: A Stateful, Conversational, Interactive Evaluation Benchmark for LLM Tool Use Capabilities

**Relevance:** medium
It contributes no training method, quantization data, or small/on-device model numbers, but its "Insufficient Information" / Minefield methodology and negative results are directly relevant context for designing and sanity-checking the malformed-tool-return flag-rate probe.

## TL;DR

ToolSandbox is an evaluation benchmark (not a training method) that tests tool-use LLMs in a stateful, multi-turn, LLM-simulated-user setting, scoring trajectories against human-authored "Milestones" (must happen) and "Minefields" (must not happen, e.g. hallucinated tool calls). Its "Insufficient Information" category — testing whether a model recognizes a task is unsolvable rather than hallucinating a tool or argument — is conceptually the closest published analogue to this project's "flag rather than assert" sub-criterion, though it is evaluated on 7B+ and proprietary models only, none on-device or quantized.

## Techniques to try

- Minefield scoring as a template for the malformed-tool-return probe: define events that must NOT occur (e.g., asserting success on garbage input) and zero out the whole trajectory score if they do — "ensuring if minefields are violated (non-zero minefield similarity), the similarity score for the whole trajectory is 0" (Eq. 1, Section 2.3) — a stricter pattern than averaging flag-rate and false-flag-rate independently.
- Their "Insufficient Information" scenario design method — deliberately withholding a needed tool/argument (e.g., no access to current timestamp) and checking the model doesn't hallucinate a tool call — is a usable template for constructing malformed/incomplete tool-return probe cases: "This category exercises if the agent is able to identify that it cannot complete the task, as opposed to hallucinating tools or tool arguments, as shown in Figure 3" (Section 3).
- Tool schema robustness ablations (name/description/argument-description/type scrambling, 0/3/10/all distraction tools) are a cheap way to stress-test whether the fine-tuned model's schema adherence is robust to the operator's actual (imperfect) tool docs, not just to clean training-style schemas (Appendix A.2.1).

## Baselines & datasets used

- 1032 human-authored test scenarios, 34 tools across 11 domains (Contact, Messaging, Reminder, System settings, Time, Math, Map, Weather, Stock, Conversion, Holiday); GPT-4o-2024-05-13 used to generate benchmark statistics (Table 4, Section 3).
- Models evaluated: GPT-4o, GPT-4-0125-Preview, GPT-3.5-Turbo, Claude-3-Opus/Sonnet/Haiku, Gemini-1.5-Pro/1.0-Pro, Hermes-2-Pro-Mistral-7B, Mistral-7B-Instruct-v0.3, Gorilla-Openfunctions-v2, C4AI-Command-R/R+ (Table 5). The only sub-8B models tested are Mistral-7B-Instruct-v0.3 and Hermes-2-Pro-Mistral-7B — both roughly half the score of proprietary models (29.8 and 31.4 avg similarity vs. 73.0 for GPT-4o), and no model near this project's 1.2B scale, and no quantized variants, appear anywhere in the paper.

## Pitfalls / negative results

- Command-R, Command-R+, and Gorilla-Openfunctions-v2 "are not capable of consuming tool responses" at all (Table 10, Appendix D.2) — they can only pass Single Tool Call scenarios and fail anything requiring a second turn on tool output, a hard architectural/prompt-template failure worth checking for in any base model before fine-tuning.
- Weak models can look artificially good on "don't hallucinate" metrics simply because they act less: "These models' subpar performance unexpectedly caused them to achieve higher rating in the Insufficient Information category, which rewards the model for not generating hallucinated tool calls or arguments when provided tools are insufficient to complete the task. This should be considered a side effect instead of a positive outcome" (Section 4, "Open Source Models") — directly cautions against reading a high flag-rate as good behavior without also checking the false-flag rate and overall task competence, which is exactly why this project pairs flag rate with false-flag rate.
- "Insufficient Information performance overall negatively correlates with other categories. The stronger the model performance on complex tasks, the worse the insufficient information performance" (Section 4) — even frontier models trade off task-completion drive against correctly recognizing impossibility; even GPT-4o and Claude-3-Opus only score 76.6 and 71.1 (a similarity metric, not the same as flag rate, and measured on much larger proprietary models) on this category, suggesting the project's target of ≥0.80 flag rate / ≤0.10 false-flag rate is an ambitious, not obviously "given" bar even for top-tier models, let alone a 1.2B model.
- Larger models (GPT-4, Claude-3-Opus) issue erroneous parallel tool calls on dependent tools more often than smaller/mid models, causing race-condition failures in State Dependency scenarios (Section 4, "State Dependency") — a caution that scaling up training data/capacity does not monotonically fix tool-sequencing correctness.
- Canonicalization (especially date/time reasoning) remains hard for all models tested, including hallucinated timestamps and incorrect relative-date conversion (Section 4, "Canonicalization") — relevant if the operator's stack requires date/time canonicalization in tool arguments.

## Metric / eval choices

- Milestone DAG matching: trajectories are scored by finding the best assignment of turns to milestone nodes subject to a topological-order constraint, using per-column similarity functions (exact match, ROUGE-L F for text, AST matching for tool-call structure "similar to the AST metric found in BFCL") combined via geometric mean (Appendix A.7, Eq. 2) — a more flexible alternative to BFCL's static AST match if the project ever needs multi-turn tool-call correctness scoring beyond BFCLv3.
- Minefield scoring: score = score_M+ × 𝟙(score_M− = 0) (Eq. 1) — any hallucinated/forbidden action zeroes the entire trajectory score, a harsher aggregation than this project's independent flag-rate/false-flag-rate pairing.
- ReAct-style prompting gave only marginal gains over minimal prompting in their setup (Table 9, Appendix D.1) — suggests prompt engineering is not a substitute for capability, consistent with this project's decision to fine-tune rather than rely on prompting.

## Open questions for our project

- ToolSandbox's Insufficient-Information/Minefield framing is the closest published proxy for "flag rather than assert," but it measures *task-level* hallucination (calling a tool that shouldn't exist for the task) rather than this project's target of flagging a *malformed tool return* mid-trajectory — worth checking whether the operator's probe set should borrow the Minefield "must not occur" scoring even though the triggering condition differs.
- No data here at 1.2B scale, no 4-bit/quantized results, and no results on models with small (65K) vocabularies — this paper cannot inform the quantization-degradation or vocabulary-size questions in this project's brief.
- No instruction-like text directed at the reader was found in the paper; it is a straightforward benchmark description.
