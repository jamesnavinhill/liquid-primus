# 2603.16901v1 — From Language to Action in Arabic: Reliable Structured Tool Calling via Data-Centric Fine-Tuning

**Relevance:** medium
Small on-device function-calling model (270M FunctionGemma) fine-tuned with a data-centric pipeline gives directly comparable full-vs-LoRA and tool-sampling evidence, but it never touches quantization/GGUF, DPO/GRPO, or malformed-tool-return detection, so it informs several open questions without settling any pre-registered target.

## TL;DR

The authors take a 270M-parameter FunctionGemma model that is near-useless for Arabic tool calling out of the box (87% parse failure) and, purely through dataset repair, tool-count reduction per prompt, and full-parameter SFT, drive parse failure below 1% and lift function-name accuracy more than eightfold. After structural failures are fixed, remaining errors are almost entirely semantic (wrong tool, hallucinated tool, argument mismatch) rather than formatting — a clean illustration that serialization reliability and decision-level tool selection are separable problems, which matches this project's split between "first-attempt schema validity" and BFCL-style correctness.

## Techniques to try

- Stochastic tool-subset sampling during training to control prompt length: each example gets exactly 5 tool declarations (ground-truth tool + 4 random distractors for positives, 5 random tools for negatives), permuted to remove positional bias — "This mechanism reduces the median prompt length from approximately 4,900 tokens to approximately 793 tokens, ensuring all examples fit within the 2048-token context window." (§3.3). Directly applicable if our agent-gateway tool catalog is large enough to blow the context budget during training.
- Completion-only masking over just the assistant's function-call tokens (and, in the reasoning variant, the `<think>` segment too), implemented via `dataset_text_field="text"` so "all prompt tokens (developer, tool declarations, and user turns)" are masked out of the loss (§3.4, §3.6) — standard, but confirms it's necessary to keep gradients on the structured-output tokens rather than the tool schema text.
- Full-parameter fine-tuning outperformed partial/LoRA adaptation at 270M scale: "Preliminary experiments with partial adaptation indicated instability in function-name prediction and argument alignment, particularly under dialectal variation. Full-parameter fine-tuning yielded significantly improved convergence behavior and more stable structured outputs" (§3.6) — a data point (at 270M, not 1.2B) toward the project's "LoRA or full fine-tuning at 1.2B?" question, but the scale gap is large enough that it's suggestive rather than conclusive.
- Explicit enum-null repair: the original filter rejected `None` as an enum violation for optional parameters, silently deleting valid training examples and "reactivated six tools that had effectively become 'dead' due to complete sample exclusion" (§3.2) — a concrete data-auditing checklist item worth running against any tool-call dataset we build or reuse.
- Reasoning-augmented LoRA variant with an explicit `<think>...</think>` block before the tool call, trained with LoRA rank 64 on top of the fully fine-tuned checkpoint, reaching near-perfect strict-eval scores (Table 3) — relevant as a possible mechanism for instilling deliberate tool-selection behavior, though it targets tool *choice* correctness, not the "flag malformed tool return" behavior this project needs.

## Baselines & datasets used

- Base model: `unsloth/functiongemma-270m-it`, a 270M-parameter FunctionGemma variant with dedicated control tokens for tool declaration/call/response (§3.1, §2). Far below the project's 1.2B target but useful as a small-model baseline reference.
- Dataset: HeshamHaroon/Arabic_Function_Calling, 50,810 samples, 36 tools, 5 Arabic dialects (MSA, Egyptian, Gulf, Levantine, Maghrebi), 8 domains, repaired into AISA-AR-FunctionCall (41,104 train / 4,568 val / 5,079 held-out test) (§3.2, §3.5).
- Training config: 2 epochs, batch size 4 with grad-accum 8 (effective 32), 8-bit AdamW, cosine schedule, lr 2e-5, BF16, gradient checkpointing (§3.5) — a concrete, reproducible SFT recipe reference at small scale.

## Pitfalls / negative results

- Naive inclusion of all tool declarations per example (36, later 27 after pruning) produced prompts "frequently exceeded 4,900 tokens" against a 2048-token limit, so "gradient updates were dominated by prompt tokens rather than the structured action output" until tool sampling was introduced (§3.3) — a training-pipeline failure mode worth checking for directly if we train with our full tool catalog inlined.
- After fine-tuning fixes parsing, tool hallucination becomes a leading error category (24.7% of errors, up from 0.04% at baseline — Table 2), i.e., fixing structural reliability did not fix over-eager or wrong tool invocation, and can even make it more visible as a share of remaining errors.
- Reasoning supervision changes output serialization in a way that breaks naive format validators: "strict formatting validators classify many reasoning outputs as parse failures because the serialized output now includes `<think>` tokens before the function-call marker. This does not reflect structural instability, but rather a difference in output serialization" (§4.3) — a concrete warning that our eval harness must be reasoning-aware if we ever add a think-before-call mode, or it will misreport schema validity.
- Domain-level results show a persistent gap for "procedurally complex domains such as Government Services," even after structural fixes eliminate parse failures uniformly — semantic/decision accuracy does not improve equally across all task types, only structural validity does (§4, Fig. 5).

## Metric / eval choices

- Error taxonomy used to diagnose model behavior post-fine-tuning: parse failure, tool hallucination, wrong function, argument mismatch, correct (Table 2) — a reusable failure-mode breakdown that maps well onto separating "first-attempt schema validity" from tool-selection/argument correctness in this project's own eval design.
- Structural vs. semantic metric split: parse failure rate, format validity, full tool-call match, function-name accuracy, argument F1/exact-match, hallucination rate (§4, Figs. 3–4) — a similar decomposition to what the project needs for BFCL + first-attempt schema validity + malformed-return flagging, though defined slightly differently (no analog to the project's flag-rate/false-flag-rate pair for malformed *tool returns*, since this paper's "negative samples" are queries that require no function call, not garbage tool outputs).
- Strict vs. "deployment-aware" evaluation distinction for the reasoning variant (Table 3, §4.3) — worth borrowing conceptually: define evaluation so reasoning/think tokens don't get penalized as schema violations if such a mode is used.

## Open questions for our project

- The paper's "negative sample" concept (100% abstention accuracy when `requires_function=False`) is about deciding whether to call a tool at all, not about detecting a malformed tool *result* — it does not directly answer this project's flag-rate/false-flag-rate question for malformed tool returns; that behavior isn't tested here at all.
- No quantization, GGUF, or throughput results are reported anywhere in this paper — it offers nothing on whether low-bit quantization damages structured output more than knowledge, one of this project's central open questions.
- The full-vs-LoRA comparison here is confounded (full FT is the "primary" checkpoint, LoRA is applied on top of the already-fine-tuned model for the reasoning variant, not as a controlled ablation against full FT from the base model) — so the "full FT beat partial adaptation" claim in §3.6 is asserted from unreported preliminary experiments, not shown with numbers, and shouldn't be taken as strong evidence on its own.
