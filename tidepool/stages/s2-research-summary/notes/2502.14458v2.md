# 2502.14458v2 — Llamba: Scaling Distilled Recurrent Models for Efficient Language Processing

**Relevance:** low
The paper is about distilling Transformer teachers into a new Mamba-2-based architecture at pretraining scale (MOHAWK, billions of distillation tokens), not about post-training an existing hybrid model like LFM2.5 for tool-calling/structured output, so it does not bear on this project's method choices, metrics, or targets.

## TL;DR

Llamba distills Llama-3.x (1B/3B/8B) into a Mamba-2-based recurrent architecture using the MOHAWK framework, reaching near-teacher accuracy on general benchmarks with under 0.1% of the teacher's original pretraining tokens, and ships an MLX/4-bit on-device implementation for edge throughput and memory gains. It targets general commonsense/knowledge benchmarks and raw decode throughput, not instruction-following, tool-calling, or structured-output reliability, and it never quantifies how 4-bit quantization affects task accuracy (only throughput/memory).

## Techniques to try

- None directly applicable — this is an architecture-distillation recipe (Transformer → Mamba-2 via MOHAWK's three-stage matrix orientation / hidden-state alignment / weight-transfer+KD) for building a new base model, not a recipe for post-training an already-deployed hybrid model on tool-use data. Not relevant to the LoRA/SFT/DPO/GRPO ladder this project is working through.

## Baselines & datasets used

- Distillation data: "fineweb-edu-4.0" (a stricter-filtered subset of fineweb-edu) for Matrix Orientation and Hidden-State Alignment, plus "the Open-Hermes-2.5 dataset was employed for an additional 4 epochs, processing 200 million tokens per epoch with sequences of length 4096" for knowledge distillation ("4.3 Data") — an open-source-only data recipe, offered as a contrast to "many alternative models that rely on highly curated proprietary datasets."
- Evaluation harness: "All evaluations were conducted using bfloat16 precision and the lm-eval-harness v0.4.4 Python library (Gao et al., 2024)" — general commonsense/knowledge suite (ARC-C/E, PIQA, Winogrande, HellaSwag, Lambada, MMLU, OpenBookQA), zero- and few-shot. No instruction-following, tool-use, or agentic benchmark (no BFCL, IFEval-style, or schema-validity evaluation of any kind).

## Pitfalls / negative results

- MMLU is the weak spot for this class of distillation: "We specifically focus on MMLU, which is known to be difficult for recurrent models (Waleffe et al., 2024), and has the biggest gap for distilled models from prior work" and "We found that MMLU performance takes much longer to improve compared to other benchmarks in our end-to-end distillation... while MMLU took longer to improve." At 8B, Llamba's MMLU relative-to-teacher score is 80.6% (Table 3) — a persistent, slow-to-close gap even with a strong teacher and full-precision training, suggesting knowledge-heavy multi-choice tasks are the hardest thing to preserve under architecture-level compression. This is a generic reminder that knowledge-style metrics can lag behind other capabilities during any compression/distillation process, even if the specific mechanism (Transformer→SSM) doesn't apply to this project.
- Data-choice effect is narrow: "while the C4... and fineweb datasets achieve similar scores across most benchmarks, fineweb-edu drives a marked improvement in MMLU" — i.e. one specific data-quality lever moved one specific benchmark and not others, a caution against assuming a single training-data change will move all target metrics uniformly.
- Structural limitation acknowledged directly: "MOHAWK transfers only the MLP weights that affect the hidden dimensions, excluding the sequence mixer weights related to the time dimension. This omission limits the ability to capture time-dependent information directly" — not applicable to this project's post-training setting, but a reminder that distillation methods can systematically fail to transfer specific capability classes (here, temporal/sequence-mixing behavior).

## Metric / eval choices

- Uses standard zero/few-shot lm-eval-harness accuracy on general knowledge/commonsense tasks and raw decode throughput (tokens/sec at varying batch size) plus on-device memory consumption as its two evaluation axes; no schema-validity, tool-call correctness, or refusal/flag metric anywhere in the paper — this project's core metrics (BFCLv3, IFEval/IFBench/Multi-IF, first-attempt schema validity, flag/false-flag rate) are entirely outside this paper's scope.
- 4-bit quantization is evaluated only for throughput and memory ("Llamba maintains constant high throughput and low memory consumption while the inference performance of Llama drops linearly with increasing context size") — no accuracy/quality numbers at 4-bit are reported at all, so this paper cannot inform the project's "≥97% of full-precision average, no axis below 93%" quantization-retention question.
