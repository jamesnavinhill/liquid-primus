# 2504.15077v5 — Think2SQL: Reinforce LLM Reasoning Capabilities for Text2SQL

**Relevance:** high
The paper's GRPO reward design for structured-output generation (dense partial-credit correctness reward plus explicit format/tag rewards to curb reward hacking) is directly analogous to the schema-validity + execution-correctness GRPO stage on this project's candidate ladder, and it demonstrates the method on small models (0.5B–7B) rather than only at frontier scale.

## TL;DR

The authors post-train Qwen2.5-Coder models (0.5B–14B) for Text2SQL using SFT on distilled reasoning traces followed by GRPO with a rule-based reward, and show that a dense partial-credit reward beats a binary execution-accuracy reward, especially for small models, while separate format/tag-count rewards keep the output structure well-formed without needing constrained decoding. A 7B model trained this way beats its untuned self by double digits and even beats much larger generalist models on the hard subset of BIRD.

## Techniques to try

- Replace binary correctness reward with a dense, partial-credit reward for structured-output RL: "we adopt a dense reward function that provides partial credit for partially correct SQL queries... This approach ensures the model receives feedback for partially correct SQL queries, encouraging incremental improvements during training, especially for small LLMs." (§2.3) — directly transferable to schema validity (e.g., field-level precision/recall/cardinality-style partial credit instead of pure valid/invalid).
- Separate structure-compliance rewards from the task-correctness reward rather than folding them together: "Format Reward (FR)... a binary reward indicating whether the output matches the expected format" and "Tag Count Reward (TCR)... penalizes the overuse or omission of tags" (§2.3) — a template for a tool-call "did it even parse as a call" reward distinct from "was the call/args correct," which maps onto this project's first-attempt schema-validity metric.
- Fixed reward-weighting recipe that worked in practice: "R=0.85⋅R_text2SQL+0.10⋅R_FR+0.05⋅R_TCR" (§2.3), i.e. correctness dominates, formatting is a small shaping term — a concrete starting point for weighting a schema-validity-plus-execution GRPO reward.
- SFT on reasoning traces before RLVR ("cold start") produces more robust, better-generalizing models than RL-only, even though RL-only can match or exceed it in-domain: "adding SFT traces before RLVR yields the most robust models overall, achieving the highest average accuracy on cross-domain benchmarks" (Appendix E) — relevant to the project's LoRA SFT → GRPO ladder ordering.
- Loss masking on distilled reasoning traces (train only on the trace + answer tokens, not the prompt) for SFT efficiency when traces are much longer than inputs (§2.2, §A.1).

## Baselines & datasets used

- BIRD (9,428 examples, 69 DBs, 37 domains) as main training/eval set, split into Simple/Medium/Challenging by SQL-construct count; 1,530-instance BIRD dev set used for evaluation since BIRD test is unavailable.
- Cross-domain generalization checked on Spider, Spider-Syn (paraphrase robustness), Spider-DK (implicit domain knowledge), and KaggleDBQA (real-world unnormalized schemas) — a useful precedent for testing whether a narrow post-training pass generalizes beyond its target domain, analogous to checking guardrail metrics don't erode.
- Baselines span 0.5B to 405B/671B open models plus GPT-4o and o3-mini, letting the paper isolate the effect of reasoning-trace SFT and RLVR from raw scale at ≤7B, which is the scale relevant here (target model is 1.2B, one size class below their smallest, 0.5B).

## Pitfalls / negative results

- Generic (non-task-specific) reasoning distillation can hurt: "all the distilled DeepSeek models with reasoning perform worse than their non-reasoning counterparts... generic reasoning skills are insufficient to solve the Text2SQL task effectively." (§3.2) — a caution against assuming any chain-of-thought SFT helps; it has to be task-specific.
- SFT without reasoning traces (SFTNT) sometimes underperforms even the untuned base model at larger size: "for the 7B model, the SFTNT variant performs slightly worse than the base model suggesting possible overfitting to the training data." (§3.3)
- Combining the two correctness reward types added no value and hurt: "When R_EX=1, R_QATCH is also 1, so combining the rewards adds no value... Empirically, this combination leads to suboptimal performance. Therefore, we keep them separate." (§2.3) — a concrete example of naive reward-combination failing, relevant to the "reward hacking" open question here.
- RL-only training yields shorter, terser reasoning traces than SFT+RL ("roughly one-fourth of the length"), and while RL-only wins in-domain, it generalizes worse cross-domain than SFT+RL (Appendix E) — a trade-off to watch for if this project's GRPO stage similarly shortens reasoning/justification before a tool call.
- Explicitly flagged limitation: gold, question-specific schema/tables are provided in-context during training and eval, not retrieved: "Real deployments must retrieve tables automatically; linking errors may reduce accuracy." (Table 5) — the reported numbers assume an easier setting than a real agent pipeline.
- Compute cost for GRPO here is substantial even at small scale: RLVR training ran "8×H100 80GB GPUs... over 40h (3B) and 60h (7B)" for 1 epoch/567 gradient steps — a data point on how expensive a full GRPO pass can be even at sizes near this project's 1.2B target.

## Metric / eval choices

- Execution Accuracy (EX): binary, exact row-by-row match between predicted and target SQL execution — the "sparse" baseline reward/metric.
- QATCH-derived partial-credit sub-metrics used as reward components: Cell Precision, Cell Recall, Tuple Cardinality, averaged into R_QATCH ∈ [0,1] (Appendix D) — a worked example of decomposing a pass/fail correctness check into partial, gradient-rich sub-scores, which is the same shape of problem as scoring "how close" a malformed/near-miss tool call is.
- Format Reward and Tag Count Reward are computed via regex/tag-count checks on the raw output, not model-scored — consistent with this project's constraint that no model-scored stored reward may be reused as a training signal.

## Open questions for our project

- The dense partial-credit reward here is built from SQL execution semantics (cell overlap, row counts) — it's unclear how directly this generalizes to JSON Schema / tool-call argument validation, where "partial correctness" isn't as naturally defined (e.g., is a call with one wrong argument value 90% correct or 0%?). Worth designing an analogous partial-credit scheme (per-field validity/match) rather than assuming binary schema-valid/invalid is the only option.
- The paper only ever tests reward-hacking mitigation (Tag Count Reward) for exactly one structural pattern (<think>/<answer> tags exactly once); it doesn't test whether a model can hack partial-credit correctness rewards (e.g., padding extra correct-looking cells to game Cell Precision/Recall) — an open risk for a schema-validity partial-credit reward too.
- All positive results are shown at ≥0.5B and the strongest gains are reported at 3B–14B; the paper does not test below 0.5B, so it's untested whether reasoning-trace SFT + GRPO still helps at 1.2B or whether a hybrid architecture (versus pure transformer here) changes the picture.
- No content in this paper reads as an instruction directed at the reader; it is a standard research paper describing methodology and results.
