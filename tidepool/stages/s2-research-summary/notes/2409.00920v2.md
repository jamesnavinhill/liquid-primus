# 2409.00920v2 — ToolACE: Winning the Points of LLM Function Calling

**Relevance:** high
Directly informs the SFT/data-mix rung of the candidate ladder: it gives a concrete synthetic-data pipeline for function-calling SFT, a transferable LoRA recipe at comparable model scale, and a sharp negative result on what happens when "flag rather than call" training examples are dropped — exactly the failure mode the malformed-tool-return probe is designed to catch.

## TL;DR

ToolACE is an agentic pipeline that synthesizes a large, diverse API pool and matching multi-turn dialogs (single/parallel/dependent/no-call), filters them with a rule + model dual-verification layer, and uses the model-being-trained's own loss to keep dialog difficulty in its "learnable" zone. LoRA-SFT on this data lifts LLaMA-3.1-8B-Instruct to state-of-the-art BFCL-v3 scores rivaling GPT-4, and a scaling study shows even 0.5B–1.8B Qwen1.5-Chat models — which could barely produce structured output raw — gain substantially from fine-tuning on the same data.

## Techniques to try

- Use the model being fine-tuned as its own "complexity evaluator": score candidate training samples by the tuned model's own next-token loss and keep only samples in a data-driven complexity band, rather than a fixed difficulty. ("the loss of a data sample is generally positively correlated with (1) the number of candidate APIs available for selection, (2) the number of APIs utilized, and (3) the dissimilarity between the user query and the API descriptions" — Section 2.2.2)
- Dual-layer data verification before training: a cheap rule checker (API name in tool list, required params present, regex-checked parameter formats) followed by an LLM-based checker split into hallucination detection, consistency validation, and tool-response-format checks. ("we propose an automatic dual-layer verification system (DLV) to verify our synthesized data ... which consists of a rule verification layer, and a model verification layer" — Section 2.3) The ablation shows both layers matter: "the model trained on dually verified data significantly outperforms both ablation models in terms of AST and overall accuracy" (Section 3.3.1).
- Deliberately include a "non-tool-use" / irrelevant-query dialog type in the SFT mix, not just successful calls — this is the category that teaches refusal/flagging behavior (see pitfall below).
- Concrete LoRA starting point for a comparable-scale SFT run: rank 16, alpha 32, learning rate 1e-4, cosine schedule, batch size 48, 3 epochs (Table 5, used for 8B-parameter backbones).

## Baselines & datasets used

- Benchmarks: BFCL-v3 (Berkeley Function-Calling Leaderboard, 4,951 test cases, AST + executable + relevance/irrelevance sub-scores) and API-Bank (314 dialogues, 753 API calls; Call and Retrieval+Call metrics).
- Backbones: LLaMA-3.1-8B-Instruct (main), LLaMA-3-8B-Instruct, Qwen1.5-Chat series at 0.5B/1.8B/4B/7B for the scaling study.
- Head-to-head data comparison at matched size (25,000 samples, same LLaMA-3.1-8B-Instruct base): ToolACE data reaches 58.19 BFCL overall vs. 40.51 for xLAM's dataset and 24.90 for ToolLLM's dataset (Table 6) — a same-model, same-data-size comparison that isolates data quality from model choice.

## Pitfalls / negative results

- Removing the "multi-type" data category (includes irrelevant-query / no-call examples) from an otherwise matched 25k-sample training set collapsed irrelevance detection from 86.42 to 6.99, i.e. the model essentially stopped recognizing when no tool applies: "excluding multi-type samples hampers the model's ability to detect when the candidate tools are irrelevant to the question, resulting in only 6.99% accuracy in irrelevance detection" (Appendix E.2, Table 7). This is the clearest evidence in the paper that "flag rather than assert" behavior has to be explicitly represented in the training mix — it does not emerge from call-only data.
- Removing parallel-call examples specifically damaged multi-tool-call ability: "removing parallel execution data significantly impairs the model's ability to invoke multiple tools concurrently" (Appendix E.2), while removing nested/dependent samples had only a minor effect on this particular benchmark, because "almost none [test samples] involve dependent tool usage" — a benchmark-coverage caveat worth remembering when reading any BFCL number.
- Complexity evaluator ablation: using a stronger external model (Qwen1.5-14B-Chat) instead of the model actually being trained as the complexity judge produced a worse Non-live AST score despite a slight Live AST gain, and a weaker external evaluator (Qwen1.5-7B-Chat judging an 8B learner) showed the opposite pattern — self-judged complexity ("LLaMA-8B | LLaMA-8B") gave the best overall score, 59.22 vs. 57.61/57.67 (Appendix E.3, Table 8).
- The authors flag their own complexity-based sampling as potentially self-reinforcing: "the non-uniform sampling may introduce bias, such as causing the model to struggle with learning difficult examples after one round of training, effectively remaining in its comfort zone" (Appendix H) — a caution against using self-assessed loss as the sole curriculum signal without periodic re-evaluation.
- Few-shot in-context learning (no fine-tuning) underperformed both zero-shot and fine-tuned settings, and was actively misled by irrelevant retrieved examples: "the model is misled by the tools in the few-shot examples due to its limited reasoning ability and generalization, selecting those instead of the tools in the test sample, which further exacerbates the model's hallucination phenomenon" (Appendix G) — supports SFT over prompting-only approaches for this size class.

## Metric / eval choices

- BFCL "Overall Accuracy" is defined as "the unweighted average of the accuracies across all sub-categories" (Appendix C.1) — useful to know exactly what a published BFCL-v3 "overall" number is aggregating over when comparing to this project's own BFCLv3 targets.
- Irrelevance score = "the number of correct non-function-call predictions divided by the total number of test samples"; Relevance score is the analogous count for correct-but-unscored-on-parameters function calls (Appendix C.1) — precise operational definitions that map onto (but are not identical to) this project's flag-rate/false-flag-rate sub-criterion; BFCL's irrelevance test set is not the same as a malformed-tool-return probe, so the numbers aren't directly transferable, only the framing is.
- General-capability check used to argue "no regression": MMLU, HumanEval, GSM8K, CommonSenseQA alongside BFCL, all at 8B scale — same style of guardrail-metric table this project needs, though the actual numbers are 8B-scale and not reported in the excerpted body text (only described qualitatively as "negligible ... degradation").

## Open questions for our project

- All fine-tuned, verification-ablated, and complexity-ablated results are reported at 8B (LLaMA-3.1/LLaMA-3, Qwen1.5-7B); the only smaller-scale evidence is a scaling curve for raw vs. fine-tuned Qwen1.5-0.5B/1.8B-Chat showing "smaller raw models ... showed minimal function-calling ability, struggling to generate structured outputs" before fine-tuning closed much of the gap — encouraging directionally for a 1.2B target, but no BFCL numbers at that scale are given in this paper, and Qwen1.5 is a different (non-hybrid, larger-vocab) architecture than LFM2.5.
- The paper has no quantization, throughput, or GGUF-conversion content at all, so it cannot speak to this project's 4-bit retention (≥97%) or 5% decode-throughput targets.
- Unclear whether the self-guided complexity-evaluator trick (loss of the model being trained) is stable under LoRA specifically, or only demonstrated under the same LoRA setup used throughout this paper (rank 16/alpha 32) — worth checking whether it needs a higher-rank or full fine-tune to give a reliable loss signal at 1.2B.
- No text in this paper reads as an instruction directed at the reading agent; it is a standard research paper describing its own pipeline and results.
