# 2605.01347v1 — MAD-OPD: Breaking the Ceiling in On-Policy Distillation via Multi-Agent Debate

**Relevance:** medium
Offers a concrete, quotable divergence-choice principle for tool-use/agentic on-policy distillation and a shared-vocabulary caveat worth heeding, but the method itself (multi-teacher debate with 8B–32B teachers, 8×H20 serving, full-vocab logit sidecars) is infrastructure this project's 1.2B/single-GPU scope cannot replicate.

## TL;DR

MAD-OPD distills a student from a *debate* between two teacher models (rather than one), using each teacher's post-debate confidence to weight its contribution, and shows that JSD works better than reverse-KL for multi-step tool-use/agentic distillation while reverse-KL works better for single-turn code generation. Tested with Qwen3/Qwen3.5 teachers (8B–32B) and students down to 1.7B on BFCL-v4, τ²-Bench, VitaBench, LiveCodeBench, and MBPP+; not tested on anything near 1.2B or in a quantized setting.

## Techniques to try

- Divergence choice for on-policy distillation of tool-use/agentic behavior: use JSD, not reverse KL. "Multi-step agentic tasks → $D=\mathrm{JSD}_{\beta}$. By Prop. 1.1, the per-position logit gradient is bounded by 2 uniformly across positions and privileged $p$–$q$ gaps, supporting stable long-trajectory training" (Remark 1, §3.3) — relevant if the project's later "quantization-aware distillation" ladder step uses a token-level on-policy distillation loss against a larger teacher for tool-calling behavior.
- If a second teacher/reference model is cheaply available, weight its contribution by self-reported, post-hoc confidence rather than fixed/uniform weighting: "the weights reflect post-deliberation certainty rather than pre-debate agreement... the increment requires only that relative confidence ordering correlates with relative quality on average, not that any single $c_k$ is accurate" (§4.2, App. C.1) — a lightweight idea even without full multi-agent debate infrastructure.

## Baselines & datasets used

- BFCL-v4 (Berkeley Function-Calling Leaderboard v4) as the agentic training/checkpoint-selection benchmark, "AST-based correctness checking on the emitted function call schema, comparing argument names, types, and values against ground truth" (App. B.8) — same family as this project's BFCLv3 target metric, though a newer version.
- ToolACE (~16K step-split agentic instances) as agentic training data (App. B.3).
- τ²-Bench and VitaBench as held-out multi-turn tool-use benchmarks, both scored using **Claude-4.6-Opus as the user simulator** (App. B.9, B.10) — an external LLM judge/simulator in the eval loop, not a training reward, but worth flagging given this project's "no model-scored stored reward may be reused as a training signal" constraint.
- LiveCodeBench v6 and MBPP+ for code generation (not directly relevant to a tool-calling-focused project).

## Pitfalls / negative results

- Naive multi-teacher averaging can hurt: "MT-OPD's per-token gradient conflict drops it below single-teacher OPD on code, because per-token averaging of two teacher distributions interpolates between distinct coherent code paths each teacher prefers and produces incoherent supervision the student then absorbs" (§5.2) — a caution against blending signals from multiple teachers/checkpoints without more care.
- Divergence choice reverses gains depending on task type: reverse-KL causes agentic training-loss spikes ("reverse KL, $\mathcal{L}_{\mathrm{MAD}}$ swings across two orders of magnitude: the empirical signature of the unbounded per-token logit gradient... which fires whenever the privileged teacher disprefers a student-sampled token", App. C.5) while JSD underperforms on code. A single fixed divergence for a mixed agentic+structured-output curriculum may not be optimal.
- More debate/deliberation is not always better: "$R=3$ overshoots: the extra round inflates the prompt context and introduces noise that erodes the gains (Ag-Avg drops by −8.27% relative to $R=2$)" (App. C.6).
- Explicit scope limitation that maps onto this project's vocab concern: "MAD-OPD requires teacher token-level distributions, excluding black-box (API-only) models, and assumes a shared vocabulary between teacher and student; black-box and cross-vocabulary distillation are open extensions" (§6, Limitations) — any token-level distillation approach for LFM2.5 (65,536-token vocab) would need a teacher sharing that tokenizer, or would hit this exact unsolved cross-vocabulary problem.

## Metric / eval choices

- BFCL-v4 reported as "the unweighted mean across all eight subtasks" (App. B.8), including Miss-Function and Miss-Parameter subtasks that test refusal/clarification behavior — conceptually adjacent to this project's "flag rather than assert" sub-criterion, though BFCL's miss-parameter/miss-function setup is not the same as the malformed-tool-return probe this project needs.
- Practical checkpoint selection via a cheap dev proxy: "checkpoints are evaluated every 10 steps for agentic tasks on BFCL-v4 and every 5 steps for code tasks on LCB-v6, and the highest-scoring checkpoint for each task type is then evaluated once on all five benchmarks" (App. B.6) — a reasonable pattern for avoiding overfitting to a single eval when compute for full eval sweeps is limited.

## Open questions for our project

- All experiments use teachers of 8B–32B and students of 1.7B–14B, with the smallest gap still ~5–15x; nothing here demonstrates the debate/distillation recipe scales down to a ~1.2B target student, nor addresses post-quantization behavior at all. Unclear if any of this transfers to the project's 4-bit GGUF target.
- The paper explicitly excludes black-box/API teachers and requires shared teacher-student vocabulary — worth asking whether any candidate teacher for this project shares LFM2.5's 65,536-token vocabulary, or whether this line of technique is a non-starter here.
- No instruction-like text directed at the reader was found in the paper; it reads as a standard research paper throughout.
