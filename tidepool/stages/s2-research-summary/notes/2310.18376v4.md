# 2310.18376v4 — SQLformer: Deep Auto-Regressive Query Graph Generation for Text-to-SQL Translation

**Relevance:** low
Real topic overlap (structured SQL generation, schema-aware decoding) but the method is a from-scratch bespoke GNN+Transformer architecture trained on Spider-family datasets, not a fine-tuning recipe applicable to post-training an existing instruct LLM like LFM2.5-1.2B.

## TL;DR

SQLformer is a custom encoder-decoder architecture (not a fine-tuned pretrained LLM) that represents the natural-language question and the DB schema as graphs, uses learnable tokens to select the top-k relevant tables/columns, and autoregressively generates the SQL query as an abstract-syntax-tree graph in BFS order. It reports state-of-the-art exact-match/execution accuracy on Spider, SParC, CoSQL, and three zero-shot generalization benchmarks, trained from scratch (not by fine-tuning a decoder-only chat model).

## Techniques to try

- Baking structural validity into generation by construction rather than via post-hoc constrained decoding: node type, adjacency, and previous-action embeddings are added as a bias term directly inside self-attention so every decoding step is aware of what SQL-grammar state it is in ("we modify Eq. 3 so that Ψ(N^V) and Φ(N^A) act as a bias term in the attention calculation" — Section 4.4). This is conceptually related to structured-output reliability but requires a custom architecture/training loop from scratch, not something a LoRA/DPO/GRPO pass on an existing decoder-only model can replicate.
- Explicit table/column "selection" sub-task as an auxiliary signal: prepending learnable `Z_tables`/`Z_cols` tokens whose encoder-output states are projected to per-table/per-column probabilities, then masking columns to only those belonging to selected tables ("A masking vector is applied to P_columns to ensure that only columns from the selected tables are considered" — Section 4.3). The ablation shows this component matters most (see below), which is a generic reminder that schema/context grounding can be worth an explicit auxiliary objective — but again this is architecture, not a fine-tuning recipe.

## Baselines & datasets used

- Spider (8,659 train / 1,034 dev / 2,147 test, 300 DBs, 138 domains), plus SParC and CoSQL for context-dependent (multi-turn) text-to-SQL, and Spider-DK/Spider-SYN/Spider-Realistic for zero-shot domain-generalization and robustness evaluation (Appendix E).
- Compared against RAT-SQL, LGESQL, RESDSQL, GRAPHIX-T5-3B, T5-3B, PICARD — all text-to-SQL-specific systems, none of which are the kind of general-purpose instruct/tool-calling models this project targets.

## Pitfalls / negative results

- Ablation: removing table/column selection is the single biggest degradation, dropping EM accuracy from 78.2% to 72.3% on Spider dev ("table and column selection has the biggest impact, with a performance drop from 78.2% to 72.3% when removed" — Section 5.3) — i.e., ungrounded schema context hurts structured-output accuracy substantially more than losing syntactic (dependency-graph, part-of-speech) features, which only cost 0.7–0.9 points.
- Swapping their Transformer decoder for the standard LSTM-based tree decoder (Yin and Neubig 2017a) costs 4 points EM (78.2% → 74.2%), suggesting that for this class of grammar-constrained generation the decoder's ability to retain long-range context (needed for sub-queries) matters — of debatable relevance since our target model is already a Transformer decoder.
- Performance still drops sharply with query complexity even with all these structural biases: 92.7% EM on "easy" queries down to 51.2% on "extra hard" (Table 2) — a reminder that structural grounding alone doesn't close the gap on genuinely hard compositional generation, which may bear on how much to expect from architecture/prompt tricks alone versus training signal quality.

## Metric / eval choices

- Uses Exact Match (EM) and Execution accuracy (EX) as the two standard text-to-SQL metrics, explicitly noting EX can give false positives ("there can be instances where EX gives false positives" — Section 5.1) and EM is used as a complementary stricter check. Not directly reusable for BFCL/JSON-schema validity, but is a reminder that execution-based correctness metrics (analogous to this project's "execution correctness" GRPO reward) can be gamed/false-positive without a structural check alongside them.

## Open questions for our project

- None of the paper's numbers are at ≤8B-parameter LLM fine-tuning scale in the sense this project needs (this is a from-scratch ~dozens-of-millions-of-parameters custom architecture, not a post-trained decoder-only model), so no number here directly grounds any of the pre-registered targets (BFCL, IFEval, quantization retention, etc.).
