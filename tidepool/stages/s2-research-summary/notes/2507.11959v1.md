# 2507.11959v1 — PoT-PTQ: A Two-step Power-of-Two Post-training for LLMs

**Relevance:** low
Real overlap on topic (low-bit weight-only PTQ, calibration-efficient scale refinement) but the method targets a non-GGUF power-of-two format with custom CUDA dequant kernels at 2–3 bit, not the 4-bit GGUF/llama.cpp path this project ships, and evaluation never touches structured output, tool calling, or instruction following.

## TL;DR

The paper proposes a two-step post-training quantization scheme that constrains LLM weights to signed powers-of-two (PoT) instead of uniform integers: first a data-agnostic grid search picks per-group scales purely from weight statistics, then a lightweight calibration pass fine-tunes those scales (via a learnable residual) against ~128 WikiText-2 sequences. It beats GPTQ/AWQ/OmniQuant on perplexity at 2- and 3-bit on LLaMA1/2 (7B–30B), and ships a custom bit-manipulation dequant kernel that is 3.67x faster on V100 and 1.63x on RTX 4090 versus FP16 dequantization — but none of this is in the GGUF/llama.cpp ecosystem this project targets.

## Techniques to try

- Two-stage calibration pattern is generally transferable in spirit (not implementation): "we initialize the quantization scales with a robust starting point, and (ii) refine these scales using a minimal calibration set" (Abstract) — cheap calibration-set fine-tuning of quantization scales, if analogous tooling exists for GGUF/int4, could be worth checking as a lever for closing the last few points of the ≥97% full-precision retention target.
- The learnable-scale fine-tuning only touches "one learnable scalar per weight group" (Section 3.3, "Efficiency.") and needs "only a few epochs on a small calibration set" — reinforces that scale/calibration-only refinement (no full retraining) is a cheap step to try before reaching for quantization-aware training.

## Baselines & datasets used

- Baselines: RTN, GPTQ, AWQ, OmniQuant (Table 1, Table 3), all uniform-integer PTQ methods adapted to PoT for comparison (Table 2).
- Calibration/eval data: WikiText-2 perplexity (128 randomly sampled 2048-token calibration sequences) and the Open LLM Leaderboard harness (arc-c, arc-e, boolq, hellaswag, piqa, winogrande) — general knowledge/QA tasks only, no tool-use or JSON/schema-following benchmarks.
- Models: LLaMA1 and LLaMA2 at 7B, 13B, 30B — 7B is the only size at/below this project's 8B preference threshold.

## Pitfalls / negative results

- "Applying Step 2 (fine-tuning) without Step 1 ... results in inferior performance, likely due to poor initial scale estimates" (Section 5.4) — calibration-only fine-tuning without a good init is markedly worse (e.g., LLaMA1-7B 2-bit: 51.87 PPL with tuning-only vs 9.79 with both steps, Table 4). A caution against skipping principled scale initialization if we ever try analogous scale-tuning for GGUF.
- Naively porting existing PTQ methods (RTN/GPTQ/AWQ/OmniQuant) to a PoT grid destroys accuracy — GPTQ_POT diverges to NaN or ~1e4–1e5 perplexity (Table 2) — a reminder that quantization tricks tuned for one numeric format (uniform int) do not transfer to another (PoT) without dedicated recalibration.
- The method's speed gains depend on a bespoke CUDA dequantization kernel exploiting sign/exponent bit layout; it is explicitly benchmarked only on Tesla V100 and RTX 4090, not the RTX 2080 Super class of device this project's reference deployment uses, and is unrelated to llama.cpp's existing INT4 GEMM/dequant path.

## Metric / eval choices

- Primary metric is WikiText-2 perplexity, plus a 6-task QA/commonsense harness average — no structured-output, JSON-validity, or agentic tool-call metric is used anywhere in the paper, so it offers no direct evidence on this project's core question of whether quantization disproportionately harms structured output versus general knowledge.

## Open questions for our project

- The paper's own ablation (Table 4) suggests scale-calibration fidelity matters a lot at very low bit-widths (2–3 bit); does an analogous sensitivity exist for GGUF Q4_K-style quantization at 4-bit, or is 4-bit far enough from the "non-smooth error surface" regime described here (Section 3.2, "Motivation") that this concern doesn't apply?
- No content in this paper reads as an instruction directed at the reader; it is a standard research paper description throughout.
