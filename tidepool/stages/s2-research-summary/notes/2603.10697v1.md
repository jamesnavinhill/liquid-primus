# 2603.10697v1 — EvoSchema: Towards Text-to-SQL Robustness against Schema Evolution

**Relevance:** medium
Directly relevant to the "flag rather than assert" question and to SQL-dialect specialization via a concrete abstention-training result, but it is a 7-8B text-to-SQL parsing study with no tool-calling schema, quantization, or throughput content.

## TL;DR

EvoSchema is a BIRD-derived benchmark and training-data augmentation recipe that perturbs SQL database schemas (10 types: column/table add, remove, rename, split, merge) while keeping the NLQ fixed, then fine-tunes 7-8B text-to-SQL models on a mix of original + perturbed triples. Training on the mix makes models much more robust to schema drift, and a separate experiment trains models to abstain when required tables/columns are removed — this is the paper's closest analogue to this project's "flag rather than assert" goal, including a measured false-flag cost.

## Techniques to try

- Data-mix augmentation for robustness: fix the input/question, vary the "schema" (analogue: vary tool schema / JSON schema) and correct output across many structural perturbations of the same underlying task, then train on original + perturbed data merged and shuffled. ("we obtain multiple triples that can be derived from each of the original triples. We train the model by learning multiple schema designs and SQLs to the original question mappings" — Section 4, Training Paradigm)
- For "should refuse" cases, construct explicit out-of-scope training examples with a fixed abstention string as the gold target, rather than hoping the model infers when to refuse: they use `"The given column information is insufficient to generate an SQL query to answer the question"` and the table-level equivalent ("Remove columns in gold SQL" / "Remove tables" — Section 3.6).

## Baselines & datasets used

- Seed dataset: BIRD (chosen over Spider for more realistic/complex schemas and SQL). Perturbations generated with a mix of heuristics + GPT-3.5/GPT-4/Claude 3.5 for synthesis, plus human verification only on the eval set (train perturbations are fully automatic, no human annotation).
- Open-source models fine-tuned: Code Llama-7B, Mistral-7B, Llama 3-8B, SQLCoder-7B — all well above this project's 1.2B target, so absolute numbers don't transfer, but the relative effect of the training intervention may generalize directionally.
- Closed-source models (GPT-3.5, GPT-4) used eval-only as a robustness reference point — found to be comparatively stable across perturbations without any special training, attributed to broader pretraining exposure.
- Additional baselines: in-context learning (3-shot) and CHESS (schema-selection + candidate generation pipeline using GPT-4o for pruning).

## Pitfalls / negative results

- Training for abstention hurts normal-case and in-scope performance: "incorporating out-of-scope types results in performance degradation across both original and in-scope evaluation sets" and error analysis shows the abstention-trained model becomes over-conservative, refusing even when a valid gold SQL exists (Section 6.4). This is a direct precedent for the tension between this project's flag-rate target and its "stay within 2 points on guardrail metrics" constraint.
- Abstention accuracy is imperfect even after targeted training: "the TP is only around 84%, which indicates that the model still has a 16% chance to make a prediction even when there should not be an SQL" (Section 6.4) — i.e. even with dedicated out-of-scope training data, a ~7-8B model only reaches ~84% correct-abstention rate, which is exactly this project's flag-rate ballpark (≥0.80 target) but achieved with a real false-flag cost, not for free.
- Perturbation training isn't free even on the in-scope side: "adding the perturbation data during training leads to a slight Exec Acc (EX) drop for original non-evolved evaluation data, adding, removing and renaming column types" — small regressions on simple/unperturbed cases even though it helps a lot on hard structural shifts.
- Naively adding irrelevant tables as a proxy for full perturbation training doesn't work: it approximates the "Add Tables" robustness gain but "caused a performance drop on other perturbation types," so partial data augmentation isn't a shortcut for the full mix (Section 6.5).
- Schema-pruning pipelines (CHESS) can over-prune and drop needed context, performing worse than a plain fine-tuned baseline specifically on merge-columns and merge-tables cases — a caution for any "prune irrelevant tool schemas before the model sees them" design.
- Table-level structural changes (add/split/merge tables) hurt far more than column-level changes (add/remove/rename columns): e.g. Table Match F1 for Code Llama drops from 89.77 (original) to 57.88 on "Add Tables" without perturbation training, vs. much smaller drops for column-level perturbations — suggests coarse structural schema/interface changes are the harder robustness case, not renaming.

## Metric / eval choices

- Two schema-specific metrics introduced: Table Match F1 and Column Match F1 (precision/recall over which tables/columns the model's SQL references vs. gold) — a fine-grained localization metric to have alongside end-to-end execution accuracy, potentially adaptable as "did the model select the right tool/right function" checks in a tool-calling context.
- They note plain Execution Accuracy is noisy ("Exec Acc can still make mistakes when different SQL queries produce the same results... or sometimes both the gold SQL and wrong predicted SQL return the empty which may mislead the evaluation") and fall back to human evaluation for baseline comparison, with McNemar's test for significance — a reminder that this project's own execution-correctness reward (GRPO stage) needs the same false-positive-match sanity check.

## Open questions for our project

- The paper never touches quantization, on-device throughput, or vocabulary size, so it has nothing to say on the GGUF/4-bit or 65K-vocab questions in our brief.
- Would the abstention-degradation pattern (over-conservative refusals costing ~similar magnitude to the intended flag-rate gain) hold at 1.2B, or does a smaller model degrade more sharply when asked to learn both "do the task" and "know when not to"? This paper only tests 7-8B models, so the scale gap is exactly the kind of thing our brief asks us to flag.
- No instruction-addressed-to-model text was found in the paper; it reads as a standard research paper throughout.
